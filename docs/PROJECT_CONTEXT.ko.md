# TOV 프로젝트 컨텍스트

## 93. 순서가 보장되는 원격 아바타 이동 전송

- Authority 플레이어 이동은 고정 Tick에서 계산되는 일시적 결과로 유지한다.
  Zone Tick에서 아바타 상태가 변경되면 서버는 평가된 세션 ID, 서버 Tick/시간,
  위치, 속도, 접지 상태, 이동 상태를 포함한 `zoneMotionFrame`을 묶어서 보낸다.
  기존 HTTP Zone 스냅샷은 입장, 재연결, 존재 상태 복구에만 사용한다.
- Unity 원격 아바타는 Authority 시간보다 약 100~150ms 늦은 세션별 정렬
  스냅샷 타임라인을 표시한다. 승인된 두 샘플 사이를 보간하고 짧은 속도 제한
  외삽만 허용하며, 오래되거나 순서가 뒤바뀐 Tick은 거절한다. 세션 변경이나 긴
  단절 뒤에는 새 기준점을 만든다. 입력 목적지나 Unity가 임의로 정한 속도로 최신
  위치를 추격해서는 안 된다.
- SignalR 연결 소유권은 연결 세대별로 구분한다. 프로토콜 handshake 응답 뒤에만
  연결 완료로 처리하며, 이전 소켓 세대의 메시지는 현재 연결을 끊거나 시간을
  되돌릴 수 없다. 재연결은 상한이 있는 지수 백오프와 jitter를 사용한다.
- 모션 프레임은 변경분이며 전체 접속자 목록이 아니다. 아바타 제거는 인증된 전체
  복구 스냅샷과 grace 정책으로만 결정한다. 이 전송은 이미 평가된 Authority 결과의
  Unity 표현이므로 새 게임 규칙 블록이나 영속 Fact를 만들지 않는다.

> canonical 규칙 정의는 규칙 ID와 정의 버전으로 식별되는 전역 불변
> 콘텐츠입니다. 월드 패키지는 액션과 콘텐츠를 활성화하지만, 배정된 규칙
> 블록은 이 전역 식별자로 발행 정의를 해석합니다. 규칙이 처음 발행된 패키지
> 버전과 월드의 현재 패키지 버전이 다르다는 이유로 실행을 거절하면 안 됩니다.

## 81. 데이터 작성형 전투 표현 경계

- 장착 입력은 공용 Unity Input Action 자산에 작성합니다. 입력은 상호작용
  트리거만 발행하며, `equip_action` / `unequip_action`과 할당된 규칙 블록이
  권한과 상태 전환을 계속 소유합니다.
- Damageable 표현에는 `collision_proxy_shape`, `collision_radius`,
  `collision_height`로 구성된 충돌 프록시 계약이 필요합니다. Unity는 이
  트리플로 쿼리 전용 피격 형상을 만들며 계약이 없거나 모호하면 실패
  폐쇄합니다. 임의 렌더러나 자식 Collider를 추측해 선택하지 않습니다.
- 무기 접촉 쿼리는 비할당 빠른 경로를 사용하지만 버퍼가 가득 차면 고정
  용량 때문에 접촉을 누락하지 않도록 완전 쿼리로 재시도합니다. 쿼리
  용량이 Authority 승인 대상의 접촉 여부를 결정해서는 안 됩니다.
- 장착 이동 표현은 장착 엔티티에 투영된 `idle_animation_intent`와
  `move_animation_intent` Fact로 선택합니다. 템플릿 ID와 시각 카탈로그는
  자산 위치를 찾을 수 있지만 의미 권한이나 애니메이션 의도의 대체 경로가
  아닙니다.

## 81. Authority 투영 기반 액터 체력 피드백

- 플레이어와 몬스터 머리 위 숫자는 Authority 투영의 표준
  `current_health` 변화만 표현합니다.
- 최초 값은 기준값으로만 저장합니다. 이후 감소는 피해, 증가는 회복으로
  표시하며 Unity는 체력을 예측하거나 변경하지 않습니다.
- 프리팹이나 오브젝트 이름이 아니라 영속 엔티티 GUID와 시각 경계에
  연결합니다. 값이 없거나 중복이면 표시하지 않고, 사라진 엔티티의
  기준값도 제거합니다.

> **언어 정책**: 영문 원본은 [`PROJECT_CONTEXT.md`](PROJECT_CONTEXT.md)입니다.
> 두 문서는 같은 변경에서 함께 갱신합니다. 구현 식별자·API·코드명은 영문
> canonical ID를 그대로 유지하고, 제품 정책과 설명은 이 한국어 문서에서도
> 동일한 의미를 가져야 합니다.

> **목적**: TOV 개발을 계속 이어 갈 때 우리 둘이 공통으로 참고하는 결정
> 기준 문서입니다. 시스템 경계, 온톨로지 규칙, 데이터 소유자, 사용자 경험의
> 방향이 바뀌면 이 문서부터 함께 갱신합니다.

## 1. 제품 방향

TOV는 샌드박스 월드 빌딩 게임입니다. 사용자는 준비된 월드에 들어가
오브젝트를 배치하고, 오브젝트의 온톨로지 데이터와 규칙 블록을 정의하며,
그 결과를 시뮬레이션·애니메이션·물리 표현·상호작용·향후 멀티플레이로
확인합니다.

핵심은 **데이터로 정의되는 의미**입니다.

- 오브젝트를 코드에서 나무·튜브·배·돌로 고정하지 않습니다.
- 오브젝트의 의미는 온톨로지 트리플, 선택한 물리 프로필, 연결한 규칙 블록에서
  나옵니다.
- Unity는 결과를 보이고, 충돌을 감지하고, 애니메이션을 재생합니다. Unity 코드가
  숨겨진 두 번째 규칙 엔진이 되면 안 됩니다.

현재 콘텐츠 콘셉트는 바다를 건너 자기만의 세상을 만들고, 오브젝트 배치와
관계/행동 정의로 월드를 확장하는 것입니다.

## 2. 현재 기준선

| 영역 | 현재 상태 |
| --- | --- |
| Unity | Unity 6 (`6000.4.7f1`), 진입 씬 `Assets/Scenes/TormiaBootstrap.unity`, 작성 원본 씬 `TormiaWorld.unity` 및 `TormiaUI.unity` |
| 비주얼 | Poly Style 환경 에셋, 런타임 UI는 Farm Game UI kit을 아트 기준으로 사용 |
| 월드 편집 | 런타임 오브젝트 배치, 온톨로지 트리플 편집, 규칙 블록/물리 선택 |
| 온톨로지 런타임 | Fact, 규칙 DB, 추론, 액션, 퀘스트, 애니메이션 Intent 선택, 언어팩 |
| 환경/장비 사례 | 물 영역 감지, 이동 표현, 물리 프로필, 착용/장착 가능한 월드 오브젝트 |
| 로컬 서비스 | Docker PostgreSQL + Redis + .NET World Authority (`http://127.0.0.1:5272`) |
| 멀티플레이 기반 | 월드 리비전 명령, Zone, 임시 입력, kinematic authority motion, SignalR 알림, 원격 아바타 표현 |
| 계정 기반 | 이메일/비밀번호 인증, Bearer 세션, 계정 소유 캐릭터 프로필, 저장 캐릭터/월드 선택, Unity 입장 흐름 |

현재 플랫폼은 **개발용 기반**이며, 출시 가능한 운영 서비스가 완성된 것은 아닙니다.

## 3. 시스템 지도와 데이터 소유권

```text
플레이어 / 월드 편집기
        |
        v
Unity 클라이언트 -- 의도 명령 --> World Authority API
   |                                  |
   |                         PostgreSQL: 영속 월드 데이터
   |                         Redis: 임시 조정 / 런타임 lease
   |
   +-- 로컬 어댑터: 렌더러, Animator, CharacterController,
       UI, 물/물리 표현
```

| 소유자 | 담당하는 데이터/행동 | 담당하면 안 되는 것 |
| --- | --- | --- |
| 계정 서비스 | 사용자 신원, 저장 캐릭터 프로필, 캐릭터 템플릿, 선택한 파츠 ID | 공유 월드 의미, 추론 시뮬레이션 상태 |
| World Authority | 배치된 엔티티, 작성된 트리플, 규칙 블록 연결, 권한, 리비전/이벤트 | 비밀번호, Unity 씬 내부 구조 |
| 온톨로지 엔진 | 데이터 기반 규칙 적용과 추론 상태 생성 | 렌더링, 직접 Transform 이동, UI 배치 |
| Unity 어댑터 | 입력, 충돌/지형 접촉, 애니메이션, 렌더러, 시각 물리 | 숨겨진 게임 규칙 중복 구현 |
| PostgreSQL | 영속적이고 리비전된 데이터 | 매 프레임 관측값/입력 샘플 |
| Redis | 만료되는 입력, 모션, 세션, 서버 간 조정 | 영구 월드 이력 |

Unity는 PostgreSQL이나 Redis에 직접 접속하지 않고 World Authority API와만 통신합니다.

## 4. 온톨로지 정책 (반드시 지킬 기준)

### 4.1 Fact의 종류

| 종류 | 예시 | 위치 | 저장 여부 |
| --- | --- | --- | --- |
| 작성/정적 Fact | `BeachWater_01 has_concept WaterRegion` | 월드 저작 데이터 | 영속 월드 데이터 |
| 관측/런타임 Fact | `Player immersion_depth Deep` | 어댑터가 만든 런타임 관측 | 임시, 매번 재계산 |
| 추론 Fact | `Player movement_mode Swimming` | 규칙 엔진의 결과 | 원인 대신 직접 작성하지 않음 |
| 계정 프로필 데이터 | 캐릭터 이름, 템플릿, 선택한 시각 파츠 ID, 스킬·소유 펫·소지 아이템 canonical 관계 | 계정 캐릭터 프로필 | 영속 계정 데이터, **월드 Fact 아님** |
| 표현 상태 | Animator blend, renderer 활성화, bobbing 위치 | Unity 어댑터 | 임시 로컬 표현 |

`BeachWater_01 water_depth Deep`은 물 지역의 설명입니다. 플레이어가 지금 깊이
잠겼다는 뜻이 아닙니다. 전자는 작성된 월드 데이터이고, 후자는 런타임 관측입니다.

### 4.2 트리플 편집

런타임 트리플 편집기의 구조는 다음과 같습니다.

```text
주어(선택한 오브젝트, 고정) --> 관계 --> 대상
```

- **주어**는 현재 선택한 월드 엔티티이며, 한 행에서 변경하지 않습니다.
- **관계**와 **대상**은 화면에서는 선택 언어로 보이지만, 저장은 canonical 영문 ID로
  합니다.
- `Plant`, `Rock`, `WaterRegion` 같은 개념은 데이터입니다. 나무처럼 생긴 메시를
  의도적으로 `Rock`으로 선언할 수 있습니다.
- UI는 잘못된 용어와 알려진 정의 충돌을 경고하지만, 메시 외형만 보고 창작을 막지는
  않습니다.

canonical ID, 번역 레이블, 별칭, 마이그레이션은
`Assets/Resources/Ontology/Localization`에서 관리합니다.

### 4.3 규칙과 규칙 블록

규칙은 온톨로지 조건이 성립할 때 어떤 결과가 참이 되는지 정의합니다. 규칙 블록은
그 규칙을 월드의 특정 엔티티/영역에 연결하여 켜는 저작 가능한 데이터입니다.

- 새 게임 관계를 메시 이름 기반 `if` 문으로 만들지 않습니다.
- 재사용 가능한 의미는 규칙 정의나 규칙 블록 템플릿으로 만듭니다.
- 특정 오브젝트의 선택은 트리플, 연결된 규칙 블록, 물리 프로필에 둡니다.
- Unity 어댑터는 `movement_mode Swimming` 같은 추론 결과를 애니메이션/이동 표현에
  연결할 수 있지만, 왜 수영이 가능한지는 판단하지 않습니다.
- 규칙 블록을 제거하면 그 월드 행동도 제거되어야 합니다. 하드코딩된 fallback이
  남아 계속 작동하면 안 됩니다.
- 재사용 가능한 새 게임 행동은 입력이나 전송 기능보다 먼저 규칙 DB에 정의하고,
  사용자가 연결할 수 있는 규칙 블록으로 발행합니다. 호환되는 다른 오브젝트도
  필요한 트리플과 같은 규칙 블록을 연결하면 오브젝트 전용 코드 없이 동일한 행동을
  사용할 수 있어야 합니다.
- 입력 어댑터와 Authority 전송 명령은 canonical Intent 또는 관측만 전달할 수
  있습니다. 규칙 블록이 소유해야 할 최종 게임 관계를 직접 작성하면 안 됩니다.
  액션에서 `has_rule_block`만 확인한 뒤 같은 결과를 직접 만드는 것은 이 계약을
  충족하지 않습니다.
- 사용자용 규칙 블록 화면에는 규칙만 연결하는 불완전한 저작 경로를 노출하지
  않습니다. 사용자는 Rule Block 프리셋 데이터베이스를 사용하는 하나의
  `빠른 설정`에서 완전한 트리플 + 규칙 블록 + 선택적 물리 의미 패키지를
  적용합니다. 규칙 블록 목록은 확인과 제거 용도로 유지하며, 원시 바인딩은
  일반 런타임 UI가 아니라 내부 제작·발행 단계에서만 사용합니다.

공식 게임플레이 생산라인은 다음과 같습니다.

```text
트리거
  -> canonical Intent 또는 관측
  -> 작성된 트리플 + 연결된 규칙 블록
  -> 규칙 평가
  -> 출처가 구분된 결과 Fact/상태/관계
  -> 영속 또는 공유 결과일 때 Authority 저장·투영
  -> Meaning/Profile
  -> Unity Adapter
  -> 플레이어 경험
```

Authority 저장은 조건부입니다. 임시 입력·관측·추론을 이 도식에 맞추기 위해
DB 이벤트로 만들면 안 됩니다. 물리 의미도 모든 기능에 필수인 단계가 아니라 결과
분기입니다. 대화·퀘스트·UI·오디오·애니메이션 결과는 물리 프로필 없이 대응하는
표현 의미와 어댑터를 사용할 수 있습니다. 단, 어댑터 실행 근거가 되는 평가 완료
결과와 그 출처 구분은 생략할 수 없습니다.

### 4.4 물리 행동, 환경, 장비

물리 프로필은 온톨로지로 선택하는 행동 프리셋입니다. 예를 들어 “물 위에 가볍게
떠요”라는 사용자 선택을 Unity 물리/표현 어댑터가 읽는 데이터 파라미터로 바꿉니다.
물·수영·튜브는 이 일반 구조의 첫 구현 사례일 뿐, 별도 예외 목록이 아닙니다.

- 환경에서의 배치와 반응은 파일명 대신 오브젝트 데이터/프로필로 판단합니다.
  물은 현재 구현된 첫 환경 사례입니다.
- 튜브, 보트, 탈것, 도구, 착용물 등 월드 장비는 수집 가능 여부, 착용 가능 여부,
  슬롯/부착 방식, 물리 행동, 임시 스킬 부여를 각각 독립적으로 가집니다.
- 장착한 월드 오브젝트는 규칙에 필요한 임시 능력을 부여할 수 있습니다. 튜브가
  수영 능력을 부여하는 것은 첫 사례입니다. 그렇다고 튜브 자체가 플레이어의 영구
  계정 프로필이 되는 것은 아닙니다.

## 5. 캐릭터와 계정의 생명주기

```text
인증된 사용자
  --> 계정 소유 캐릭터 프로필
  --> 선택한 캐릭터 + 선택한 월드
  --> 등록된 월드 아바타
  --> 월드 입장
  --> 로컬 외형 어댑터가 저장 외형 적용
```

현재 로컬 첫 수직 슬라이스는 씬에 배치된 가입 또는 로그인 화면에서 시작합니다.
Authority는 비밀번호를 해시하고 불투명 Bearer 세션을 발급하며, 서버에는 세션 토큰의
해시만 저장합니다. REST와 SignalR 모두 이 세션으로 사용자를 확인합니다. Unity는 로컬
세션을 기억해 계정 대시보드를 복구하지만, 현재 PlayerPrefs 저장은 데스크톱 개발 편의를
위한 것이므로 운영 전에는 플랫폼 보안 저장소로 교체해야 합니다.

Unity 가입·입장 흐름은 로그인, 가입, 캐릭터 생성·선택, 월드 생성·선택, 프로필 최종
확인, 월드 입장 로딩의 분리된 패널을 사용합니다. 예전 통합 계정 진입 패널은 대체
경로로 사용하지 않습니다. 캐릭터 생성에서 뒤로 갈 때 기존 캐릭터가 있는 계정은
캐릭터 선택으로 돌아가고, 캐릭터가 없는 계정은 로그아웃한 뒤 로그인으로 돌아갑니다.

계정 캐릭터 프로필에는 이름, 템플릿, 선택한 시각 파츠 ID와 스킬·소유 펫·소지 아이템의
canonical 관계가 들어갑니다. 월드 입장 시 Unity가 이 프로필의 시각 파츠 부분을 로컬
캐릭터 파츠 어댑터에 반영합니다. 계정 선택을 기억하려고
임의의 월드 Fact로 복사하면 안 됩니다. 다른 사용자에게 외형을 보여 주는 기능은 별도의
멀티플레이 표현 과제입니다.

캐릭터 파츠 교체는 canonical 슬롯과 `conflicts_with_slot` Fact로 결정합니다.
canonical `Body`와 `Face` 정의만 필수이며, 그 밖의 착용·표현 파츠는 선택된 섬네일을
다시 누르면 해제할 수 있습니다. 전신 의상처럼 여러 슬롯을 덮는 파츠를 교체하거나
해제해도 이전에 밀려난 파츠를 기억하거나 복원하지 않으므로, 전신 의상을 벗으면
덮여 있던 착용 슬롯은 빈 상태로 남습니다. 변형 렌더러는 원본 프리팹의
메시·머티리얼·로컬 bounds를 함께 복사하며, `useBaseRendererMesh` 정의는 캐시한
템플릿 렌더러 상태를 복원합니다.

연결된 코스튬 액세서리는 부모 정의가 명시적으로 다르게 선언하지 않는 한 독립적으로
교체할 수 있습니다. 일반 모자를 선택하면 공용 `Headwear` 슬롯의 코스튬 모자만
교체하고 전신 코스튬은 유지합니다. 이때 밀려났던 기본 상·하의를 복원하지 않습니다.

사용자에게 의미 있는 선택지를 제공하지 않는 필수 내부 정의는 꾸미기 화면에서 숨길 수
있습니다. 기본 신체는 필수 프로필·렌더러 연결로 유지하고, 선택 사항인 임시 상의
메시는 숨겨서 파츠 하나뿐인 카테고리를 만들지 않습니다.

게임 내부 캐릭터 꾸미기 패널은 가입 단계의 외형 선택 화면과 분리된 런타임 화면입니다.
파츠 변경은 미리보기와 게임 반영을 위해 로컬 어댑터에 즉시 투영할 수 있지만, 게임 내부
패널을 닫을 때 선택 파츠 ID를 World Authority를 통해 현재 선택된 계정 소유 캐릭터
프로필에 저장합니다. 가입용 외형 패널은 게임 내부 C키나 열기 버튼을 소유하지 않습니다.

운영 로그인에서는 현재 세션 기반을 이메일 인증, 복구, 요청 제한, 세션 관리와 필요 시
OIDC 같은 외부 신원 공급자로 강화하되 계정 --> 캐릭터 --> 월드 경계는 유지합니다.

## 6. 저작과 UI 원칙

- 런타임 월드 편집은 Unity Inspector 없이도 이해할 수 있어야 합니다.
- 선택 오브젝트 툴바는 이동/회전/복사 같은 변형과 Ontology 편집 열기만 담당합니다.
- `Tab`은 가까운 오브젝트를 선택하고 연속 입력으로 후보를 순환합니다. 플레이어 이동이나
  UI 클릭으로 입력이 새면 안 됩니다.
- 게임 UI는 프로젝트 소유 hierarchy/asset 중심으로 관리합니다. 스크립트로 만든 중복 UI와
  hierarchy UI를 동시에 운영하지 않습니다.
- `WorldEditHUD`와 선택 오브젝트 편집 핸들은 `Assets/Prefabs/Ontology/UI` 아래의 수정 가능한
  프리팹으로 관리합니다. 트리플, 규칙, 물리, 결과의 반복 행은 `WorldEditHUD` 안의 템플릿으로
  작성하며, 런타임 복제는 작성된 데이터 행 개수를 표현할 때만 허용합니다.
- 런타임 UI 바인더는 텍스트·선택지·상태·콜백만 연결합니다. 시각 컨트롤 생성, 레이아웃 값 결정,
  프리팹 hierarchy 중복 생성은 하면 안 됩니다.
- 사용자가 수정한 hierarchy/UI는 요청이 명시적으로 교체하지 않는 한 보존합니다.
- 서드파티 데모 에셋은 참고용이며, 프로젝트 변경은 작성 원본인
  `TormiaWorld.unity`, `TormiaUI.unity`, 프로젝트 prefab, 데이터 asset에 둡니다.
- 런타임 배치는 하나의 수정 가능한 **월드 배치** 패널 안에서 `오브젝트`, `NPC`, `몬스터`
  모드를 전환합니다. 모드는 프리팹·메시·오브젝트 이름으로 추론하지 않고 각 카탈로그 정의에
  명시적으로 작성합니다. 카테고리와 온톨로지 요약은 hierarchy가 소유하는 스크롤 UI이며,
  실제 배치는 공통 카탈로그와 배치 컨트롤러를 계속 사용합니다.

## 7. 언어팩 계약

- 사용자에게 보이는 문구는 CSV 언어팩으로 번역합니다.
- 온톨로지 canonical ID는 영문 그대로 저장합니다.
- Authority 의미 ID는 ASCII 영문 문법만 허용합니다. 한글 등 Unicode 표시는
  별칭·언어팩 경계에서만 입력받습니다.
- 사용자는 한글/영문 별칭으로 입력할 수 있지만 저장 시 canonical ID로 해석합니다.
- 관계 ID는 `snake_case`, 개념/상태/값 ID는 보통 `PascalCase`를 사용합니다.
- 자유 입력 인스턴스 이름은 자동 번역하거나 대소문자 변환하지 않습니다.
- 이미 저장된 ID의 이름 변경은 직접 교체하지 말고 `OntologyMigrations.csv`로 처리합니다.
- 사용자에게 보이는 작업 흐름·런타임 안내는 `언어팩 키 + 포맷 인자`로 전달합니다.
  Authority·전송·Adapter의 원시 상태 문구는 진단 데이터이며 UI 라벨에 직접 넣지
  않습니다.
- 재사용 가능한 작성 콘텐츠는 canonical ID와 언어팩 키를 함께 제공합니다. 배치
  카탈로그, 물리 프로필, 규칙, 캐릭터 템플릿, 기본 퀘스트는 영문·한글 프로젝트
  커버리지 검증을 통과해야 합니다. 사용자가 직접 작성한 이름과 퀘스트 문장은
  명시적인 언어팩 키를 지정하지 않는 한 원문을 유지합니다.
- 동적 온톨로지 요약은 표시 경계에서만 canonical 개념·관계·Rule Block 이름·프로필·
  캐릭터 파츠를 번역합니다. 저장 ID와 Authority 명령은 canonical 영문을 유지합니다.

## 8. 네트워크와 성능 원칙

- 영속 편집은 월드 리비전과 idempotent command ID를 가진 명령입니다.
- 임시 입력, 관측 상태, 모션 샘플, 접속 상태는 매 프레임 DB 이벤트를 만들면 안 됩니다.
- Zone projection은 클라이언트가 필요한 데이터만 불러오게 합니다. Zone 밖 참조는 해당
  Zone이 필요해질 때까지 ID로 남깁니다.
- 플레이어 이동 의도는 Authority가 평가하고 Zone 경계를 검증하지만, 지형·캡슐
  충돌은 Unity의 `LocalCharacterController` 물리 의미가 소유합니다. Unity는 충돌
  해결이 끝난 최신 위치를 원격 표현용 임시 런타임 상태로 전송합니다. 동등한 공유
  충돌 지오메트리가 생기기 전에는 서버가 충돌 없는 두 번째 플레이어 위치를 적분하거나
  로컬 캡슐을 그 위치로 끌어당기면 안 됩니다.
- 오브젝트별 새 행동은 polling 주기, allocation, 네트워크 fan-out, 규칙 반복 비용,
  DB 쓰기량을 함께 검토합니다.
- 선택한 월드의 권한 역할은 계정/월드 세션 계약의 일부입니다. Unity는
  `owner` 또는 `editor`에게만 편집 UI를 허용하고, 최종 권한 판정은 World
  Authority API가 담당하며 viewer 명령은 거부합니다.

## 9. 확정된 주요 결정

| 결정 | 이유 |
| --- | --- |
| 환경 Volume과 땅 충돌은 분리 | 물은 첫 사례로, 관측할 수 있지만 단단한 바닥인 척하지 않음 |
| 이동 모드는 관측된 배우 상태로 판정 | 수영은 첫 사례로, 깊은 물 지역이 모든 배우의 수영을 뜻하지 않음 |
| Animation Database와 Character Profile은 분리 | DB는 클립 후보, 프로필은 배우가 쓸 수 있는 항목을 선택 |
| Capability를 애니메이션 메타데이터 제한으로 쓰지 않음 | 캐릭터/월드 관계가 허용을 결정하고 애니메이션은 해결된 Intent를 클립에 연결 |
| Rule Block은 데이터로 연결하는 월드 행동 | 블록 제거 시 코드 수정 없이 효과도 사라져야 함 |
| 빈 액션·퀘스트·규칙 카탈로그는 빈 상태 유지 | 데이터를 제거했을 때 코드 기본 행동이나 임의 verb Fact가 되살아나면 안 됨 |
| Fact는 출처별 기여를 보존 | 영속·추론·관측·계정 프로필·Actor 프로필·외형 기여가 겹쳐도 서로의 Fact를 삭제하지 않음 |
| 로컬 스냅샷에는 영속 출처만 저장 | 관측·추론·계정 프로필 투영·캐릭터 외형은 각 소유자가 다시 구성 |
| Authority 액션은 projection 메타데이터 사용 | Unity 액션 UI가 패키지/버전을 고정하지 않고 서버가 내려준 활성 패키지·정의 버전을 사용 |
| Character Profile은 계정 데이터 | 하나의 프로필이 여러 월드에 들어가도 월드 온톨로지를 바꾸지 않음 |
| 계정 진입은 Authority 인증 필수 | 가입/로그인으로 불투명 Bearer 세션을 만들며 호출자가 보낸 사용자 ID 헤더와 자동 개발 계정은 신뢰하지 않음 |
| 런타임 표현은 월드 입장 확인 뒤에만 시작 | 월드 선택은 입장이 아니며 Authority 입장·복원 절차가 끝나기 전에는 플레이어, HUD, 입력, 스트리밍, 편집 기능을 숨김 |
| 이어하기는 Authority 체크포인트 사용 | 모션 샘플은 임시로 유지하고 위치·회전은 일정 주기와 일시정지/로그아웃 때 리비전·멱등 명령으로 저장 |
| 로컬 복구 데이터는 계정·월드별 격리 | 로컬 스냅샷과 전송 실패 명령이 다른 계정/월드로 섞이지 않으며 Bearer 토큰을 저장하지 않음 |
| UI는 asset/hierarchy 중심 | 코드로 만든 UI와 hierarchy UI의 충돌을 방지 |

## 10. 앞으로 변경 전 확인할 질문

1. 이 요청은 **계정 프로필**, **영속 월드 데이터**, **런타임 관측**, **추론**, **Unity 표현** 중 무엇입니까?
2. 오브젝트/메시 이름 조건 없이 데이터·규칙·프로필로 표현할 수 있습니까?
3. Unity 어댑터라면 어떤 Fact 또는 해결된 Intent가 실행 근거입니까?
4. canonical 용어, 번역, 별칭, 마이그레이션이 필요합니까?
5. 리비전이 필요한 영속 명령입니까, 임시 런타임 신호입니까?
6. 멀티플레이 권한과 Zone 범위를 지킵니까?
7. 기능을 켰을 때뿐 아니라 규칙/블록/프로필을 제거했을 때 사라지는 테스트가 있습니까?
8. 재사용 가능한 새 게임 로직이라면 등록·연결 가능한 규칙 블록이 먼저 있으며,
   입력은 최종 결과가 아니라 Intent만 발행합니까?

답이 불분명하면 먼저 필요한 온톨로지 데이터 형태나 규칙 템플릿을 만듭니다. 보이는
동작만 맞추기 위해 일회성 fallback 코드를 덧붙이지 않습니다.

2. 운영 전 요청 제한, 계정 복구, 이메일 검증, 세션 관리, 플랫폼 보안 토큰 저장을 추가합니다.
3. 콘텐츠 개발을 이어 갑니다: 월드 오브젝트 카탈로그, 재사용 가능한 규칙 블록 템플릿,
   퀘스트/NPC, 사용자 생성 흐름.
4. 운영 전에는 검증된 인증 공급자, 원격 아바타용 서버 프로필 표현, 배포/관측/보안 강화,
   부하 테스트를 진행합니다.

## 12. 개발 하네스

저장소에는 사람과 AI가 반복 가능하고 검토 가능한 방식으로 변경하기 위한 경량 하네스가
있습니다. 핵심 구성은 `AGENTS.md`, 회귀 시나리오 목록, 검증 스크립트, 한글/영문 변경
기록입니다.

- 시스템 변경 완료 전 `scripts/verify-development.ps1`을 실행합니다. 이 스크립트는
  한글/영문 컨텍스트, 시나리오 증거, World Authority 빌드를 확인합니다. 로컬 .NET SDK가
  없으면 Docker 빌드로 대체합니다.
- 관련 Unity 모드는 `scripts/run-unity-harness-tests.ps1`로 실행합니다.
- 로컬 서비스에서 `scripts/run-account-world-loop-smoke.ps1`을 실행하면 가입,
  프로필 멱등성, 입장 게이트, 체크포인트 자동 저장, 로그아웃, 재로그인,
  이어하기를 검증합니다. `verify-development.ps1 -RequireServices
  -RunAccountWorldLoopSmoke`로 선택 실행할 수 있습니다.
- 실패한 시나리오를 fallback 코드로 숨기지 않습니다. 데이터, 규칙, 어댑터, 테스트 격리 중
  책임이 있는 계층에서 원인을 고칩니다.
- 시스템 수준 변경은 `docs/changes`에 한글/영문으로 기록합니다.

## 13. Actor 재사용과 Avatar 프로필 계층

- `OntologyActorProfile`은 플레이어와 NPC가 함께 사용하는 Actor 정의입니다. 프리팹이나 메시 이름으로 게임 규칙을 분기하지 않습니다.
- 계정 프로필 관계는 휴대 가능한 캐릭터 데이터입니다. 월드 입장 시 로컬 Avatar의 런타임 온톨로지 뷰에만 투영하며, 해제 시 함께 제거합니다. 이 투영을 월드 Fact로 저장하면 안 됩니다.
- 직업, 팀, 클래스, 세계별 진행도는 World Authority가 소유하는 `world-avatar profile` 오버레이에 저장합니다. 이 데이터는 revisioned world command로 변경되고 계정 프로필로 역복사하지 않습니다.
- NPC도 플레이어와 같은 Actor별 액션 후보/실행 API를 사용합니다. 현재 Unity NPC 컨트롤러는 개발·로컬 시뮬레이션 어댑터이며, 공유 월드에서 서버 권한 NPC 실행을 켜려면 서버용 액션 카탈로그를 먼저 발행해야 합니다.
- 월드는 콘텐츠 패키지 버전을 명시적으로 활성화한 뒤에만 그 패키지의 발행 액션 정의를 사용할 수 있습니다. 첫 Authority 액션 계약은 의도적으로 좁게 유지합니다. 클라이언트는 actor/target/tool 엔터티 ID만 보내고, 서버가 불변 액션 정의를 해석해 단일 action Fact를 revisioned·idempotent 명령으로 기록합니다. 조건과 구조화된 효과는 headless evaluator가 소유할 때까지 비활성화합니다.
- 첫 개발 루프는 가능한 한 한 번의 클릭으로 진행합니다. 캐릭터가 없는 연결 계정은 휴대 가능한 기본 캐릭터를 만들 수 있고, 첫 입장에서는 안정적인 씬 Avatar를 먼저 배치·등록한 뒤 해당 캐릭터와 연결합니다. 이는 계정 프로필과 Authority 메타데이터이며 Unity만의 우회 처리나 작성된 게임플레이 Fact가 아닙니다.

## 14. 세션·자동 저장·이어하기 계약

```text
SignedOut -> Authenticated -> CharacterSelected -> WorldSelected
          -> EnteringWorld -> InWorld -> LeavingWorld / Recovering
```

- 계정 패널이 이 상태를 전환하며 Unity 런타임 오브젝트는 씬에 존재한다는
  이유만으로 로그인 상태를 추측하지 않습니다.
- `InWorld` 전에는 플레이어 렌더러, 월드 HUD/알림, 게임 입력,
  실시간/스트리밍 어댑터, 퀘스트 UI, 꾸미기 UI, 월드 편집기를 비활성화합니다.
  입장 실패 시 런타임을 노출하지 않고 선택 또는 복구 상태로 돌아갑니다.
- 월드 입장은 Authority projection을 불러오고, 전송 실패한 멱등 명령을
  재실행하고, Avatar 체크포인트를 복원한 뒤 계정 외형/프로필을 투영합니다.
  이 절차가 끝나야 런타임을 활성화합니다.
- Avatar 체크포인트는 의미 있는 이동 뒤 일정 주기 및 일시정지/로그아웃 때
  저장하는 낮은 빈도의 영속 상태입니다. 프레임별 입력과 모션은 임시 상태이며
  DB 이벤트로 만들지 않습니다.
- 외형 변경은 디바운스 후 계정 소유 캐릭터 프로필에 저장합니다. 퀘스트·행동·
  인벤토리·진행도는 승인된 계정 프로필 또는 리비전된 Authority 명령으로
  표현된 경우에만 영속적이며 UI 상태를 몰래 월드 Fact로 승격하지 않습니다.
- 로컬 시뮬레이션 스냅샷은 Authority가 세션을 소유하지 않을 때만 사용합니다.
  계정/월드별 경로에 원자적으로 기록하고 관측·추론·계정 투영·외형 투영은
  포함하지 않습니다.
- 보류 명령 outbox에는 전송에 실패한 영속 명령만 계정/월드별로 저장합니다.
  멱등 재실행을 위해 원래 command ID를 유지하고 인증 정보는 저장하지 않습니다.

## 15. 크리에이터 작업공간 도우미

- 제작 전문 NPC는 Unity의 `CreatorWorkspaceRoot` 표현 계층에 둡니다. 씬에
  존재한다는 이유만으로 작성된 월드 엔터티가 되거나 월드 Fact·관측·규칙
  블록·Authority 명령을 만들지 않습니다.
- 작업공간은 월드 소유자가 입장을 완료하고 크리에이터 모드를 켠 경우에만
  표시합니다. editor 또는 viewer 권한에는 소유자 전용 표현을 자동 상속하지
  않습니다.
- 임시 전문 NPC 외형은 계정 캐릭터 파츠 데이터베이스를 재사용하지만, 선택한
  파츠 ID는 직렬화된 표현 설정입니다. 외형 표현기는 `equipped_part` Fact를
  주입하지 않습니다.
- 설계·리소스·온톨로지·물리·규칙·퀘스트·UI·테스트/발행 역할은 영문 canonical
  service ID로 구분합니다. 한글 표시 이름은 UI 라벨이며 온톨로지 ID로 저장하지
  않습니다.
- 이후 대화형 생산 서비스를 붙일 때 각 표현 NPC를 교체해도 월드 데이터
  마이그레이션이 필요하지 않아야 합니다. 전문 NPC를 통해 만들어진 영속 결과는
  기존 계정 프로필 또는 리비전된 Authority 경계를 반드시 통과합니다.

## 16. Unity 씬 구성

- 플레이어 빌드는 `TormiaBootstrap`에서 시작합니다. 이 씬은 영속 Authority,
  세션, 저장/복원, 스트리밍, 온톨로지 런타임 서비스와 단 하나의
  `EventSystem`을 소유합니다.
- `TormiaWorld`는 Additive로 로드되며 카메라, 조명, 플레이어, 작성된 월드
  오브젝트, Zone, 물리 표현, 크리에이터 작업공간을 소유합니다.
- `TormiaUI`는 Additive로 로드되며 계정 흐름 Canvas, 게임 내부 UI, 프리뷰
  스튜디오, 후보정 가능한 패널 하이라키를 소유합니다. UI는 동작을 표시하거나
  요청할 수 있지만 월드 규칙이나 영속 Fact의 주인이 되지 않습니다.
- `OntologySceneCompositionLoader`는 두 Additive 씬 로드를 기다린 뒤 월드 씬을
  활성화하고, 씬 의존 연결과 로컬 작성 투영을 갱신합니다. 세션이 `InWorld`에
  도달하기 전에는 기존 런타임 게이트가 플레이어와 게임 UI를 계속 숨깁니다.
- `TormiaWorld`와 `TormiaUI`만 직접 편집하는 콘텐츠 원본 씬입니다. 디자이너는
  두 씬을 열어 수정하고 그대로 저장합니다. 예전 통합 `TormiaMain` 스냅샷은
  `Assets/Scenes/Legacy/TormiaMain.unity`에 보관하며 재생성 원본, 테스트 씬,
  빌드 씬으로 사용하지 않습니다.
- `TormiaUI`는 프로젝트 UI 루트 `OntologyGameCanvas` 하나와 디버그·프리뷰
  루트를 소유합니다. 서드파티 데모 시절의 빈 `FarmUI_DemoCanvas`와 기존
  메인 메뉴 동작은 씬 구성에 포함하지 않습니다.
- 프로젝트 설정 도구는 분리된 세 씬과 빌드 순서를 검증합니다. Legacy 통합
  스냅샷으로 분리 씬을 다시 생성하거나 덮어쓰면 안 됩니다.

## 17. 제품 브랜드와 안정적인 기술 식별자

- 사용자에게 표시하는 제품 브랜드는 `TOV`입니다. Unity `productName`은
  `TOV`, `companyName`은 `Smileon Labs`, 플랫폼 application identifier는
  `com.smileonlabs.tov`를 사용합니다.
- 저장소 폴더, `Tormia.*` 네임스페이스와 어셈블리, 씬/스크립트 경로, Docker
  프로젝트·볼륨·네트워크 이름, API 헤더, 저장소 prefix, DB 식별자, canonical
  온톨로지 ID는 변경하지 않습니다.
- 기존 World Authority 계정·캐릭터·월드·체크포인트는 Unity 제품 표시명과
  독립적인 영속 ID를 사용하므로 이름 변경이나 데이터 마이그레이션을 하지
  않습니다.
- Unity 회사명/제품명 변경으로 일부 플랫폼에서 새 PlayerPrefs 및
  `persistentDataPath` 범위가 만들어질 수 있습니다. 인증 정보는 복사하지
  않으므로 개발자는 한 번 다시 로그인해야 할 수 있습니다. 기존 로컬 파일은
  삭제하지 않으며 로그인 후 Authority 소유 영속 상태를 이어서 불러옵니다.

## 18. 안정적인 엔티티와 제작 요청 초안

- 모든 `OntologyObject`는 명시적인 안정 `entityId`를 가집니다. 사용자가
  수정할 수 있는 Unity GameObject 이름은 표시용 메타데이터이며, 온톨로지
  식별자나 규칙 블록 바인딩의 암묵적 대체값으로 사용하지 않습니다.
- 새로 배치한 월드 엔티티는 `OntologyAuthorityEntityIdentity`와 같은 GUID를
  온톨로지 ID로 사용합니다. 저장 형식 버전 8은 수정 가능한 인스턴스 이름과
  온톨로지 ID를 분리해 저장합니다. 명시 ID가 없는 예전 기록은 호환성을 위해
  기존 인스턴스 이름을 식별자로 유지합니다.
- 이동 접촉, 근접, 클릭 의도, 시뮬레이션 틱 Fact는 런타임 기여입니다. 각
  어댑터는 자신이 만든 기여만 회수하고, 같은 값의 작성/추론 기여를 지우지
  않으며, 프레임성 이동 이벤트를 영속 세션 기록에 추가하지 않습니다.
- 플레이어, 제작 보조 NPC, 원격 아바타 렌더러는 하나의 표시 전용 캐릭터
  외형 투영기를 재사용합니다. 장착/슬롯 정책은 계정 프로필 또는 담당
  어댑터가 계속 소유하며 투영기 안에 숨기지 않습니다.
- 제작 전문가 정의는 `CreatorServiceCatalog.asset`에 둡니다. canonical 영문
  서비스 ID, 단계 순서, 작업공간 위치, 표시 번역 키, 설명, 임시 외형 파츠
  ID는 에디터 스크립트의 조건문이 아니라 데이터입니다.
- Unity NPC 의사결정에는 명시적인 `OntologyNpcDecisionPolicy`가 필요합니다.
  컨트롤러는 내장 `help`/`talk` 우선순위를 갖지 않으며, 개발/오프라인 정책이
  명시적으로 허용하지 않으면 자동 실행이나 로컬 실행을 하지 않습니다. 공유
  월드 NPC 실행 권한은 계속 서버가 소유합니다.
- 첫 월드 설계자 수직 슬라이스는 자연어 입력을 **임시 Draft**로 캡처하고
  카탈로그의 제작 경로를 미리 보여 줍니다. 초안을 만드는 행위는 월드 Fact를
  기록하거나 Authority 명령을 보내지 않습니다. 영속 리소스·트리플·물리·
  규칙·퀘스트·UI·발행 결과는 이후 검토 단계에서 각 데이터 소유 경계를 통해
  만들어야 합니다.

## 19. 리팩터링 경계

- 런타임 UI 활성화는 명시적인 씬 참조와 컴포넌트 계약을 사용합니다.
  표시 GameObject 이름을 검색하지 않으므로 디자이너가 하이라키 이름과
  위치를 바꿔도 로그인·월드 입장 게이트가 달라지지 않습니다.
- 계정 선택 프리뷰, 로컬 플레이어, 제작 보조 NPC, 원격 아바타는 모두
  `OntologyCharacterAppearanceProjector`를 사용합니다. 프리뷰 코드는
  카메라와 구도를 소유할 수 있지만 장착·연결 파츠·메시·머티리얼 투영
  로직을 복제하지 않습니다.
- `OntologyPlacedObjectFactProjection`만 배치 기록을 월드 Fact로
  투영합니다. 안정 `entityId`를 선택하고 예전 인스턴스 이름 Subject를
  마이그레이션하며 수정 가능한 표시 이름을 영속 의미에서 제외합니다.
- 제작 경로는 `OntologyCreatorRoutePlanner`가 계산합니다. 도메인 오류는
  타입 값으로 반환하며 오류 문구와 서비스 설명은 워크플로 모델이 아니라
  언어팩에서 번역합니다.
- 로컬 Authority 세션과 선택 기억은 `OntologyAuthoritySessionStore`
  뒤로 격리하며 스냅샷과 명령 outbox에 넣지 않습니다. 지연 저장되는 외형은
  캐릭터와 파츠 ID를 함께 캡처해 이후 캐릭터 선택이 보류 중인 저장 대상을
  바꾸지 못하게 합니다.
- 아바타 체크포인트는 `stale_revision`일 때만 투영을 다시 읽고
  재시도합니다. 권한·검증·전송 실패에는 숨은 두 번째 명령을 실행하지
  않습니다. 로컬 스냅샷과 Authority outbox는 하나의 원자적 파일 교체
  구현을 공유하지만 각자의 소유권과 백업 정책은 분리해서 유지합니다.

## 20. 첫 번째 Authority 전투 생산 라인

- 전투는 Unity 충돌 코드가 아니라 World Authority가 소유하는 상태 전이입니다.
  행동 애니메이션은 Authority가 명령을 승인한 뒤에만 시작합니다.
  피격·체력·사망·드롭 표현은 추가로 최신 투영까지 확인한 뒤 적용합니다.
- 발행된 액션 정의는 순서가 있는 영속 효과 `SetFact`, `RemoveFact`,
  경계형 `AdjustNumberFact`를 사용할 수 있습니다. 뒤의 효과는
  `current_health <= 0` 같은 범용 수치 사후 조건을 사용할 수 있습니다.
  평가기에는 몬스터명·프리팹명·체력 전용 조건문이 없습니다.
- 기본 `attack` 정의는 명시적으로 장착된 도구가 `Sword` 개념과
  `grants_capability MeleeAttack` 관계를 가질 때만 실행됩니다. 범용
  `valueFrom` 효과 소스로 무기의 수치형 `attack_damage` Fact만큼 체력을
  감소시키되 0보다 작아지지 않게 합니다. 대상은
  `combat_disposition=Hostile`이어야 하며 `Damageable`만으로 공격 권한이
  생기지 않습니다. 체력이 0이 되면 `is_alive=False`와
  `loot_status=Available`을 설정합니다. `loot_table`과 `loot_item`은 몬스터
  템플릿이 소유하며 공격 정의가 드롭을 선택하지 않습니다.
- 기본 `equip_weapon` 정의는 무기의 작성 슬롯과 룰블록을 확인한 뒤 아이템
  소유형 `weapon equipped_by avatar` 관계를 만듭니다. 다른 Actor가 이미
  점유했거나 같은 슬롯의 다른 아이템이 있으면 거부하며, 범용
  `maxActorTargetDistance` 런타임 제약을
  Authority의 ephemeral 아바타 이동 상태와 대상의 영속 Transform으로
  평가합니다. Unity의 로컬 거리 검사는 선택 보조일 뿐 최종 권한 검사가
  아닙니다. `unequip_equipment`은 리비전 Authority 명령으로 선택 관계를
  제거하고, 같은 대상의 구형 `equipped_item` 행이 있으면 함께 철회합니다.
  클라이언트는 실행 요청에 predicate, 거리, 영속 관계를 넣을 수 없습니다.
- 장착 프로필은 canonical 관계 predicate와 그 방향이 `ItemToActor`인지
  `ActorToItem`인지 명시합니다. 범용 장착 어댑터만 월드 오브젝트를 캐릭터
  앵커에 붙이고 프로필 오프셋과 임시 물리 비활성화를 적용합니다. 전투
  표현 코드에는 별도의 직접 부착 fallback을 두지 않습니다. `Weapon` 개념의
  배치 항목은 프로젝트 소유 프리팹에 작성된 `OntologyAttachmentGripPoint`가
  반드시 있어야 하며, 없으면 의미 검증에 실패합니다.
- 영속 월드 Transform과 장착 Transform의 표현 소유권은 동시에 활성화되지
  않습니다. Authority 투영은 먼저 의미 Fact를 반영하고 장착 소유권을
  결정한 다음, 월드 소유 상태로 남은 오브젝트에만 영속 Transform을
  적용합니다. 장착 관계가 제거되면 Transform 소유권과 저장해 둔
  Rigidbody/Collider 상태가 월드로 돌아갑니다.
- `Sword01Bronze`, `Sword08Corrupted`, `Sword15FrostVisual`,
  `BeholderBasic`은 외부 에셋을 감싼 프로젝트 소유 래퍼 프리팹입니다.
  무기 원본 프리팹·canonical 계열·능력·액션 ID·애니메이션 의도·VFX 의도는
  카탈로그 생성기의 고정 배열이 아니라 편집 가능한
  `WeaponContentManifest` 항목으로 관리합니다. 개념·장착 프로필·초기 체력도
  프로젝트 데이터 에셋에 있습니다. 무기 템플릿은 `damage_profile`과
  `attack_damage`를, 몬스터 템플릿은 생명력·진영·적대성·드롭 관계를
  소유합니다. Unity 표현 카탈로그는 최대 체력과 드롭 ID를 중복 소유하지
  않습니다. 소스 이름의 `Frost`는 냉기 규칙을 자동 부여하지 않습니다.
- Authority 월드 배치는 엔티티 Transform과 타입이 보존된 초기 템플릿
  Fact를 하나의 리비전 `place_entity` 명령으로 전송합니다. 숫자와
  불리언은 canonical 문자열이 아니라 각 타입으로 저장됩니다. Unity는 승인된
  투영을 받은 뒤에만 표현 오브젝트를 만듭니다. Authority 클라이언트가
  설정된 씬은 로그인 전에도 Authority가 영속 저장을 소유하므로, 로컬
  스냅샷이 로컬 전용 몬스터나 무기를 Authority 월드에 몰래 복원하지
  못합니다.
- `Basic Slash Blue`와 `Flash_round_ellow`는 풀링된 표현 효과입니다.
  Mixamo 검 애니메이션과 Beholder 애니메이션은 FBX명이나 Animator 상태명을
  게임 규칙에서 검색하지 않고 canonical 애니메이션 의도로 선택합니다.
- 발행된 행동 정의는 canonical
  `presentation.actorAnimationIntent`를 선언할 수 있습니다. 월드 투영은
  정확한 패키지·행동·정의 버전의 의도를 전달합니다. 명령 승인 뒤
  `OntologyAnimationAdapter`가 배우의 `has_animation` 레퍼토리와
  `AnimationDatabase`를 통해 해당 의도를 해석합니다. 입력·전투 컨트롤러는
  클립을 고르거나 공격 의도 fallback을 갖지 않습니다. 표현 메타데이터나
  레퍼토리 등록을 제거하면 게임플레이 코드를 바꾸지 않아도 애니메이션이
  사라집니다.
- 실행 가능한 Authority 스모크가 장착, 경계형 피해, 조건부 사망,
  온톨로지 데이터 드롭, 명령 재전송, 패키지 제거, 재로그인 복원을 검증합니다.
  전투 패키지를 끄거나 제거하면 해당 Authority 행동도 사라지며 Unity의 숨은
  대체 피해 로직은 없습니다.
- 장착 입력은 영속 Fact가 아닌 Unity의 일시적 상호작용 요청입니다.
  Authority 우선 배치가 씬에 투영되는 동안 최근 입력은 잠시 대기할 수 있지만,
  실제 장착은 canonical `Weapon` 대상과 Authority 행동 승인을 계속 요구합니다.
  승인된 애니메이션 표현도 버전이 일치하는 행동 투영, 배우 레퍼토리, 활성
  Animator가 준비될 때까지 잠시 대기할 수 있습니다. 만료된 입력과 멱등
  재전송 결과는 나중에 장착이나 애니메이션을 발생시키지 않습니다.

## 21. 프리팹 소유 장착 손잡이 기준점

- 장착 여부는 계속 Authority의 canonical 장착 관계가 결정합니다.
- 캐릭터 쪽 위치와 방향은 안정적인 `actorSocketId`로 선택되는
  `OntologyAttachmentSocket`이 소유하고, 무기 모양마다 다른 손잡이 위치와
  방향은 각 프로젝트 소유 프리팹의
  `OntologyAttachmentGripPoint`가 소유합니다.
- 배우 소켓은 명시적으로 설정된 리그 뼈 또는 소품 앵커를 따라갑니다.
  서드파티 FBX 프리팹 내부에 지원되지 않는 자식 오버라이드를 만들지 않고,
  프로젝트 소유 Actor 하이라키의 `AttachmentSockets` 아래에 둡니다.
- 공용 프로필에 특정 검 메시를 위한 위치·회전 보정값을 넣지 않습니다.
  장착 어댑터는 무기 손잡이 기준점과 배우 소켓을 정렬하므로 프리팹에서
  손잡이 기준점을 수정하면 장착 표현이 다시 정렬됩니다.
- 손잡이 기준점 계약이 없는 기존 착용물과 탈것은 호환성을 위해 공용 프로필
  자세를 사용합니다. 전투 코드에는 무기명·프리팹명별 직접 부착 예외가 없습니다.

## 22. Authority 확정 장착 애니메이션 상태

- 지속 장착 자세는 Authority가 소유하는 `equipped_item` 관계로부터 파생되는
  Unity 표현 상태입니다. 프레임마다 또는 중복 영속 `animation_intent` Fact로
  저장하지 않습니다.
- 장착된 엔티티 ID는 투영의 canonical `templateId`로 해석합니다.
  `CombatCatalog`에는 해당 템플릿과 정확히 일치하는 무기 표현 정의,
  `idleAnimationIntent`, `moveAnimationIntent`가 명시되어야 합니다. 런타임
  코드는 무기명·프리팹명·메시명·GameObject 이름으로 자세를 추측하지 않습니다.
- 정지 중에는 장착 Idle 의도가 Animator Controller의 기본 Idle을 대체하고,
  이동 중에는 장착 이동 의도가 카탈로그의 `WeaponWalk` 표현을 선택합니다.
  승인된 일시 행동은 현재 자세를 잠시 덮고, 완료 후 현재 이동 상태에 맞는
  장착 자세로 돌아갑니다.
- `equipped_item` 관계, 일치하는 카탈로그 정의 또는 장착 의도를 제거하면 해당
  표현도 제거되고 Controller의 Idle/Locomotion으로 복귀합니다. 스키마
  기본값은 `WeaponIdle`이나 `WeaponWalk`을 몰래 생성하지 않습니다.
- 배우 소켓은 매 프레임 애니메이션 리그 앵커를 계속 추적합니다. 따라서 장착
  자세 보정은 비무장 기본 Idle을 억지로 보완하지 않고, 해석된 장착
  애니메이션을 기준으로 작업합니다.

## 23. 매니페스트 기반 애니메이션 생산라인

- `AnimationContentManifest`는 애니메이션 ID, canonical 의도, 호환 배우·리그
  유형, 배우 레퍼토리, 재생 레이어, 아바타 마스크, 반복, 루트 모션 정책,
  전환 정책, 출처, 배포 키, 버전, 체크섬을 소유하는 프로젝트 저작 원본입니다.
  `AnimationDatabase`와 각 배우 프로필의 `has_animation` 레퍼토리는 여기서
  생성되는 투영입니다.
- 최초 마이그레이션만 기존 데이터베이스에서 매니페스트를 만들 수 있습니다.
  이후 동기화 방향은 매니페스트에서 런타임 데이터로만 흐릅니다. 항목을
  제거해도 오래된 런타임 데이터베이스가 다시 살리지 않으며, 알려진 배우
  프로필에서도 제거된 항목을 함께 지웁니다.
- 지상 이동, 공중·낙하 관찰, 착지, 장착 이동은
  `OntologyAnimationStateResolver`가 Unity의 일시 관찰값으로 해석합니다.
  프레임별 애니메이션 상태는 영속 월드 Fact로 저장하지 않습니다. 승인된
  Authority 행동은 공격·피격 같은 일시 의도의 더 높은 우선순위 원천입니다.
- FBX·클립·메시·프리팹·Animator 상태·GameObject 이름으로 애니메이션 능력을
  추측하지 않습니다. 호환되는 매니페스트 항목이 배우의 명시적 레퍼토리에
  있을 때만 해당 의도를 표현합니다. 게임플레이 capability는 애니메이션
  메타데이터와 분리합니다.
- 개발 행동 패키지는 발행 전에 애니메이션 매니페스트와 대조합니다. 월드
  입장은 다시 읽은 Authority 투영이 정확한 패키지 ID·패키지 버전·행동 정의
  버전·애니메이션 의도를 확인해야 하며, 경고만 남기고 우회하지 않습니다.
- 자동 임포트 설정은 프로젝트 소유 `Assets/Animations/`와 승인된 UGC
  애니메이션에만 적용합니다. 서드파티 패키지는 읽기 전용 원본입니다. 사용자가
  제출한 FBX는 출처·라이선스 메타데이터와 함께 격리되고, 구조 검증과 명시적
  승인을 통과한 뒤 승인 매니페스트로 이동합니다. 임의 런타임 FBX 로딩은
  Unity 클라이언트 범위가 아니며 별도의 신뢰 가능한 빌드·배포 서비스가
  필요합니다.

## 24. 패키지 범위 불변 행동 정의

- Authority 행동 정의는
  `packageId + packageVersion + actionId + definitionVersion` 전체 조합으로
  식별합니다. 다른 불변 패키지 버전에서 같은 행동 ID와 정의 버전을
  재사용하는 것은 유효하며 DB에서 충돌하면 안 됩니다.
- 행동이 아닌 정의는 월드 바인딩에도 패키지 식별자가 포함될 때까지 기존 전역
  식별 방식을 유지합니다. 따라서 패키지 범위 DB 제약은 `action_effect`에만
  적용합니다.
- 전투 Authority 스모크는 기본적으로 매번 새 Docker 프로젝트·네트워크·
  PostgreSQL 볼륨·Redis 볼륨에서 실행합니다. 모든 마이그레이션, 패키지 간
  정의 재사용, 전투 루프를 검증한 뒤 컨테이너와 볼륨을 삭제합니다.
  `-UseExistingServices`는 명시적 진단 옵션이며 일반 회귀 검증에서는 사용하지
  않습니다.
- 기술적인 Authority 거절 코드는 Unity Console에 기록합니다. 계정 UI는
  언어팩 키로 사용자용 안내를 표시하며 원시 전송·카탈로그 메시지를 노출하지
  않습니다.

## 25. Authority 런타임 기반 준비

- 새로 만든 편집 가능 월드는 리비전 `define_zone` 명령으로 최소 하나의 활성
  런타임 Zone을 받습니다. 시작 Zone 키·범위·시뮬레이션 모드, 아바타 이동
  속도, 준비 대기 시간은 `WorldAuthoritySettings`의 프로젝트 데이터이며
  숨겨진 게임플레이 상수가 아닙니다.
- 월드 입장은 Zone이 없는 기존 편집 가능 월드를 보정합니다. 휴면이 아닌
  작성 Zone을 선택하고 `save_avatar_checkpoint`로 등록 아바타를 연결하며,
  `movement_speed` Fact가 없을 때만 작성합니다. 기존 작성 값은 유지합니다.
- 런타임 보정은 기존 체크포인트 Transform을 덮어쓰지 않습니다. 유효한 저장
  Zone은 유지하고, Zone이 없거나 폐기된 경우 저장 위치를 기준으로 새 Zone을
  결정해 필요한 Zone 연결만 변경합니다.
- 선택 Zone에서 등록 아바타의 일시적 모션 상태가 Authority로부터 조회된
  뒤에만 입장을 완료합니다. Unity의 로컬 Transform을 서버 위치 대신
  사용하지 않습니다.
- 단방향 리비전 `migrate_legacy_equipment_relations` 명령은 행동이 만든 구형
  `equips` Fact만 철회하며 대체 관계를 추측해 만들지 않습니다. 정식 다중
  슬롯 장착 관계는 아이템 소유형 `item equipped_by actor`입니다.
  `actor equipped_item item`은 구형 호환 데이터이며 해당 아이템을 해제할 때
  함께 철회합니다.
- 거리 제한 장착 명령은 Authority 런타임 위치가 조회되기 전에는 전송하지
  않습니다. 기반을 제거하면 클라이언트 fallback 대신 해당 행동도 제거됩니다.

## 26. 플레이어 이동 세션 수렴

- `movement_speed`는 World Authority가 허용하는 작성된 최대 이동 속도입니다.
  일시적 입력 샘플은 플레이어가 요청한 걷기·달리기 속도를 함께 보내고, 서버는
  이를 작성된 최대값으로 제한합니다. 요청 속도는 Fact가 아니며 월드 리비전을
  증가시키지 않습니다.
- 월드 입장 시 선택한 아바타의 런타임 이동을 명시적으로 활성화합니다. 활성화는
  이전 세션의 만료형 입력 시퀀스를 지우고 현재 내구 체크포인트/엔티티 Transform을
  기준으로 Redis 이동 상태를 시작합니다.
- `save_avatar_checkpoint` 명령이 승인되면 커밋된 내구 Transform을 기준으로
  대응하는 일시적 이동 상태를 다시 맞춥니다. PostgreSQL이 내구 소유자이며 Redis가
  서로 다른 과거 위치를 계속 유지할 수 없습니다.
- 이동 스케줄러는 소유자가 활성 Zone 세션을 가진 아바타만 진행합니다. 오프라인
  등록 아바타는 더 이상 이동 TTL을 무기한 갱신하지 않습니다.
- Unity는 반응성 있는 로컬 이동을 유지하며, 입력 중에는 낮은 빈도의 과거
  Authority 위치가 로컬 이동을 끌어당기지 않습니다. 로컬 입력이 멈춘 뒤
  Authority가 `idle` 상태를 확인하고 제한된 안정 대기 시간이 지나면 남은 수평
  오차만 부드럽게 보정합니다. 위치 불일치를 숨기려고 장착·공격 거리를 늘리지
  않습니다.
- 입력 어댑터가 `CharacterController.Move`의 단일 소유자로 유지됩니다.
  Authority 수렴값은 같은 이동 호출에 제한된 수평 델타로 합쳐지며, 접지·충돌
  판정을 번갈아 바꿀 수 있는 두 번째 컨트롤러 이동을 수행하지 않습니다.

## 27. Authority 전투 타깃과 결정적 표현

- 전투 입력은 프로젝트에 작성된 Input System의 `Player/Attack` 행동을
  사용합니다. 카메라 시점 고정 입력은 별도 바인딩으로 유지합니다. 무기를 든
  상태에서 투영된 전투 엔티티를 누르면 클릭 이동보다 먼저 전투 입력이 소비되어
  서로 충돌하는 이동 요청을 만들지 않습니다.
- Unity Raycast는 현재 Authority 투영에 존재하는
  `OntologyAuthorityEntityIdentity` 후보만 찾습니다. 적대성·피해 가능 여부·권한·
  공격 거리·피해량·사망·드롭은 Unity가 결정하지 않습니다.
- 공격 명령은 배우·대상·도구와 정확한 불변 행동 패키지 조합을 전송합니다.
  World Authority가 장착 관계, canonical 대상 조건, 무기의 수치 피해 Fact,
  런타임 위치, 작성된 최대 거리를 확인한 뒤 변경을 커밋합니다.
- 승인되고 투영된 패키지·행동·정의 버전이 모두 일치할 때만
  `presentation.actorAnimationIntent`를 해석할 수 있습니다. 레퍼토리 누락,
  Animator 준비 실패, 거절된 행동, 메타데이터 해석 실패는 진단 단계를 남기며
  fallback 클립을 선택하지 않습니다.
- 무기 장착 프로필은 프리팹 소유의 보정 완료
  `OntologyAttachmentGripPoint`를 필수로 지정할 수 있습니다. 이 프로필에서
  마커를 제거하면 장착 표현도 제거되며 배우 루트·추정 Humanoid 본·공통 무기
  오프셋으로 대체하지 않습니다. 기존 비무기 프로필은 명시적인 공통 프로필
  자세를 계속 사용할 수 있습니다.
- 복원된 아바타 Transform은 월드 입력 게이트가 열리기 전에 하나의 표현 준비
  트랜잭션에 들어갑니다. 아바타 루트는 활성 상태로 유지하되 렌더러와 입력을
  차단하고, FixedUpdate 충돌 접지·이전 입력 초기화·애니메이션 준비를 모두
  완료한 뒤에만 `InWorld`로 전환합니다. 수영·탑승 표현은 강제로 접지하지
  않습니다. 접지 후 위치가 바뀌면 아바타 체크포인트로 revision 확인하지만,
  로컬 접지 Adapter는 게임플레이 Fact나 권한을 만들지 않습니다.

## 28. 온톨로지 행동 계약과 튜브 기준 슬라이스

- 게임플레이 수직 슬라이스는 작성된 트리플이 의미·물리 프로필을 식별하고,
  배정된 룰블록이 행동을 활성화하며, 공통 물리/표현 어댑터가 평가 결과를
  표현할 때만 완성됩니다. 활성 룰블록을 제거하면 행동도 철회되어야 하며
  Unity 입력·프리팹명·오브젝트명 fallback이 이를 다시 만들면 안 됩니다.
- 등록된 월드 아바타는 내구 canonical `has_concept -> Actor` 월드 Fact를
  가집니다. 신규 아바타 배치 시 엔티티와 함께 작성하고, 기존 편집 가능 월드는
  룰블록 평가 전에 월드 입장 기반 복구가 이를 추가합니다. 계정 프로필 데이터는
  계속 월드 Fact 밖에 둡니다.
- 개발 콘텐츠 흐름은 카탈로그 기본값에 필요한 불변 Rule 정의를 먼저 발행한
  다음 오브젝트 룰블록 바인딩을 발행합니다. 바인딩 ID는 엔티티·Rule·바인딩
  변수로 결정되므로 재전송이 중복 행동 계약을 만들지 않습니다.
- 이전 버전에서 만든 엔티티는 카탈로그 기본값으로 한 번만 복구합니다. 모든
  기본 바인딩이 성공한 뒤에만 내구 `semantic_contract_version` 마커를 씁니다.
  마커가 생긴 뒤 사용자가 룰블록을 제거하면 그 결정이 우선하며 다음 월드
  입장에서 다시 추가하지 않습니다.
- 로컬 근접 표현은 `Actor`가 하나라고 가정하지 않고 계정 아바타 또는 작성된
  플레이어 입력 역할을 찾습니다. 따라서 NPC·몬스터 Actor가 늘어나도 착용형
  오브젝트의 근접 판정이 비활성화되지 않습니다.
- 튜브가 기준 슬라이스입니다. 착용/기술 및 프로필 트리플,
  `AutoEquipNearbyWearable` 관련 룰블록, `LightBuoyant`와 허리 장착 프로필이
  가까운 배우가 명시적으로 `F`를 누른 뒤 장착과 임시 Swimming 기술을
  만듭니다. 장착 룰블록이 없는 깨끗한
  평가에서는 슬롯 관계·장착·임시 기술을 만들 수 없습니다.

## 29. 룰블록으로 제한되는 장착

- 모든 카탈로그 무기는 `Weapon`/`Carryable`과 장착 관련 트리플,
  `EquipItemOnInteractionIntent` 룰블록, `RightHandCarry` 부착 프로필,
  `HandheldWeapon` 물리 프로필을 함께 가져야 합니다.
- 불변 `equip_weapon` 행동은 canonical 임시 `interaction_intent`만
  운반하며 `equipped_by`를 직접 만들지 않습니다. World Authority가 정확히
  연결된 `EquipItemOnInteractionIntent`와 게시된 규칙 정의를 명령 스냅샷에서
  평가합니다. 따라서 바인딩을 제거하면 행동도 사라지며 Unity나 전송 액션에는
  별도의 장착 결과 fallback이 없습니다.
- 명령 범위 규칙이 만든 영속 결과에는 `source_rule_binding_id`가 기록됩니다.
  해당 룰블록이나 의미 패키지를 제거하면 그 바인딩이 소유한 결과도 함께
  회수되어 숨은 액션 결과가 남지 않습니다.
- 카탈로그 무기의 의미 계약 버전은 2입니다. 기존 배치 무기는 카탈로그에 작성된
  마이그레이션을 통해서만 `AutoCarryNearbyCarryable/?object`에서
  `EquipItemOnInteractionIntent/?target`으로 전환되며, 사용자가 의도적으로
  제거한 룰블록은 다시 생성하지 않습니다.
- 개발 패키지는 현재 튜브·장착 룰블록들을 불변 카탈로그 버전 2로
  게시합니다. 개발 패키지 게시와 새 월드 바인딩은 같은 버전을
  참조합니다. 변경된 룰블록 내용은 버전 1을 덮어쓰지 않고 카탈로그
  버전을 올려야 합니다.
- `HandheldWeapon`은 동적 월드 아이템을 위한 프로젝트 소유 물리
  설정입니다. 장착 어댑터는 장착 중에만 Rigidbody와 Collider 표현
  책임을 넘겨받으며, 물리 프로필 트리플이나 무기 의미를 프리팹
  이름으로 대체하지 않습니다.
- 기존 편집 가능 월드는 리비전·멱등 명령으로 누락된 카탈로그
  트리플과 기본 룰블록을 한 번 복구한 뒤
  `semantic_contract_version`을 기록합니다. 이 표식 이후 사용자가
  제거한 룰블록은 다음 입장 때 다시 생성하지 않습니다.
- 개발 패키지 `1.9.0`은 필요한 룰 정의를 바인딩보다 먼저 발행하고,
  `equip_weapon` 정의 버전 `7`, `equip_wearable` 버전 `1`,
  `unequip_equipment` 버전 `1`을 발행합니다. 이전 패키지나 행동
  버전은 새 장착 계약을 우회할 수 없습니다.

## 30. 런타임 Transform 단일 소유권

- Unity Transform은 한 시점에 하나의 표현 계층만 소유합니다. 우선순위는
  월드 편집, 장착, 로컬 CharacterController 또는 Actor 런타임, Dynamic 물리,
  Authority 영속 투영 순서입니다.
- 이 소유권은 명시적인 온톨로지 프로필과 활성 관계에서 계산하는 임시 표현
  상태입니다. 영속 Fact가 아니며 프리팹·메시·정의·GameObject 이름으로
  추론하지 않습니다.
- `Anchored`와 `AuthorityKinematic` 물리 프로필은 kinematic 상태로 해당
  Authority/런타임 소유자를 따릅니다. `Dynamic` 프로필은 영속 투영으로 한 번
  초기화된 뒤 Unity 물리가 실시간 위치를 소유하며, 이후 투영 갱신이 이전
  위치로 Rigidbody를 되돌리지 않습니다.
- Dynamic 물리 위치를 프레임마다 저장하지 않습니다. 의미 있는 이동 후 일정
  시간 안정된 경우에만 편집 권한이 있는 클라이언트가 revisioned·idempotent
  `move_entity` 체크포인트를 한 번 전송할 수 있습니다.
- 배치 카탈로그는 물리 프로필을 명시적으로 선택해야 합니다. 프로필이 없으면
  Rigidbody 동작도 만들지 않으며, 이전 `HeavySinking` 기본값은 런타임 정책으로
  사용하지 않습니다. 식생과 랜드마크는 `StaticAnchored`, Beholder는
  `AuthorityKinematic`, 돌은 `HeavySinking`, 무기는 `HandheldWeapon`, 튜브는
  `LightBuoyant`를 명시적으로 사용합니다.
- 배치는 최종 프리팹·온톨로지 템플릿·물리 프로필·생성 Collider를 먼저 확정한
  뒤 지면 지지 높이를 계산하고, 최종 충돌 형상을 정렬한 뒤 Rigidbody 속도를
  초기화합니다.
- 아바타 체크포인트는 계속 Authority가 소유하는 영속 데이터입니다. Unity는
  `CharacterController.Move`를 이용한 캡슐 안전 지면 탐색을 한 번 수행하고
  임시 수직 속도만 초기화합니다. 컨트롤러를 껐다 켜거나 체크포인트를 다시
  기록하지 않습니다.
- 월드 입장 세션 중 로컬 아바타의 화면상 런타임 위치는 의미 동기화가 이동
  lease를 잠시 비활성화하거나 제거해도 로컬 소유권을 유지합니다. lease가 없으면
  이동만 멈추며, 오래된 Authority 영속 투영이 아바타를 이전 위치로 되돌릴
  권한을 얻지 않습니다. 영속 위치 복원은 명시적인 입장·복구·리스폰 수명주기
  어댑터만 수행합니다.
- 지면 probe의 근접 감지는 충돌 관찰일 뿐 단차 상승 권한이 아닙니다. 명시적인
  단차 상승은 `CharacterController`의 실제 접지 상태에서만 가능하며,
  `slopeLimit` 안의 표면은 연속된 `WalkableSupport`로 처리합니다. 수평 이동은
  지지면 접선을 따르지만 중력과 접지 유지는 세계 수직 방향을 유지합니다.
  지지면 법선 방향 접지는 평면 성분이 역방향 경사 미끄러짐을 만들기 때문에
  사용하지 않습니다.

## 31. Unity 공식 MCP 개발 전송

- 로컬 Codex/Unity 개발은 Unity `com.unity.ai.assistant` 패키지에 포함된 MCP
  서버를 사용합니다. Codex는
  `%USERPROFILE%\.unity\relay\relay_win.exe --mcp`를 실행하고
  `--project-path <TOV 프로젝트 절대 경로>`로 대상을 고정하여 열려 있는 다른
  Unity 에디터를 잘못 선택하지 않게 합니다.
- 공식 Relay는 플랫폼 IPC(Windows에서는 named pipe)를 통해 Unity 에디터
  Bridge와 통신합니다. Bridge는 에디터와 함께 시작되고 승인된 클라이언트를
  기억하며 일반적인 클라이언트 세션 사이의 재연결을 담당합니다. 별도로
  유지하던 MCP for Unity HTTP 서버를 기본 전송 방식에서 대체합니다.
- 전환 기간에는 `http://127.0.0.1:8080/mcp`를 임시 fallback으로만 유지할 수
  있습니다. 공식 Relay가 재시작, 어셈블리 리로드, 콘솔, 씬, GameObject, 저장,
  컴파일, 테스트 검증을 통과하면 fallback과 `com.coplaydev.unity-mcp`를
  제거합니다. 두 MCP 구현을 영구 구조로 유지하지 않습니다.
- `scripts/verify-unity-mcp.ps1`은 실행할 때마다 새 승인 요청을 만들지 않고 공식
  Relay, Assistant 패키지, 프로젝트 경로가 고정된 Codex 설정, 실행 중인 에디터,
  연결 레코드와 named pipe를 검증합니다. Unity 승인은 클라이언트 단위이므로
  `-LiveToolProbe`는 승인된 대화형 클라이언트 세션에서만 사용합니다. 선택적으로
  기존 fallback 상태도 보고할 수 있습니다. 예상 Unity 에디터가 열린 상태에서
  `scripts/verify-development.ps1 -RequireUnityMcp`를 실행합니다.
- 이 결정은 개발 인프라에만 적용됩니다. 계정 데이터, 월드 Fact, Rule Block,
  물리 의미, 런타임 게임플레이 권한을 소유하지 않습니다.

## 32. 정규화된 온톨로지 애니메이션 전환

- canonical 애니메이션 의도와 액터 레퍼토리가 계속 클립을 선택합니다.
  Unity 표현 계층은 선택된 결과를 블렌딩할 뿐이며 이동·전투 권한이나 지속
  월드 Fact를 만들지 않습니다.
- 전신 클립 간 전환은 하나의 전신 `AnimationLayerMixerPlayable` 아래에서
  정규화된 `AnimationMixerPlayable` 하나를 사용합니다. 연속된 클립을 서로
  다른 override 레이어에 보완 가중치로 배치하면 안 됩니다. 레이어 합성은
  정규화된 크로스페이드가 아니라 순차 합성이므로 컨트롤러 또는 바인드 포즈가
  아바타에 섞일 수 있습니다.
- 컨트롤러와 클립 사이 전환은 레이어 가중치 전환을 유지합니다. 클립 간
  전환에서는 온톨로지 표현 레이어를 항상 완전히 유지하고 그 내부의 정규화된
  클립 믹서에서만 크로스페이드합니다.
- 애니메이션 의도나 레퍼토리 항목을 제거하면 선택된 표현도 계속 제거됩니다.
  이 전환 구조는 표현 어댑터일 뿐이며 Triple, Rule Block 또는 Authority
  결과가 없을 때 동작을 만드는 숨은 fallback이 아닙니다.

## 33. Authority 소유 의미 패키지 변경

- 의미 패키지는 선택한 엔티티의 작성 트리플, 룰블록 바인딩, 물리 의미
  선언을 한 번에 변경하는 영속적·리비전 기반·멱등 명령입니다. Unity가
  서로 연결된 값을 여러 로컬 변경으로 따로 확정하지 않습니다.
- 런타임 `빠른 설정`은 사용자가 의미 패키지를 적용하는 기본 화면입니다.
  선택지는 `RuleBlockPresetDatabase`에서 읽습니다. 새 선택지를 추가할 때는
  Unity 버튼이나 ID별 분기를 만들지 않고 필수 개념, 작성 Fact, 규칙 블록,
  검증 선행조건, 선택적 물리 의미를 데이터로 발행합니다.
- 의미 패키지는 배치된 모든 엔티티에 적용할 수 있습니다. Authority는
  사용자가 오브젝트에 새 의미를 부여할 수 있는지 판단할 때 템플릿,
  프리팹, 메시, 기존 개념, 오브젝트 이름 예외를 사용하지 않습니다.
- 각 패키지는 `primary_physical_meaning`, `attachment_meaning`, 개별 물리
  효과 슬롯처럼 명시적인 의미 슬롯을 사용합니다. 같은 슬롯에 새
  패키지를 적용하면 이전 기여분 제거, 밀려난 작성 기준값 복원, 새
  기여분 적용이 동일한 월드 리비전 안에서 원자적으로 처리됩니다.
- Authority 기여 원장은 해당 패키지가 소유하는 Fact·룰블록 행과 패키지
  때문에 밀려난 작성 행을 기록합니다. 패키지는 자신보다 먼저 존재하던
  정확히 일치하는 활성·미소유 행을 명시적으로 인수할 수 있지만, 다른 활성
  패키지가 소유한 행은 인수할 수 없습니다.
- 미소유 레거시 규칙 블록이 같은 규칙·매개변수를 사용하지만 불변 정의
  버전만 이전 버전인 경우, 기본 패키지 인수는 해당 바인딩과 추론 결과를
  원자적으로 철회하고 새 바인딩 ID로 요청 버전을 삽입합니다. 불변 이력은
  보존하며 여러 활성 버전이 함께 남지 않습니다.
- 카탈로그에 미리 설정된 엔티티는 데이터에서 생성되는
  `template_semantic_baseline` 패키지를 사용합니다. 이 패키지는 정의의 초기
  개념·Fact, 물리·부착 프로필 선언, 현재 남아 있는 기본 규칙 블록만
  소유합니다. 기존 배치물은 의미 계약 버전이 올라갈 때 한 번 인수하므로,
  사용자가 앞서 제거한 기본 규칙을 마이그레이션이 다시 만들지 않습니다.
- 패키지 또는 패키지가 소유한 규칙 블록 하나를 제거하면 동일한 Authority
  리비전에서 소유 기여분 전체가 철회됩니다. 독립 작성 값과 다른 패키지
  소유 값은 보존됩니다. 영속 의미 계약 표시는 남아 있으므로 다음 월드
  입장에서 제거된 기본 의미가 되살아나지 않습니다.
- 런타임 프리셋, 물리 프로필, 부착 프로필, 임시 기술 부여, 물리 효과는
  모두 명령 우선 방식입니다. Unity는 Authority가 승인한 투영을 받은
  뒤 변경된 각 엔티티의 의미 어댑터를 다시 동기화하고 로컬
  시뮬레이션과 표현을 실행합니다.
- 거절된 패키지는 아무것도 변경하지 않습니다. 투영 적용 시 변경된
  오브젝트의 의미 어댑터를 항상 다시 동기화하므로 트리플은 과거
  상태인데 Unity 물리만 새 상태로 남는 분리 상태를 허용하지 않습니다.
- 영속 Authority 브리지는 additive 월드 씬의 편집 컨트롤러보다 먼저
  활성화될 수 있습니다. 따라서 의존성 탐색과 이벤트 구독을 하나의
  멱등 작업으로 처리하며, 이후 투영이나 상호작용에서 발견한
  컨트롤러도 즉시 구독합니다. 편집 씬이 브리지보다 늦게 로드됐다는
  이유로 로컬 룰블록·의미 패키지 변경이 잠시 보였다가 사라지면 안 됩니다.

## 34. 원격 아바타의 로컬 식별자 제외

- 원격 아바타 표현은 계정 입장 아바타 식별자를 우선 사용하고, 그다음
  로컬 플레이어 입력을 소유한 Actor를 제외합니다. 씬에서 처음 발견한
  `OntologyAuthorityEntityIdentity`를 로컬 플레이어로 선택하지 않습니다.
- Carryable·NPC·몬스터·배치 오브젝트도 같은 범용 Authority 식별 컴포넌트를
  가질 수 있으므로 컴포넌트 탐색 순서는 로컬 플레이어라는 증거가 아닙니다.
- 원격 표시기보다 안정 로컬 아바타가 늦게 준비되면 잘못 캐시된 식별자를
  교체하고, 해당 로컬 아바타 ID로 만들어진 표시 전용 복제본을 즉시 제거합니다.
- 원격 복제본은 계속 일시적인 Unity 표현입니다. 이 보정은 월드 Fact,
  모션 스냅샷, 계정 프로필, 영속 월드 엔티티를 만들거나 제거하지 않습니다.

## 35. 복구 가능한 의미 패키지 보낼 편지함 계약

- Authority 명령 JSON의 선택적 엔티티 GUID는 빈 문자열이 아니라 JSON
  `null`을 사용합니다. 따라서 canonical 의미 패키지 Fact는
  `objectEntityId: null`로 발행합니다.
- Unity는 기존 대기 중인 `apply_meaning_package` 명령을 재생하기 전에
  nullable 형식으로 정규화하되 원래 command ID는 유지합니다. 새 로컬
  변경이 아니라 Authority의 멱등성 판정이 복구 명령의 적용 여부를
  결정합니다.
- 잘못된 의미 패키지 payload는
  `invalid_meaning_package_payload`라는 완료된 Authority 거절이어야
  합니다. HTTP 500으로 빠져나가 Unity에서 전송 응답 손실처럼 보이면
  안 됩니다.
- 실제 전송 실패가 해결되지 않았을 때 월드 입장이 대기할 수는 있지만,
  과거의 잘못된 보낼 편지함 항목 하나가 세션을 영구적으로 `Recovering`
  상태에 가두면 안 됩니다. 재생 또는 정상 거절이 완료된 명령은 큐에서
  제거합니다.

## 36. Authority와 정렬된 익사 복구 체크포인트

- `Drowning`은 계속 추론된 이동 관계입니다. 이 관계가 있을 때만 Unity
  복구 표현이 활성화되고, 관계를 제거하면 복구 표현도 즉시 제거됩니다.
  Unity가 물 메시나 오브젝트 이름으로 익사를 추론하지 않습니다.
- 마지막으로 승인된 영속 아바타 체크포인트를 고정 리스폰 기준으로
  사용합니다. 일반 이동, 물 겹침, 추락, 가라앉는 표현은 이 기준을
  변경하지 않습니다. 자동 체크포인트는 안정된 마른 지면 표현에서만
  저장할 수 있습니다.
- 체크포인트와 계정 입장 서비스는 로컬 플레이어 입력을 소유한 Actor를
  통해 아바타를 찾습니다. 컴포넌트 탐색 순서 때문에 NPC·몬스터·운반
  오브젝트·배치 엔티티가 체크포인트 소유자로 선택되면 안 됩니다.
- 복구 시 로컬 아바타를 확정 리스폰 기준으로 이동하고 임시 수직 속도를
  지운 뒤 한 번의 충돌 지면 정착을 요청합니다. 이후 해당 복구 위치를
  리비전 기반·멱등 `save_avatar_checkpoint` 명령으로 한 번 저장합니다.
- 복구 체크포인트가 처리되는 동안 수평 Authority 위치 보정을 중단합니다.
  체크포인트가 승인되면 Authority의 일시 모션 상태도 같은 영속
  Transform으로 다시 시작한 뒤 보정을 재개하므로, 과거 물속 위치가
  플레이어를 다시 물 쪽으로 끌어당길 수 없습니다.
- 복구는 작성 게임플레이 Fact를 만들지 않고 프레임별 이동을 저장하지
  않습니다. `Drowning` 관계가 없거나 제거되면 복구 어댑터는 아바타를
  이동할 권한이 없습니다.

## 37. 장착 상호작용과 다중 슬롯 소유권

- 착용형과 운반형 무기는 의도적으로 입력 정책을 분리합니다.
  `pickup_behavior -> SelectThenEquip`은 기존 선택·접근 흐름을 사용합니다.
  왼쪽 클릭으로 튜브를 선택하고 접근을 시작하면 일시적인
  `interaction_intent`가 발행되며, Actor가 가까워졌을 때
  `AutoEquipNearbyWearable`이 부착 관계를 추론합니다. 장착된 튜브를
  클릭하면 온톨로지 해제 행동을 실행합니다.
- `F`는 `pickup_behavior -> SelectThenCarry` 전용이며 불변
  `equip_weapon` Authority 행동을 전송합니다. Unity는 무기 허용 Fact를
  직접 쓰거나 프리팹명·메시명·오브젝트명으로 판단하지 않습니다.
- 두 경로 모두 대상의 작성된 개념·프로필 트리플과 대응하는
  `AutoEquipNearbyWearable` 또는 `EquipItemOnInteractionIntent` 룰블록을
  계속 요구합니다.
- 영속 장착 상태는 아이템 소유형 `item equipped_by actor`입니다. 장착 가능한
  각 아이템은 정확히 하나의 `has_slot` 값을 작성합니다. 공통
  `EquipmentSlotAvailable` 온톨로지 조건은 같은 배우가 동일 슬롯의 다른
  아이템을 이미 장착했으면 거부하며 슬롯명·아이템명·프리팹명·메시명을
  검사하지 않습니다.
- 서로 다른 슬롯은 함께 사용할 수 있습니다. 기준 조합은
  `InflatableRing has_slot Waist`와 `Sword has_slot RightHand`입니다.
  어느 한쪽을 장착하거나 해제해도 다른 아이템의 부착·물리 의미·임시 기술·
  애니메이션 선택은 유지됩니다.
- 장착된 무기를 바라보고 `F`를 누르면 `unequip_equipment`를 실행합니다.
  튜브는 전투 입력 후보와 자동 해제 후보에서 제외되므로 `F`로 튜브를
  장착하거나 해제할 수 없습니다.
- 부착 어댑터는 `equipped_by`를 표현하고, 전투 애니메이션 해석기는 장착
  아이템 중 데이터 소유 무기 표현 카탈로그에 등록된 것만 선택합니다. 따라서
  튜브가 무기 Idle을 선택하지 않으며 무기 표현 데이터가 없을 때 fallback
  애니메이션도 만들지 않습니다.
- 대응 장착 룰블록을 제거하면 해당 행동도 사라집니다.
  `AutoEquipNearbyWearable`이 없으면 튜브 근접 장착이 추론되지 않고,
  `EquipItemOnInteractionIntent`가 없으면 Authority가 무기 장착을 거부합니다.
  어느 경로에도 이름 기반 허용 fallback은 없습니다.

## 38. Authority 투영 소속과 의미 계약 룰블록 폐기

- 월드 입장 뒤에는 현재 World Authority 투영이 런타임 배치 오브젝트 표현의
  소속 기준입니다. 영속 Authority GUID를 가졌지만 투영에 없는 Unity 배치
  오브젝트는 즉시 비활성화한 뒤 제거하며, 상호작용할 수 없는 로컬 유령
  오브젝트로 계속 보이게 두지 않습니다.
- 리비전 기반 배치 명령을 전송 중인 Authority-first 표현은 제거 대상에서
  제외합니다. 에디트 모드와 월드 입장 전 로컬 저작에는 이 런타임 투영
  정리가 적용되지 않습니다.
- 룰블록 교체와 폐기는 카탈로그가 소유하는 별도 작업입니다. 마이그레이션은
  교체 규칙을 도입한 계약 버전을 넘어갈 때 한 번만 새 규칙을 추가하며,
  폐기는 자신이 선언된 계약 버전을 넘어갈 때만 구형 바인딩을 제거합니다.
- 무기 의미 계약 버전 3은 `AutoCarryNearbyCarryable/?object`를 폐기합니다.
  버전 1 무기는 먼저 `EquipItemOnInteractionIntent/?target`을 받고, 버전 2
  무기는 남아 있던 구형 자동 장착 바인딩만 제거합니다. 사용자가 새 F 상호
  작용 룰블록을 제거한 결정은 자동으로 되돌리지 않습니다.
- 버전 3 이후 사용자가 폐기된 재사용 룰블록을 다시 추가하는 것은 명시적인
  저작 결정으로 보존합니다. 런타임 코드는 한 번의 데이터 선언 계약 전이
  뒤에 룰블록을 계속 감시하거나 재생성하지 않습니다.

## 39. Unity와 Authority 사이의 선택적 효과 메타데이터

- Unity 직렬화는 설정하지 않은 선택적 중첩 오브젝트를 기본 인스턴스로 만들
  수 있습니다. 발행된 룰 정의에서는 값이 전부 빈 수치 소스나 비교 방식이
  `None`인 수치 가드로 나타날 수 있습니다.
- Authority는 의미 필드가 전부 비어 있는 기본 수치 소스·가드를 미설정으로
  처리합니다. 의미 필드가 하나라도 설정된 경우에만 해당 오브젝트를 검증하고
  평가합니다. 일부만 잘못 설정한 메타데이터는 계속 거부합니다.
- 이 전송 경계 규칙은 공통 효과 의미론입니다. 장착·특정 predicate·룰블록
  ID·프리팹·Unity 오브젝트명을 예외 처리하지 않습니다.
- 기존 불변 정의의 payload나 checksum을 다시 쓰지 않고도 실행할 수 있습니다.
  실제로 설정된 수치 소스·가드는 기존과 동일하게 엄격히 검증·평가합니다.
- 같은 호환 경계는 선택적 룰블록 표현에도 적용합니다. Unity는 설정하지 않은
  `runtimePresentation`을 빈 중첩 오브젝트로 직렬화할 수 있습니다. Authority
  canonicalization은 이 빈 오브젝트를 기존의 필드 부재와 동일하게 처리하므로,
  스키마 필드 추가가 이미 발행된 모든 불변 룰의 체크섬을 바꾸지 않습니다.
- `AttackLight`처럼 실제로 설정된 런타임 표현은 계속 불변 룰블록 payload의
  일부입니다. 설정값을 변경하려면 새 정의 버전이 필요하며, 비어 있는 스키마
  자리표시자만 정규화하여 제거합니다.

## 40. 중단 가능한 행동 표현의 이동 전환

- Authority 승인은 계속 행동 정의의 canonical 애니메이션 의도를 통해 일시적
  행동 표현을 선택합니다. Unity는 무기·프리팹·메시·오브젝트명에서 장착
  애니메이션을 추론하지 않습니다.
- 일시적 클립의 중단 가능 여부는 애니메이션 매니페스트가 소유합니다. 중단
  가능한 행동 표현 중 플레이어 이동 의도가 들어오면 표현 어댑터는 현재 장비의
  이동 의도를 즉시 다시 평가하며, 중간 Idle 프레임을 기다리지 않습니다.
- `WeaponEquip`과 `WeaponUnequip`은 이동으로 중단할 수 있으므로 카탈로그가
  선택한 `WeaponWalk`으로 바로 전환합니다. 공격·피격 등 매니페스트에서 중단
  불가로 작성한 표현은 기존 잠금을 유지합니다.
- 이는 임시 표현 스케줄링일 뿐입니다. 월드 Fact를 작성하거나 Authority 장착
  상태를 변경하지 않으며 트리플·룰블록·물리 의미·애니메이션 레퍼토리 요구를
  우회하지 않습니다.

## 41. Manifest 우선 애니메이션 위자드 생산 라인

- `AnimationContentManifest.asset`이 재사용 애니메이션 콘텐츠의 유일한 저작
  원본입니다. `AnimationDatabase.asset`과 각 ActorProfile의 애니메이션
  레퍼토리는 독립 저작 영역이 아니라 자동 생성되는 투영입니다.
- 캐릭터 애니메이션 위자드는 클립 출처, 의도, Actor·Rig 범위, 재생 정책,
  대상 Profile을 포함한 canonical Manifest 항목을 먼저 만들고 전체 후보
  Manifest를 검증한 뒤에만 등록합니다.
- 검증에 성공하면 런타임 Animation Database와 영향받는 모든 ActorProfile을
  자동 동기화합니다. 검증에 실패하면 이전 Manifest를 복원하여 Database에만
  있거나 Profile에만 있는 항목을 남기지 않습니다.
- Manifest 항목을 제거하면 다음 동기화 때 생성된 런타임 정의와 Profile
  소속도 함께 제거됩니다. 위자드는 `Swimming`, `Locomotion` 같은 의미
  속성을 하드코딩하여 주입하지 않습니다.
- 현재 기본·장착·공격·회복 애니메이션도 같은 투영 계약으로 검증합니다.
  World Authority 개발 행동의 애니메이션 의도는 패키지 발행 전에 동기화된
  Manifest에서 반드시 해석되어야 합니다.

## 42. 룰블록이 소유하는 기본 근접 공격

- `Player/Attack`은 클릭 이동과 마우스 왼쪽 클릭을 공유합니다. Unity는
  포인터 후보와 장착 도구에 작성된 행동 ID만 전달합니다. World Authority가
  실행과 동일한 발행 행동·배정 룰블록을 변경이나 쿨다운 획득 없이
  사전 평가합니다. 작성된 `attack_range` 안의 살아 있는 적대 대상이
  승인된 경우에만 클릭을 전투가 소비하며, 빈 바닥·우호 대상·죽은 대상·
  누락된 룰블록·사거리 밖 대상 클릭은 이동 입력으로 남습니다. 마우스
  오른쪽은 카메라 또는 향후 보조 행동을 위해 비워 둡니다.
- 휘두르고 공격할 수 있는 무기는 `swing_action`, `attack_action`,
  `attack_damage`, `attack_range`, `attack_cooldown`,
  `grants_capability -> MeleeAttack`과 호환되는 물리·부착 프로필을
  작성합니다. 행동 ID와 수치는 프리팹·메시·오브젝트명이 아니라 무기 데이터와
  함께 이동합니다.
- `SwingWeaponOnPrimaryIntent/?tool`은 canonical `AttackLight` 런타임 표현을
  소유하고 영속 효과는 갖지 않습니다.
  `MeleeAttackOnPrimaryIntent/?tool`은 체력·사망·보상 변경을 별도로
  소유합니다. 두 불변 전송 정의는 배정된 룰블록 결과를 중복하지 않습니다.
- 부작용 없는 행동 사전 평가 엔드포인트가 `primary_attack_intent`와
  `primary_swing_intent`를 실행과 동일한 준비·룰블록 경로로 평가합니다.
  사전 평가는 이후 변경 내용을 계산할 수 있지만 실제 적용, 쿨다운 획득,
  이벤트·Fact 기록, 리비전 증가는 하지 않습니다. 두 사전 평가가 승인되면
  휘두르기는 표현 전용 런타임 행동으로 실행하고 같은 대상을 기존
  리비전·멱등 피해 행동으로 처리합니다. 실행 시 계약을 다시 검증하므로
  사전 평가는 권한 승인권이 아닙니다.
- 위치 샘플과 쿨다운 임대는 일시적입니다. 프레임마다 또는 빈 바닥
  클릭마다 영속 Fact·이벤트를 만들지 않습니다. 사전 평가는 공격 행동이
  작성된 도구를 장착하고 포인터가 투영 대상을 찾았을 때만 요청합니다.
  서비스 사용 시 Redis가 복제 서버 간 쿨다운 임대를 제공합니다.
- Unity 애니메이션·VFX 어댑터는 Authority가 승인한 표현 의도만 소비합니다.
  검증된 애니메이션 Manifest·Actor 레퍼토리·전투 카탈로그·VFX 데이터가
  시각 표현을 해석하지만 전투 결과를 만들지는 않습니다.
- 무기 의미 계약 버전 4는 대상 공격 데이터를 한 번 도입하고, 버전 5는
  `swing_action`과 해당 룰블록을 한 번 도입합니다. 기존 작성값과 이후 사용자
  제거 상태를 보존합니다. 필요한 두 블록 중 하나라도 제거하면 숨은
  fallback 없이 전투 클릭 경로가 사라지고, 같은 클릭은 이동 입력으로
  남습니다. 공격 행동 버전 9와 휘두르기 행동 버전 1은 Authority 패키지·
  무기 Manifest·전투 카탈로그에서 함께 동기화됩니다.

## 43. 재사용 가능한 자율 액터·몬스터 계약

- 메시, 프리팹, 배치 카테고리, 오브젝트 이름만으로는 몬스터가 되지
  않습니다. 나무토막 같은 일반 오브젝트도 `Actor`,
  `AutonomousAgent`, `Monster`, `Combatant`, `Damageable` 컨셉과 진영,
  적대 관계, 생명, 이동, 감지, 추적 한계, 공격, 액션, 애니메이션 의도
  Fact, 자율 전투 Rule Block, `AuthorityKinematic` 물리 의미를 모두
  가지면 같은 자율 근접 액터로 동작합니다.
- `autonomous_melee_monster`는 선택한 엔티티에 이 계약을 붙이는 에디터
  프리셋입니다. Unity 실행 로직을 포함하지 않고 원본 프리팹이나
  템플릿도 바꾸지 않습니다. 적용 후 사용자가 Fact 수치와 규칙을
  수정하거나 다른 재사용 규칙으로 교체할 수 있습니다.
- 카탈로그 기본 몬스터는 의미 계약 버전 3을 사용합니다. 계약 마커가
  없는 기존 배치 인스턴스에는 현재의 완전한 계약을 한 번 적용하고,
  버전이 있는 인스턴스에는 해당 버전 전환 구간에 선언된 Fact와 Rule
  Block의 도입·폐기만 적용합니다. 버전 3은 같은 predicate에 다른 활성
  값이 있을 때만 구형 작성 기본값 `current_health=30`,
  `is_alive=true`를 폐기합니다. 따라서 충돌하는 구형 기본값은 제거하지만
  죽은 몬스터를 되살리거나 유일한 정상 상태를 지우지 않습니다. 마커가
  올라간 뒤에는 사용자의 제거 결정을 보존하며 이후 갱신이 행동을 몰래
  복구하지 않습니다.
- 계약 이행에 사용하는 관계 카디널리티는 Unity 이름 예외가 아니라
  canonical 용어 메타데이터입니다. `has_concept` 같은 집합 관계는 정확히
  같은 값만 중복으로 판단하므로 기존 `Monster` 컨셉이 있어도
  `AutonomousAgent`와 `Combatant` 도입을 막지 않습니다. 단일값 또는
  미지정 관계는 사용자가 이미 작성한 값을 보존합니다. 계약 마커가 없는
  구형 인스턴스 복구에도 같은 카디널리티를 적용하므로, 기존 단일값 상태
  옆에 카탈로그 기본값을 추가하지 않습니다.
- `attack_action`은 활성화된 불변 액션 정의를 선택합니다. 해당 액션이
  선언한 Rule Block과 액터에 활성 배정된 Rule Block이 일치해야 합니다.
  스케줄러는 특정 몬스터 프리팹을 알아보거나 숨은 전투 fallback을
  만들지 않습니다.
- World Authority가 목표 선택, 진영 판정, 거리, 추적 한계, 이동 시뮬레이션,
  쿨다운, 피해, 사망, 리비전, 멱등성을 소유합니다. 자율 이동과 표현
  타이밍은 일시 데이터이며 승인된 체력·사망 변경만 Authority의 영속
  변경으로 기록됩니다.
- Unity의 `AuthorityKinematic` 어댑터는 승인된 위치·회전을 보간하고
  canonical 대기·이동·공격 애니메이션 의도만 표현합니다. 플레이어를
  찾거나 적대 관계, 거리, 피해, Rule Block을 평가하지 않습니다.
- Rule Block, 액션과 규칙의 연결, 필수 의미 Fact/컨셉,
  `AuthorityKinematic` 의미 중 하나를 제거하면 다음 설정 갱신 때 자율
  행동이 제거됩니다. 오브젝트는 일반 배치물로 남으며 이름 기반 fallback은
  몬스터 행동을 복구하지 않습니다.

## 44. Rule Block이 소유하는 플레이어 전투 리스폰

- 전투 사망 복구는 익사 복구와 분리합니다. 플레이어 아바타는
  `respawn_action -> respawn_avatar`를 작성하고, 배정된
  `RespawnPlayerOnDeath` Rule Block이 영속 체력과 생존 상태 전환을
  소유합니다.
- World Authority가 현재 리비전에서 액션을 평가하여 `maximum_health`로
  `current_health`를 회복한 다음 `is_alive=true`를 설정합니다. Unity는
  두 결과를 직접 기록하지 않습니다.
- Authority가 액션을 승인하고 갱신된 사영에서 생존 상태를 확인한 뒤에만
  Unity가 이미 확정된 체크포인트 위치를 표현하고, 일시적인 접지·이동 상태를
  초기화한 뒤 같은 위치를 한 번 다시 시드합니다. 체크포인트 어댑터는 리스폰
  규칙을 소유하지 않습니다.
- 플레이어 의미 계약 버전 1은 액션 Fact와 Rule Block 배정을 한 번만
  도입합니다. 이 마커 때문에 사용자가 나중에 제거한 Rule Block을 갱신
  과정이 몰래 복구하지 않습니다.
- `RespawnPlayerOnDeath`를 제거하면 Authority가 리스폰 의도를 거절합니다.
  Unity에는 체력, 생존 상태, 위치를 되살리는 숨은 fallback이 없습니다.
- 재사용 계약은 개발 액션 패키지 `social_village@3.2.1`로 발행합니다.

## 45. 하네스가 강제하는 무기·몬스터 생산 계약

- 모델을 장착할 수 있거나 애니메이션이 재생된다는 이유만으로 완성된 무기가
  되지 않습니다. 필수 `weapon-ontology-production` 계약은 다음 순서를
  요구합니다. 프로젝트 소유 리소스 등록, 능력·행동 ID·슬롯·공격력·사거리·
  쿨다운·프로필 트리플, 장착·휘두르기·공격 Rule Block 배정, 해당 블록을
  호출하는 불변 액션, 물리 의미와 부착·그립 프로필, 검증된 애니메이션·VFX
  Manifest, Authority 평가와 영속 변경, 승인 결과만 표현하는 Unity, 실행
  가능한 Rule Block 제거 증거입니다.
- 프리팹이 이동하거나 공격한다는 이유만으로 완성된 몬스터가 되지 않습니다.
  필수 `monster-ontology-production` 계약은 다음 순서를 요구합니다. 프로젝트
  소유 비주얼·카탈로그 등록, 액터·자율 에이전트·몬스터·전투원·피해 가능·
  진영·적대·생명·이동·감지·추적 한계·공격·액션·애니메이션 의도 트리플,
  자율 Rule Block 배정, 해당 블록을 호출하는 불변 액션,
  `AuthorityKinematic` 물리 의미, 검증된 애니메이션 Manifest·Profile,
  Authority 시뮬레이션과 영속 전투 변경, Unity 보간·표현, 실행 가능한 계약
  제거 증거입니다.
- `scripts/verify-development.ps1`는 두 canonical 생산 계약 중 하나가
  없거나, 중복·이름 변경·단계 누락·버전 오류가 있거나, 금지 구현 선언이
  부족하거나, 활성·제거 증거가 있는 게임플레이 파이프라인 시나리오에
  연결되지 않으면 하네스 검증을 실패시킵니다.
- 금지 구현에는 메시·프리팹·오브젝트 이름 기반 게임플레이 분기, Unity가
  소유하는 게임 결과 또는 직접 영속 기록, 배정 Rule Block 결과를 중복하는
  액션 효과, Rule Block 제거 뒤에도 남는 행동, 검증된 Manifest를 우회하는
  애니메이션 등록이 포함됩니다.
- 새로 만들거나 마이그레이션하는 모든 무기·몬스터는 재사용 가능한 생산
  콘텐츠로 인정되기 전에 canonical 생산 계약과 실행 증거를 확장해야 합니다.

## 46. 하네스가 강제하는 플레이어 온톨로지 생산 계약

- 플레이어 게임플레이도 이제 필수 `player-ontology-production` 계약을
  따릅니다. 계정 소유 외형·프로필 설정은 월드 Fact에 넣지 않으며, 선택한
  월드의 아바타 엔티티가 플레이어 역할, 능력, 생명, 진영, 액션, 이동,
  물리 의미, 애니메이션 의도 트리플을 소유합니다.
- 플레이어 의미 계약 버전 2는 `locomotion_action -> move_avatar`,
  `grants_capability -> Locomotion`, 숫자형 `movement_speed`,
  `physical_profile -> AuthorityKinematic`, 대기·이동 애니메이션 의도,
  배정된 `MovePlayerFromIntent/?actor` Rule Block을 도입합니다. 이 계약은
  `social_village@3.3.0` 패키지로 발행합니다.
- 모든 일시적 이동 샘플은 불변 이동 액션을 함께 지정합니다. World
  Authority는 샘플을 받기 전에 그 액션을 배정된 Rule Block 경로로
  사전 평가합니다. 이동 스케줄러도 Actor/Player 개념, 이동 능력, 생존
  상태, 물리 의미, 액션-규칙 연결, 활성 배정, 숫자형 속도를 독립적으로
  모두 요구합니다.
- Unity 입력은 사용자 트리거와 로컬 충돌·표현만 소유합니다. Authority
  월드에서는 현재 계약이 승인된 뒤에만 예측 이동을 표현할 수 있습니다.
  이동 액션을 제거하면 Unity 입력 경로가 사라지고, Rule Block이나 필수
  의미를 제거하면 Authority가 입력을 거절하며 이동 스케줄에서도
  플레이어가 제외됩니다.
- 입장 마이그레이션은 기록된 계약 버전 이후에 새로 도입된 의미만
  추가합니다. 런타임 기반 준비 과정은 더 이상 입장할 때마다 플레이어의
  모든 기본 Fact를 다시 작성하지 않으므로, 마이그레이션 뒤 사용자가
  제거한 상태가 그대로 유지됩니다.
- 플레이어 생산 증거는 이동의 활성·제거 경로, 기존 장착·기본 공격 계약,
  전투 사망·리스폰, 검증된 애니메이션 Manifest, Authority와 Unity 경계를
  함께 확인합니다. 자동 계약 검증 뒤 실제 사냥 전체 플레이가 다음
  제품 수준 인수 테스트입니다.
## 39. Authority 장착 관계와 구역 복구

- `migrate_legacy_equipment_relations`는 행동이 만든 구형 `equips` Fact와,
  대응하는 `tool equipped_by actor` 관계가 없는
  `actor attacks_with tool` 잔여 관계를 철회합니다. 과거 행동 기록만으로
  장착 상태를 새로 추측해 만들지는 않습니다.
- `migrate_unassigned_entity_zones`는 구형 무구역 엔티티의 저장 X/Z 위치가
  정확히 하나의 작성된 Zone에 포함될 때만 해당 Zone을 배정합니다.
  여러 Zone에 겹치거나 범위 밖이면 Authority가 임의로 정하지 않습니다.
- Unity의 리비전 영속 명령은 Authority 클라이언트 단위로 직렬화합니다.
  서버가 `stale_revision`을 반환하면 새 멱등 키로 한 번 재시도합니다.
  이 처리는 전송 순서만 보장하며 Rule Block을 대신하거나 게임 규칙을
  만들지 않습니다. 플레이어 이동 표본은 계속 비영속 런타임 상태입니다.

## 47. 전투 대상 고정 기본 공격 접근

- 투영된 살아 있는 전투 대상을 왼쪽 클릭하면 World Authority가 작성된
  공격·휘두르기 액션을 사전 평가하는 동안 해당 클릭을 비영속 전투
  의도로 보관합니다. 다른 공격이 처리 중이거나 쿨다운 중이라는 이유로
  같은 클릭을 지형 이동 명령으로 바꾸지 않습니다.
- Authority가 `action_target_out_of_range`만 반환하면 Unity가 관찰한
  대상에게 접근할 수 있습니다. 정지 반경은 장착 도구의 canonical 숫자
  `attack_range` 트리플과 작은 이동 전용 안쪽 여유값으로 계산합니다.
  Unity는 공격 허용, 사거리, 적대성, 생존, 쿨다운, 피해, 애니메이션
  결과를 만들지 않습니다.
- 정지 반경에 도달하면 Authority 사전 평가를 한 번 다시 요청합니다.
  승인되면 기존 비영속 휘두르기와 리비전 영속 피해 경로를 실행합니다.
  처리 중·쿨다운 응답에서는 이동하지 않고 기다립니다. 대상 사망,
  투영 제거, 직접 키보드 이동, UI 입력 점유, 컴포넌트 비활성화 시
  비영속 접근 의도를 제거합니다.
- Rule Block, 액션 정의, 필수 의미 또는 올바른 사거리 데이터가 없으면
  접근을 활성화하지 않습니다. 거절된 클릭은 일반 비전투 경로로
  돌아가므로 전투 계약을 제거했을 때 숨은 Unity 대체 동작 없이 전투
  행동도 함께 제거됩니다.

## 48. 이동 승인 계약 범위와 공격 후 전환

- 월드 리비전이 바뀌었다는 사실만으로 플레이어 이동 계약이 바뀐 것은
  아닙니다. 공격 피해로 몬스터 체력처럼 다른 엔티티의 데이터만 바뀐
  경우 Unity는 이미 승인된 비영속 이동 임대를 유지합니다.
- 이동 계약 지문에는 월드와 Zone 범위, 해당 아바타 자신의 Fact,
  아바타에 배정된 Rule Block, 유일한 불변 이동 액션 정의가 포함됩니다.
  계약이 누락·중복·제거·변경된 경우에만 예측 이동 승인을 폐기하고
  Authority의 새 승인을 요구합니다.
- 애니메이션 중단 정책의 주인은 계속 `AnimationContentManifest`입니다.
  현재 `AttackLight` 표현은 승인된 이동 의도가 들어오면 이동 표현으로
  넘기도록 명시하여, 몸은 이동하지만 공격 자세가 남는 미끄러짐을
  제거합니다. Manifest에서 중단 불가로 작성한 다른 표현은 그대로
  잠금을 유지합니다.
- 이 표현 전환은 이동이나 공격 권한을 만들거나 피해량을 바꾸거나
  Fact를 생성하지 않습니다. Authority가 배정된 Rule Block을 통해 이동과
  공격 액션을 계속 평가하고, 애니메이션 어댑터는 승인된 결과의 표현만
  선택합니다.

## 49. 영속 엔티티 폐기와 처치 상태의 경계

- `is_alive=false`는 영속 게임 상태이며 Unity GameObject 삭제 명령이
  아닙니다. 처치된 엔티티는 시체로 보이거나 전리품을 제공하거나 작성된
  생명주기에 계속 참여할 수 있습니다.
- 월드에서 영구 제거할 때는 revision 및 멱등성이 보장되는 World Authority
  명령 `retire_entity`를 사용합니다. Authority는 한 revision에서 엔티티의
  `deleted_revision`을 설정하고, 해당 엔티티를 설명하거나 참조하는 활성
  트리플과 배정된 Rule Block을 철회하며, 활성 의미 패키지 적용을
  종료합니다. 과거 행과 승인된 명령·이벤트는 감사용으로 보존합니다.
- Unity 월드 에디터는 Authority Projection 엔티티를 먼저 파괴하지
  않습니다. 폐기를 요청하고 승인된 Projection을 다시 받은 뒤, 그
  Projection에서 빠진 경우에만 로컬 표현을 제거합니다. Authority가
  소유하지 않은 로컬 미리보기에는 로컬 삭제 경로를 유지합니다.
- 계정 소유 플레이어 아바타의 생명주기는 계정·아바타 명령이 소유하므로
  일반 월드 편집 폐기 명령으로 삭제할 수 없습니다.
- 처치가 몰래 폐기를 실행하지 않습니다. 자동 시체 정리는 추후 처치와
  전리품 회수 같은 작성 조건을 가진 재사용 가능한 생명주기 Rule
  Block·액션으로 추가해야 하며, 그 블록을 제거하면 처치 엔티티가
  유지되어야 합니다.
- 처치 상태가 Projection에 유지되는 동안 Unity는 canonical 죽음 의도를
  영속 상태 표현으로 재생하고, 검증된 비반복 클립의 마지막 프레임을
  유지합니다. Idle·이동·자율 행동 표현이 처치 엔티티를 다시 살아 있는
  모습으로 보이게 할 수 없습니다. 처치 상태가 해제되거나 엔티티가
  폐기되면 이 표현 잠금도 해제합니다.
- 템플릿, 프리팹, 메시, 표시 이름, 몬스터 이름, 오브젝트 이름 분기는
  폐기 과정에 사용하지 않습니다. 온톨로지로 구성된 모든 월드 엔티티는
  같은 Authority 명령과 Projection 경로를 따릅니다.

## 50. Authority 사전 평가와 실제 접촉 기반 근접 타격

- 기본 근접 피해는 더 이상 대상 선택이나 휘두르기 승인 직후 실행하지
  않습니다. World Authority가 작성된 공격·휘두르기 액션을 먼저 사전
  평가하며, 이 사전 평가는 영속 변경을 만들지 않습니다.
- 무기는 `attack_contact_mode -> WeaponContactWindow`를 작성하고, 배정된
  `MeleeAttackOnPrimaryIntent` Rule Block은 이 트리플을 요구합니다. 트리플
  또는 Rule Block을 제거하면 Unity fallback 없이 피해도 사라집니다.
- `AnimationContentManifest`가 승인된 `AttackLight` 클립의 정규화된 접촉
  구간을 소유하고, 프로젝트 소유 무기 프리팹이 조절 가능한 접촉 볼륨을
  소유합니다. Unity는 해당 구간 안에서 Authority가 사전 승인한 대상과
  실제로 겹치는지만 관찰합니다.
- 클릭 이동은 Authority가 작성한 공격 사거리와 무기·대상 콜라이더
  형상에서 계산한 정지 거리 중 더 짧은 값을 사용합니다. 이 이동 보정은
  피해를 만들지 않으며 짧은 무기가 실제로 닿을 수 있는 위치까지만
  접근시키는 표현 계층 계산입니다.
- 접촉 관찰은 비영속 입력 시점이며 피해 권한이 아닙니다. 접촉하면 Unity가
  기존 revision 영속 액션을 요청하고, World Authority가 규칙·사거리·
  쿨다운·장착·적대·생존 계약을 다시 평가한 뒤 체력·사망·전리품을
  변경합니다.
- 타격 VFX와 피격 반응은 영속 액션 승인 및 Projection 갱신 뒤 실제 접촉
  지점을 사용합니다. 마우스 레이캐스트 위치, 경과 시간 fallback, 프리팹명,
  애니메이션 이름은 타격을 만들 수 없습니다.

## 51. 실제 이동 방향을 따르는 무기 궤적 표현

- 휘두르기 VFX는 더 이상 휘두르기 승인 직후 하나의 고정된 프리팹
  회전값으로 시작하지 않고, 검증된 애니메이션 접촉 구간 안에서
  시작합니다.
- 무기 표현 Adapter는 작성된 검 길이축과 편집 가능한 Slash Anchor의
  프레임별 실제 이동을 관찰합니다. 두 벡터가 만드는 평면으로 동적 VFX
  Anchor를 정하므로 반대 방향이나 다른 각도의 휘두르기도 애니메이션을
  따라갑니다.
- 카탈로그의 VFX 로컬 회전값은 이동 방향 계산 뒤에 적용되는 후보정용
  아트 오프셋으로 유지합니다. 무기명·프리팹명·메시명·애니메이션명 분기는
  방향 계산에 사용하지 않습니다.
- 궤적 이동은 비영속 Unity 표현이며 접촉·피해·쿨다운·사망·전리품을 만들
  수 없습니다. Authority가 승인한 휘두르기 Rule Block이 애니메이션 의도를
  발행해야 하며, 해당 블록을 제거하면 숨겨진 궤적 fallback도 없습니다.

## 52. 방향에 무관한 대상 지정 근접 공격

- 대상 클릭 공격은 공격 의도를 발행하기 전에 플레이어를 선택된 Projection
  대상 방향으로 회전시킵니다. 바라보기는 비영속 이동 표현이며 Authority의
  대상·사거리·적대·Rule Block 평가를 대신하지 않습니다.
- 접촉 관찰은 이전 프레임의 무기 Box 위치·회전을 보관하고 현재 Pose까지
  이동과 회전을 보간해 검사합니다. 따라서 빠른 검이 렌더링 프레임 사이로
  대상을 통과해도 접촉을 놓치지 않습니다.
- 선형·각도 샘플 해상도와 최대 샘플 수는 프로젝트 소유 무기 프리팹에서
  후보정할 수 있는 범용 형상 설정입니다. 월드 방향·무기명·몬스터명·
  애니메이션명을 예외 처리하지 않습니다.
- 보간 접촉도 Manifest 접촉 구간 안에서 사전 승인된 대상 하나에만
  적용됩니다. 체력·쿨다운·사망·전리품 변경 권한은 계속 World Authority가
  단독으로 소유합니다.

## 53. 회전된 실제 표면 기준 근접 접근

- 접촉 접근 거리는 더 이상 무기 Box의 3차원 대각선 전체를 모든 수평
  방향의 사거리로 간주하지 않습니다. Adapter는 현재 회전된 작성 접촉
  볼륨을 승인 대상 콜라이더의 가장 가까운 점 방향으로 투영하고, 두 실제
  표면에서 보수적인 이동 정지 거리를 계산합니다.
- Manifest 접촉 구간이 열리기 전에는 피해를 보고하지 않고 이전 무기
  Pose만 계속 샘플링합니다. 따라서 첫 승인 구간 샘플은 바로 전 렌더링
  Pose부터만 보간하며 구간 경계에서 통과한 대상을 놓치지 않습니다.
- 전투 이동은 플레이어 CharacterController와 승인 대상의 작성된 상호작용
  콜라이더에서 최소 수평 몸체 간격도 계산합니다. 공격 사거리 이동 여유값은
  플레이어를 Authority 사거리 안으로 이동시킬 수 있지만, 이 물리 간격을
  줄이거나 두 표현 몸체를 서로 겹치게 만들 수 없습니다.
- 이 계산은 비영속 Physical Meaning 표현입니다. 무기명·프리팹명·
  애니메이션명·몬스터명·월드 방향 예외가 없고 피해를 만들 수 없습니다.
  실제 접촉, 접촉 모드 트리플, 애니메이션 구간, 배정된 공격 Rule Block 중
  하나라도 없으면 피해 경로는 계속 제거됩니다.

## 54. 전투 포인터의 표면 클릭 구분

- 포인터 타기팅은 레이의 모든 충돌을 가까운 순서로 확인하고, 전투 대상
  프레젠테이션 계약을 가진 Projection 엔티티만 선택합니다. 앞에 있는
  비전투 Projection 엔티티가 뒤의 유효한 전투 후보를 가리지 않습니다.
- 포인터 레이가 대상 Trigger를 근소하게 빗나가 바로 아래 지면에 닿으면,
  타기팅 Adapter는 작성된 상호작용 Collider의 수평 영역과 작고 편집 가능한
  프레젠테이션 여유값으로 대상 후보를 복원할 수 있습니다. 카메라와 대상
  사이의 시야도 열려 있어야 하므로 다른 지면이나 벽 뒤 대상은 계속 일반
  이동 입력으로 처리됩니다.
- 이 복원은 휘발성 포인터 관찰일 뿐 공격 허가가 아닙니다. 적대 관계,
  생존 상태, 사거리, 쿨다운, 배정 Rule Block, 애니메이션 의도, 접촉, 피해는
  계속 World Authority가 평가합니다. 필요한 Rule Block을 제거하면 Unity
  fallback 없이 같은 클릭은 다시 이동 입력으로 남습니다.

## 55. 플레이어·무기·몬스터·사냥 계약 통합

- 장착, 플레이어 이동, 자율 전투, 처치, 전리품은 이제 하나의 추적 가능한
  경로를 따릅니다.
  `작성 Triple -> 배정 Rule Block -> 불변 액션 -> World Authority 평가 ->
  영속/휘발 결과 -> Physical Meaning·표현 의도 -> Unity Adapter`.
- 무기 상호작용은 더 이상 Controller에 하드코딩된 액션 ID나 탐색 거리를
  사용하지 않습니다. 각 아이템이 `equip_action`, `unequip_action`,
  `interaction_range`를 Projection하며, 장착·해제 Rule Block이 관계 변경을
  소유합니다. 어느 블록이든 제거하면 해당 경로도 사라집니다.
- 플레이어 지상 이동은 월드 아바타 Triple의 액션 ID, 이동 속도, 달리기
  속도, 중력, Physical Meaning, 애니메이션 의도를 사용합니다. Unity는
  휘발성 의도만 보내고 Authority 승인을 표현하며 데이터나 Rule Block이
  없을 때 로컬 이동 상수로 복구하지 않습니다. 플레이어 점프 런타임은 현재
  완전한 계약 단위로 제거된 상태입니다.
- 자율 타기팅과 추적은 `target_concept`, `targeting_profile`,
  `chase_profile`, `target_action`, `chase_action`, 타깃·추적 Rule Block,
  공격 액션, `AuthorityKinematic` 의미를 명시적으로 요구합니다. 각 후보는
  불변 타깃 액션을 배정된 타깃 Rule로 미리 평가해 승인된 경우에만
  선택되며, 이동도 불변 추적 액션이 배정된 추적 Rule을 통과한 뒤에만
  시작합니다. 두 액션은 명시적인 평가 전용 액션이므로 승인되어도 영속
  Fact나 revision을 만들지 않습니다. World Authority는 임의의 호환
  엔티티를 조회하며 Unity 플레이어 컴포넌트, 몬스터 프리팹, 템플릿 이름,
  스케줄러 내부의 진영·개념 필터를 대상 자격으로 사용하지 않습니다.
  또한 스케줄러는 배정 Rule ID를 불변 액션 정의에서 해석하며, 몬스터 Rule
  Block ID의 내장 목록을 갖지 않습니다.
- Projection 엔티티가 `Damageable` 의미를 가지면 전투 Presenter를
  동적으로 받으며, 해당 의미를 제거하면 Presenter가 비활성화됩니다.
  따라서 타기팅·피격·사망·전리품 표현은 통나무, 바위, 생성 생물 등
  호환되는 어떤 비주얼에도 재사용할 수 있습니다.
- 공격 피해와 처치를 먼저 평가하고, 전리품 활성화는 대상에 별도 배정된
  명시적 후속 Rule 호출로 처리합니다. 치명타가 아닌 공격도 성공해야 하므로
  후속 호출은 조건부 선택이지만, 해당 블록을 제거하면 전리품 활성화도
  사라집니다. 수집도 독립 Rule Block·액션을 사용하며, 한 플레이어의
  `collected_item`을 덮어쓰지 않고 처치 대상에
  `loot_status`, `loot_collected_by` 영속 출처를 기록합니다.
- 기존 의미 버전은 불변 정의 버전으로 마이그레이션합니다. 원본 배정이
  남아 있을 때만 기존 바인딩을 갱신하며 사용자가 제거한 Rule Block을
  재입장 시 몰래 복원하지 않습니다.
- 하네스는 장착·해제, 지상 이동, 실제 평가되는 타깃·추적·공격, 의미 기반
  Presenter 생명주기, 처치·전리품 전환 각각의 활성 경로와 제거 경로를
  검증합니다.

## 56. 엔티티 표시 이름과 canonical 용어 커버리지

- 영속 엔티티 ID와 저장된 인스턴스 이름은 변경하지 않습니다. Unity 표시
  경계에서는 숫자 배치 순번과 8자리 Authority GUID 접두부처럼 확인된
  시스템 생성 접미사만 숨깁니다. 사용자가 작성한 인스턴스 이름은 항상
  그대로 표시합니다.
- 카탈로그 정의는 필수 `displayNameKey`로 다국어 기본 이름을 소유합니다.
  같은 시스템 이름을 가진 엔티티가 목록에 여러 개면 표시 전용 순번을
  붙일 수 있지만, 이 순번은 Authority나 월드 Fact에 저장하지 않습니다.
- 액터 프로필, 맵 오브젝트 템플릿, 룰 블록 프리셋, 규칙 조건/효과,
  카탈로그 의미 마이그레이션이 참조하는 모든 canonical 컨셉은
  `OntologyTerms.csv`에 등록되고 영문·한글 라벨을 가져야 합니다. 참조한
  컨셉이 없거나 잘못된 용어 종류로 등록되면 프로젝트 커버리지 검증이
  실패합니다.
- 파일명·프리팹 이름 확인은 에디터 저작 보조 기능일 뿐입니다. 비어 있는
  표시 메타데이터를 제안할 수는 있지만 게임 의미를 추론하거나 작성된
  이름을 덮어쓰거나 런타임 이름 기반 동작 분기가 될 수 없습니다.

## 57. 프로젝트 소유 UI 타이포그래피

- 프로젝트 소유 게임 UI는 `Assets/UI/Fonts/Jua-Regular.ttf`에서 생성한
  동적 TextMesh Pro 자산을 사용합니다. TMP 프로젝트 기본값, TOV 씬,
  `Assets/Prefabs/Ontology/UI`, `Assets/Data/Ontology/UI`의 프로젝트 소유
  온톨로지 UI 프리팹이 같은 자산을 사용하여 런타임 생성 텍스트와
  하이라키 작성 텍스트가 일관되게 보입니다.
- Unity `Selectable` 컨트롤 아래의 텍스트(버튼, 토글, 드롭다운, 입력창,
  해당 템플릿과 플레이스홀더)는 Jua로 변경할 때 정확히 2포인트
  커집니다. 비상호작용 라벨은 작성된 포인트 크기를 유지하며 레이아웃,
  Transform, 정렬, 색상, 하이라키, 사용자 수정값은 변경하지 않습니다.
- 타이포그래피 마이그레이션은 재실행해도 안전합니다. 다른 폰트에서 Jua로
  바뀌는 시점에만 2포인트가 더해지며 도구를 다시 실행해도 계속 커지지
  않습니다. 서드파티 UI 자산은 수정하지 않습니다.

## 58. 온톨로지 데이터 패널 언어팩 계약

- 온톨로지 데이터 패널의 제목, 탭, 모드에 따라 달라지는 추가 버튼,
  저장·불러오기, 플레이스홀더, 행 동작, 물리 선택지, 규칙 변수, 관계,
  의미 값은 모두 언어팩 키로 표시합니다. 씬이나 프리팹의 텍스트는
  에디터 작성용 대체 문구일 뿐입니다.
- 작성된 트리플, 규칙 블록, Authority 명령과 저장 데이터의 canonical
  온톨로지 ID는 계속 영어를 사용합니다. `OntologyTerms.csv`가 사용자에게
  보이는 모든 지속 관계와 의미 값을 표시 키에 연결하며, 한글·영문
  라벨이 canonical 저장 데이터를 대신하지 않습니다.
- 데이터 패널에서 사용하는 등록 관계에는 영문·한글 팩트 문장 템플릿이
  함께 있어야 합니다. 용어 라벨, 팩트 템플릿, 물리 선택·결과 키가
  빠지거나 별칭이 중복·충돌하면 Unity 언어팩 회귀 테스트가 실패합니다.
- Authority GUID·순번 접미사와 에디터 `_Copy` 접미사를 포함하여 시스템이
  생성한 것으로 확인된 런타임 인스턴스 이름은 UI에서 카탈로그 표시 키로
  보여줍니다. canonical 식별자는 그대로 유지하며, 사용자가 작성한
  인스턴스 이름과 자유 텍스트는 제거하거나 번역하지 않습니다.

## 59. 런타임 생명주기와 월드 입장 수렴

- 자율 런타임 자격은 프리팹이나 캐시된 Presenter로 추측하지 않고
  Projection으로 결정합니다. 스케줄링되는 액터와 대상은 완전한 액션,
  Rule Block, Physical Meaning 계약과 함께 활성 boolean `is_alive=true`
  Fact를 가져야 합니다. 자격을 잃으면 휘발성 이동 레코드도 제거되므로
  처치되거나 설정이 제거된 엔티티가 시각적 유령처럼 계속 이동하지
  않습니다.
- Physical Meaning이 런타임 레지스트리에 실시간 위치 소유권을 배정한
  엔티티는 최신 런타임 위치로만 타깃이 될 수 있습니다. 실시간 위치가
  없을 때 World Authority는 영속 스폰·체크포인트로 대체하지 않습니다.
  런타임 위치 소유자가 없는 정적 대상만 영속 Transform을 사용할 수
  있습니다.
- 월드 입장은 여러 활성화 보정의 묶음이 아니라 순서가 고정된 하나의
  트랜잭션입니다. 체크포인트 Controller는 영속 데이터만 복원합니다.
  `OntologyWorldEntryPresentationCoordinator`가 활성 아바타를 숨김·입력
  차단 상태로 유지하면서 FixedUpdate 충돌 준비를 기다리고, 이전 입력과
  애니메이션 표현을 초기화한 뒤, 보정된 지면 위치를 World Authority에
  revision 확인합니다. 이 단계가 모두 성공한 뒤에만 세션이 `InWorld`가
  됩니다. 필수 구성 누락, 시간 초과, 확인 거절은 게임플레이를 노출하지
  않고 입장을 실패시킵니다.
- 일반 런타임 게이트는 전용 월드 UI 루트와 런타임 Behaviour만 끌 수
  있으며 로컬 아바타 표현 경계 안의 GameObject를 비활성화할 수 없습니다.
  `OntologyActorToast`처럼 아바타에 붙은 보조 기능은 Behaviour로만
  게이트합니다. 경계를 열기 전 계정 입장 흐름은 아바타에 배정된 이동
  액션과 Rule Block을 검증하는 0 이동량의 휘발성 intent를 한 번 보냅니다.
  따라서 첫 화면의 idle·접지는 사용자의 첫 이동 입력에 의존하지 않으며
  영속 월드 이벤트를 만들지 않습니다.
- 기본 이동 애니메이션은 해당 프레임의 이동 소유자가 갱신된 뒤
  결정되는 표현 상태입니다. 애니메이션 Adapter는 `LateUpdate`에서
  승인된 idle/locomotion 의도를 다시 계산하며 이동 권한을 만들거나,
  프레임별 애니메이션 Fact를 저장하거나, Authority 승인을 대신하지
  않습니다.
- 명령 기반 애니메이션 준비 대기열에는 승인된 `execute_action` 명령만
  들어갑니다. 체크포인트, 배치, 의미 패키지 등 다른 명령은 자신이
  소유하지 않는 애니메이션 의도를 반복해서 해석하지 않습니다.
- 의미 패키지가 소유한 Rule Block 하나를 제거하면 그 바인딩과 RuleBound
  결과만 철회하고 형제 바인딩은 유지합니다. 공유 패키지 Fact는 마지막 소유
  바인딩을 제거할 때까지 유지하며, 마지막 제거 시 패키지 소유 canonical 및
  typed Fact를 철회하고 밀려났던 작성 기준값만 복원합니다. 독립 생명주기,
  계정 또는 다른 소유자의 Fact는 의도적으로 남습니다.

## 60. 전투 런타임 가용성과 규칙 결과 수명

- `InWorld` 진입은 하나의 명시적인 런타임 경계를 엽니다. 전투 입력,
  Authority 타기팅, 아바타 입력, 런타임 표현은 이 경계 전에는
  비활성화되고 경계가 열릴 때 Authority 의존성을 다시 찾습니다.
  따라서 계정·로딩 화면에서 오래된 전투 구독이 남지 않으며 정상 월드
  입장이 컴포넌트 활성화 순서에 의존하지 않습니다.
- Zone 시뮬레이션 존재 여부는 SignalR이 소유하지 않습니다. Unity는
  플레이어 런타임 활성화 후 인증된 HTTP Zone 세션 lease를 주기적으로
  갱신하고 월드·Zone·세션을 나갈 때 해제합니다. SignalR은 선택적인
  revision 알림 채널로만 남습니다. 인증된 클라이언트가 Zone에 있는 동안
  WebSocket이 끊겨도 자율 타깃·추격·공격 스케줄링이 조용히 멈추지
  않습니다.
- 액션 참조는 관계별 canonical 값입니다. `attack_action`,
  `target_action`, `chase_action` 같은 관계는 전역 표시값 별칭표를
  거치지 않고 정확한 불변 액션 ID를 유지합니다. 단일 카디널리티 관계는
  의미 패키지 적용 때 원자적으로 교체되므로 과거 별칭과 canonical
  액션이 동시에 남아 액션 해석을 모호하게 만들지 않습니다.
- 규칙 효과는 `RuleBound` 또는 `DurableState` 결과 수명을 선언합니다.
  장착 규칙이 소유한 장착 관계 같은 `RuleBound` 결과는 해당 Rule
  Block을 제거하면 철회됩니다. 승인된 피해, 사망, 리스폰, 드롭 전이는
  `DurableState`이며 Rule Block을 제거하면 이후 전이만 막히고 World
  Authority가 이미 확정한 이력은 되감기지 않습니다.
- 결과 수명은 액션이 만든 각 월드 Fact의 출처 정보로 저장됩니다. 새
  불변 규칙 정의를 게시할 때 새 정의가 같은 결과 관계를
  `DurableState`로 선언한 경우에만 기존 활성 결과를 승격합니다.
  Authority에는 체력·사망·드롭·무기·몬스터·프리팹·오브젝트 이름 기반
  마이그레이션 목록이 없습니다.
- 기존 플레이어 아바타는 의미 계약 버전 4로 이관됩니다.
  `current_health`가 없으면 Unity 숫자 상수가 아니라 아바타의 유일한
  작성 `maximum_health`와 `is_alive` 상태로 복구합니다. 기존 리스폰
  바인딩은 `WorldAuthoritySettings`에 게시된 버전으로 이동하며 사용자가
  의도적으로 제거한 바인딩은 다시 만들지 않습니다.
- 선택형 Rule 스키마 필드를 추가할 때 그 값이 과거 기본 의미와 같다면
  이미 게시된 불변 버전을 무효화해서는 안 됩니다. 따라서 canonical Rule
  직렬화는 기본 `RuleBound` 수명을 생략하고, 기본값이 아닌 명시적
  `DurableState`만 불변 내용으로 유지합니다. 이는 wire 하위 호환 규칙이며
  같은 버전의 작성 규칙을 임의로 바꿀 수 있다는 뜻이 아닙니다.

## 61. 이동 승인 범위와 연속 접지

- Manifest의 `canBlend` 전환 정책은 실제 재생에 적용됩니다.
  `canBlend=true` 항목만 정규화된 믹서에서 혼합하고,
  `canBlend=false`인 착지 항목은 즉시 전환합니다. 따라서 충돌 캡슐이
  지면에 닿은 뒤에도 공중 애니메이션의 수직 포즈가 남아 캐릭터가 다시
  튀어 오르는 것처럼 보이지 않습니다.

- 월드 입장은 이동 승인을 요청하기 전에 Projection의 `is_alive`
  상태를 확인합니다. 저장된 아바타가 사망 상태라면 작성된
  `respawn_action`과 배정된 `RespawnPlayerOnDeath` 규칙 블록을 통해
  Authority가 생명·체력을 복구하고, 새 Projection에서 생존 상태를
  검증한 다음에만 이동 승인 절차를 시작합니다. Unity는 입장을
  우회하기 위해 생명이나 체력을 로컬에서 직접 기록하지 않습니다.

- 플레이어 이동 승인 지문에는 Authority 평가에 실제로 참여하는 작성
  지상 이동 Fact, 배정된 Rule Block, 불변 이동 액션, 월드와 Zone만
  포함합니다. 전투, 장착, 프로필, 리스폰, 애니메이션 등 이동과 무관한
  아바타 변경은 이미 승인된 이동 lease를 취소하지 않습니다.
- 관련 이동 계약이 실제로 변경되면 Unity는 새 이동을 fail-closed로
  중단하고 0 이동량 Authority 재검증을 자동 요청합니다. 다음 키 입력을
  기다리지 않으며 영속 Fact를 만들지 않습니다.
- 작성된 중력은 연속적인 Physical Meaning입니다. 일시적인 이동 lease
  재검증 중에도 이미 보이는 `CharacterController`를 계속 지면으로
  접지시키고 낙하를 만들지만 위쪽 임펄스는 만들지 않습니다.
- 현재 운영 플레이어 계약에는 점프 입력, 점프 전송, `jump_avatar` 액션,
  `JumpPlayerFromIntent` Rule Block, 로컬 점프 임펄스, `JumpStart` 선택
  경로가 없습니다. 지면 접촉이 끊긴 것은 공중 표현 관찰로만 남습니다.

## 62. Authority 승인형 하이브리드 플레이어 점프와 충격 소유권

- 61절은 과거의 이중 이동 구현을 제거하는 동안 점프를 임시 폐기한
  결정을 기록합니다. 현재 운영 계약은 그 로컬 우회 코드를 다시 켜는
  대신 새 버전의 온톨로지 수직 슬라이스로 점프를 복구합니다.
- 영속 아바타는 `jump_action`, `jump_takeoff_speed`,
  `gravity_acceleration`, `ground_stick_velocity`,
  `impact_response_profile`을 작성하고 `JumpPlayerFromIntent`를
  배정받습니다. `jump_avatar`는 이 Rule Block을 호출하는 불변 평가 전용
  액션입니다. 액션 트리플이나 규칙 블록을 제거하면 점프 경로도
  제거됩니다.
- 복구된 하이브리드 계약은 개발 패키지 3.8.1의
  `JumpPlayerFromIntent` 버전 2와 `jump_avatar` 버전 2로 발행합니다.
  버전 1은 불변 이력으로 유지합니다. 플레이어 의미 계약 버전 6은 월드
  입장 전에 활성 버전 1 점프 바인딩을 철회하고 버전 2를 배정하며, 이미
  발행된 버전 1 정의를 덮어쓰지 않습니다.
- Space 입력은 일시적인 점프 요청과 현재 접지 충돌 관측만 만듭니다.
  World Authority는 전체 작성 계약이 존재하고
  `requiresGroundedObservation` 조건이 충족될 때만 승인합니다. 접지
  샘플과 수직 속도는 영속 월드 Fact로 저장하지 않습니다.
- 승인 뒤 Unity는 작성된 이륙 속도와 중력을 로컬 충돌 표현에
  적용합니다. 수평 이동, Authority 보정, 중력, 점프, 컨트롤러 방식
  임펄스를 프레임당 정확히 한 번의 `CharacterController.Move`에
  합칩니다. 반환된 `CollisionFlags`로 두 번째 Move 없이 천장 충돌과
  착지를 정리합니다.
- `impact_response_profile`은 재사용 가능한 충격 응답 Adapter를
  선택합니다. `ControllerImpulse`는 같은 컨트롤러 Move에 합쳐집니다.
  `TemporaryRigidbodyReaction`은 독립된 solid Collider가 있을 때만
  CharacterController 소유권을 중단하고 반응 중 Transform을 단독
  소유한 뒤 안정화되면 명시적으로 소유권을 돌려줍니다. 안전한 형상이
  없으면 두 solver를 동시에 실행하지 않고 단일 컨트롤러 경로로
  되돌아갑니다.
- 점프 승인은 Authority가 평가하는 일시적 결과입니다. Authority가 지형
  충돌 표현을 소유하기 전까지 포물선 수직 이동은 로컬 Unity 충돌
  표현이며, 영속 아바타 시작 위치에 기록하거나 서버 권한 원격 수직
  시뮬레이션이라고 주장하지 않습니다.
- 승인된 점프 한 번은 일시적인 표현 발생 번호를 한 번 증가시킵니다.
  애니메이션 해석기는 그 발생을 `JumpStart`로 소비하고, 이후 수직 충돌
  관측으로 `Airborne`/`Fall`을 선택하며, 지지면이 돌아오면 `Landing`에
  한 번만 진입합니다. `JumpStart`는 보통 Manifest에 작성된 재생 구간이
  끝날 때 완료하지만 클립이 실제 상승보다 길면 관측된 정점에서 즉시 이륙
  단계를 끝냅니다. `Landing`은 작성된 구간으로 완료하며 고정 타이머로
  전환하지 않습니다.
- 플레이어 직접 이동은 CharacterController가 계속 소유하므로 점프 생명
  주기의 모든 Manifest 항목은 Root Motion 비활성화를 명시해야 합니다.
  서드파티 `Jump_End` 원본은 수정하지 않고 프로젝트 Manifest에서 정규화
  0.85~1.00의 안정화 구간만 선택하여, 두 번째 점프처럼 보였던 원본
  클립의 상승 구간을 제외합니다.

## 63. 로컬 캐릭터 이동과 충돌 역할 소유권

- `physical_profile LocalCharacterController`가 하나의 Unity 이동 드라이버를
  선택합니다. 일반 이동에서 `CharacterController.Move`를 호출하는 컴포넌트는
  `OntologyCharacterMotionCoordinator` 하나이며 입력·중력·수영·승인된 충격
  어댑터는 이 소유자에게 변위만 제공합니다.
- `CharacterController.stepOffset`은 항상 0입니다. 명시적 단차 판정은 현재
  프레임 지지 탐지와 `WalkableSupport` 충돌 역할만 사용합니다. `ActorBody`,
  `DynamicProp`, 상호작용 트리거, 물 영역과 다른 액터는 장애물이며 플레이어를
  계단처럼 들어 올릴 수 없습니다.
- 월드 입장·리스폰 접지는 실제 캡슐 반지름과 skin width를 반영해 위치를 정한 뒤,
  입력이 잠긴 동안 이동 코디네이터가 접촉 샘플을 한 번 수행합니다. 따라서 첫
  사용자 이동이 바닥 안쪽에 복원된 캡슐을 위로 밀어내지 않습니다.
- 물리 의미 프로필은 독점 `motionDriver`와 `collisionRole`도 선언합니다. 프로필을
  제거하면 해당 이동 소유권과 어댑터가 비활성화되며 컴포넌트 이름이나 플레이어
  프리팹을 기준으로 한 숨은 대체 경로를 남기지 않습니다.
- Authority는 계속 이동·점프 액션과 배정된 Rule Block을 평가합니다. Unity 충돌
  관찰과 해결 위치는 임시 상태입니다. 서버 스케줄러는 충돌 없는 두 번째 Transform을
  적분하지 않으며, 공유 충돌 시뮬레이션이 생기기 전까지 클라이언트가 순서와 Zone을
  검증받는 해결 위치를 원격 표현용으로 게시합니다.

## 64. 익사 복구 이동 소유권

- 추론된 `movement_mode Drowning` 관계는 일반 입력·점프·중력·UI 입력 차단 및
  `CharacterController` 이동을 평가하기 전에 익사 표현에 임시 단독 이동 소유권을
  부여합니다.
- 복구는 가라앉는 동안 의도적으로 `CharacterController`를 끌 수 있습니다. 따라서
  복구 상태 머신은 컨트롤러가 켜진 일반 이동 분기 안이 아니라 플레이어 입력 생명
  주기에서 직접 갱신합니다. 컨트롤러를 끈 행위가 컨트롤러를 다시 켜야 할 복구 갱신을
  멈출 수 없습니다.
- 복구가 이동을 소유하는 동안 임시 수직 속도·컨트롤러 임펄스·클릭 이동·이동
  애니메이션 입력을 초기화합니다. 확정 체크포인트 복원 뒤 오래된 이동이 재개되거나
  아바타를 위로 발사할 수 없습니다.
- `Drowning` 관계가 제거되면 복구 소유권을 즉시 해제하고 컨트롤러를 복원한 뒤
  온톨로지 승인을 받은 일반 이동 경로를 재개합니다. 물 이름·메시 이름 또는 숨은
  로컬 익사 fallback은 존재하지 않습니다.

## 65. 충돌 해결 기반 평면 이동

- 지지면 탐지는 일시적인 충돌 증거일 뿐입니다. 탐지한 삼각형 법선으로 작성된
  수평 입력을 수직 변위로 바꾸지 않습니다.
- 단일 이동 코디네이터는 세계 평면 기준 이동과 작성된 수직 속도를 한 번의
  `CharacterController.Move`에 전달합니다. 경사와 충돌은 CharacterController가
  한 번만 해결하며 Unity 코드가 같은 지면을 먼저 계산한 뒤 다시 해결하지 않습니다.
- 충돌 역할 기반 명시적 단차 판정은 점프·중력과 분리해 유지하지만, 현재 아바타를
  지지하는 동일 Collider의 면이나 삼각형은 새 단차가 아니라 연속 지형입니다.
  별도의 `WalkableSupport` Collider만 명시적 단차 상단이 될 수 있습니다.
- 선택적으로 켜는 개발 진단은 요청하지 않은 컨트롤러 상승이나 외부 Transform
  쓰기를 `[PlayerMotionTrace]`로 기록하며 일반 플레이에서는 꺼져 있습니다.
  명시적으로 켜도 이 로그는 일시적인 표현 증거이며 Fact, 규칙 결과, revision
  또는 네트워크 메시지를 만들지 않습니다.

## 66. 점프 표현 생명 주기 소유권

- World Authority는 계속 작성된 점프 액션과 배정된 Rule Block을 평가합니다.
  승인 결과의 `JumpStart` 표현 의도는 canonical 점프 발생을 식별하지만, 클립
  길이에 따른 두 번째 상태 머신을 소유하지 않습니다.
- Manifest 기반 로컬 이동 해석기가 활성화된 아바타에서는
  `presentationOwner MotionStateResolver`로 명시한 애니메이션 항목만 충돌
  관찰 생명 주기로 전달됩니다. 기본 `JumpStart`, `Airborne`, `Fall`,
  `Landing` 항목은 이 메타데이터를 사용하며 Unity의 의도 이름 목록이
  소유권을 부여하지 않습니다.
- canonical 직접 이동 `Fall`은 공중 하강을 뜻합니다. 바닥으로 쓰러지는
  피해 반응 클립은 별도의 반응 의도를 사용할 수 있지만 원본 애니메이션 파일
  이름이 "Fall"이라는 이유로 `Fall`을 소유할 수 없습니다. 기본 플레이어는
  하강 중 제자리 공중 자세를 유지하고 지지면이 돌아온 뒤에만 작성된 착지
  구간으로 전환합니다.
- 공격·장착 같은 일회성 액션은 계속 일반 Authority 임시 표현 경로를 사용합니다.
  이 경로가 직접 이동 의도를 붙잡아 관찰된 정점이나 착지가 재생 클립을 바꾸지
  못하게 해서는 안 됩니다.
- 점프 Rule Block을 제거하면 여전히 점프 승인이 제거됩니다. 이 소유권 분리는
  로컬 허용 fallback을 추가하지 않으며 이동 관찰이나 애니메이션 단계를 영속
  Fact로 기록하지 않습니다.

## 67. 물리 의미 및 애니메이션 메타데이터 강화

- `OntologyMotionDriverAdapter`는 fail-closed 방식입니다. Physical Meaning에서
  파생된 어댑터가 없거나 꺼져 있거나 드라이버가 다르면 Transform 이동 권한으로
  취급하지 않습니다. 따라서 Physical Meaning을 제거하면 컴포넌트 존재 여부에
  따른 fallback 없이 해당 표현 드라이버도 제거됩니다.
- `maximumStepHeight`는 `OntologyPhysicalProfile`이 소유합니다. 로컬 캐릭터
  이동 코디네이터는 선택된 프로필이 `LocalCharacterController`를 소유할 때만
  그 값을 받고, 프로필을 제거하면 파생 튜닝도 초기화합니다.
- 애니메이션 생명 주기 소유권은 `AnimationContentManifest`에 작성하고
  `AnimationDatabase`로 동기화합니다. 같은 canonical 의도에 서로 다른
  소유자를 배정하면 검증에 실패하며, 이동 상태 해석기 소유 항목은 Root Motion을
  꺼야 합니다.
- canonical 애니메이션 ID는 마이그레이션 동안 명시적 호환 별칭을 선언할 수
  있습니다. 쓰러짐 반응은 이제 `Anim_Collapse_Reaction`이며 기존 영속
  `Anim_Fall` 참조는 legacy 별칭으로만 해석되고 새 데이터에는 작성하지 않습니다.
- 이동 상태 해석기는 현재 관찰 스냅샷만 사용합니다. 제거한 `deltaTime` 인자는
  어떤 전환에도 영향을 주지 않았습니다. 콘텐츠 파이프라인은 더 이상 클립
  속성에서 의도나 반복 동작을 추론하지 않고 Manifest를 유일한 표현 작성
  원본으로 유지합니다.

## 68. 명시적 충돌 레이어와 레거시 이동 제거

- 프로젝트 소유 TOV 런타임은 더 이상 서드파티 `CharacterMover`,
  `MovePlayerInput` 컴포넌트나 전환용 `OntologyPlayerController`에 의존하지
  않습니다. `LocalCharacterController` 물리 의미가 선택한
  `OntologyCharacterMotionCoordinator` 하나만 로컬
  `CharacterController.Move`를 소유합니다.
- `OntologyPhysicalProfileDatabase`가 모든 의미
  `OntologyCollisionRole`과 프로젝트 소유 Unity Physics Layer 및 충돌
  매트릭스의 표현 매핑을 작성합니다. canonical 역할은 계속 온톨로지
  데이터이며 Unity Layer는 Adapter 세부 사항일 뿐 규칙 ID가 될 수 없습니다.
- 현재 프로젝트 레이어는 `WorldStatic`, `ActorBody`, `DynamicProp`,
  `InteractionTrigger`, `WaterVolume`입니다. 의미 동기화는 Collider가 있는
  오브젝트에 작성된 레이어를 적용하고 물리 의미가 제거되면 원래 레이어를
  복원합니다.
- 정적인 Unity Collider라는 이유만으로 자동으로 `WalkableSupport`가 되지
  않습니다. 지형과 지지면은 명시적 충돌 역할 Adapter를 가져야 합니다.
  캐릭터 지지면 탐지는 작성된 `WalkableSupport` 레이어만 조회하며 액터
  몸체는 계단이나 지지면이 될 수 없습니다.
- 이 단계는 70절의 고정 Tick 통합에 앞서 클라이언트 충돌 예측 경계를
  구조적으로 강화했습니다. Unity는 계속 로컬 예측 표현을 소유하고,
  World Authority는 이제 공유 이동 결과를 소유합니다.

## 69. 작성된 서버 충돌 프록시 계약

- 월드 엔티티는 `collision_role`, `collision_proxy_shape`, 제한된 치수,
  선택적 중심 오프셋을 작성할 수 있습니다. 이 팩트와 영속 엔티티 Transform만
  경량 World Authority 충돌 프록시의 입력이 됩니다. Prefab 이름, Mesh 경계,
  장면 오브젝트 이름, Unity Collider 컴포넌트는 서버 충돌 의미가 될 수
  없습니다.
- 처음 지원하는 canonical 프록시 모양은 `Capsule`과 `Box`입니다.
  `Capsule`에는 양수 `collision_radius`, `collision_height`가 필요하며 높이는
  반지름의 두 배 이상이어야 합니다. `Box`에는 양수 `collision_size_x`,
  `collision_size_y`, `collision_size_z`가 필요합니다. 불완전하거나 유한하지
  않거나 지나치게 큰 데이터는 fail-closed로 거절합니다.
- 플레이어 의미 계약 버전 8은 `collision_role ActorBody`,
  `collision_proxy_shape Capsule`, 반지름 `0.45`, 높이 `2`, 중심 오프셋
  `(0, 1, 0)`을 작성합니다. 프로젝트 CharacterController 계약과 일치하며
  기존 revision 기반 작성 Fact 경로로 이관합니다. 버전 8 이후 사용자가 이를
  제거하면 제거 상태를 유지합니다.
- World Authority는 이제 어떤 엔티티든 일반 프록시 구성으로 투영할 수
  있습니다. 따라서 사용자 작성 오브젝트도 템플릿 이름 분기 없이 지지면,
  액터 몸체, 동적 오브젝트, 트리거, 물 영역이 될 수 있습니다. 같은 정책이
  중심점만이 아니라 전체 프록시가 Zone 경계 안에 있는지도 검증합니다.
- 이번 단계는 신뢰할 수 있는 서버 지오메트리 입력 계약을 만들었습니다.
  70절은 이 입력을 고정 Tick Zone·장애물·중력·점프 적분에 사용합니다.
  작성된 지지면 높이와 부드러운 로컬 보정은 이후 이동 권한 단계입니다.

## 70. World Authority 고정 Tick 플레이어 이동

- World Authority는 이제 활성 플레이어 아바타를 50ms마다 일시적 canonical
  이동 입력으로 전진시킵니다. 방향을 정규화하고 요청 속도를 작성된
  `movement_speed` 이내로 제한하며, 클라이언트가 보고한 좌표는 이 적분의
  입력으로 사용하지 않습니다.
- 이미 규칙 평가를 통과한 런타임 행동은 짧게 유지되는 일반 행동 발생으로
  기록합니다. 스케줄러는 그 canonical 행동 ID가 아바타에 작성된
  `jump_action`과 같을 때만 점프 입력으로 사용하며, 작성된
  `jump_takeoff_speed`, `gravity_acceleration`, `ground_stick_velocity`로
  계산합니다. 행동 이름이나 애니메이션 이름에 따른 분기는 없습니다.
- 스케줄러는 작성된 플레이어 Capsule 전체를 Zone 안에 유지하고, 작성된
  `ActorBody`·`DynamicProp` Capsule/Box 프록시에 대해 평면 이동을
  해결합니다. 이동 튜닝이나 플레이어 충돌 프록시가 없으면 시각 자산 또는
  컴포넌트 fallback 없이 이동을 비활성화합니다.
- `/resolved-pose`는 현재 이동 입력에 연결된 유한하고 소유권이 확인되며
  순서가 맞는 클라이언트 관찰만 받습니다. 관찰은 진단과 향후 보정을 위해
  별도 저장되며 Authority 이동 레지스트리를 변경할 수 없습니다.
- 기존 영속 입장/체크포인트 Y 지면 기준은 제거했습니다. 71절에서 이를
  작성된 `WalkableSupport` 높이와 제한된 로컬 평면 보정으로 교체합니다.

## 71. 작성된 지지면 높이와 평면 보정

- 프로젝트 소유 기본 월드는 소유자 입장 중 결정적인 ID를 가진 영속 지지면
  엔티티 하나를 준비합니다. 이 엔티티는 `collision_role WalkableSupport`,
  `collision_proxy_shape Box`, 제한된 치수, 영속 Transform,
  `physical_profile StaticAnchored`를 작성합니다. 설정값은
  `WorldAuthoritySettings`에서 수정할 수 있으며 서버는 Unity Plane, Mesh,
  Prefab, 오브젝트 이름 또는 Collider를 읽어 의미를 추론하지 않습니다.
- 수동적인 지지면 형상은 행동을 시작하지 않으므로 이 엔티티에는 새 Rule
  Block이 적용되지 않습니다. 이동과 점프는 계속 기존 불변 액션과 배정된 Rule
  Block을 요구합니다. 지지면을 폐기하거나 지지/프록시 의미를 제거하면 서버
  접지도 제거되며, 결정적 ID를 사용해 사용자가 의도적으로 제거한 엔티티를
  다시 만들지 않습니다.
- 플레이어 의미 계약 버전 9는 `maximum_step_height 0.3`과
  `ground_clearance 0.03`을 작성합니다. World Authority는 플레이어 전체
  발자국 아래의 유효한 작성 Box 중 가장 높은 것을 선택하고, 작성된 여유
  높이를 루트 Y에 적용하며, 작성된 단차 범위만 허용하고, 지지면이 없으면
  중력을 시작합니다. 영속 체크포인트 Y는 누락된 지지면을 대신하지 않습니다.
- Authority 이동 스냅샷은 현재 지지 엔티티 ID를 노출합니다. Unity는 소유한
  로컬 아바타 상태만 조회하고 오래되거나 잘못된 스냅샷을 거절하며, 제한된
  표현 시간만큼만 평면 위치를 외삽합니다. 계산된 X/Z 오차는 상한을 적용해
  `OntologyCharacterMotionCoordinator`에 전달하며 다음 프레임의 유일한
  `CharacterController.Move`에서 소비합니다. 직접 Transform 쓰기나 두 번째
  Move는 허용하지 않습니다.
- 첫 지지면 슬라이스에서는 수직 클라이언트 보정을 의도적으로 로컬 충돌
  소유로 유지합니다. 경사·다층·이동 지지면 스냅샷 계약 전에 Y를 서버로
  끌어당기면 제거했던 착지 튕김을 다시 만들 수 있습니다. 현재 지지 프록시는
  평평한 Box이며 지형 높이장과 이동 지지면은 이후 작성 프록시 유형으로
  추가해야 하고 Mesh 이름 예외로 만들지 않습니다.

## 72. 접촉 소유 착지와 작성된 공중 표현

- 지지면 Probe가 감지했다는 것은 작성된 지지면이 가까이 있다는 뜻이지
  CharacterController가 착지했다는 뜻이 아닙니다. 접지는 이제 작성된
  `WalkableSupport` 관찰과 컨트롤러의 현재 접지/`Below` 충돌 결과를 모두
  요구합니다. 지지면 근접만으로 점프를 승인하거나 공중 상태를 끝내거나
  Landing을 시작할 수 없습니다.
- 승인된 점프 발생 한 번이 계속 일시적 표현 생명 주기를 소유합니다. 이동
  상태 해석기는 수직 이동과 충돌 접촉으로 `JumpStart`, `Airborne`, `Fall`,
  `Landing`을 선택하며 이 단계를 영속 Fact로 기록하지 않습니다.
- `Airborne`과 `Fall`은 이제 서로 다른 canonical Manifest 항목으로
  해석됩니다. 현재 첫 슬라이스는 같은 라이선스 원본 클립의 서로 다른 작성
  재생 구간을 재사용하지만 구간 경계, 반복, 전환, Root Motion 모드와 표현
  소유자는 코드 상수나 클립 이름 분기가 아니라 Manifest 데이터입니다.
- `Landing`은 실제 접촉 뒤에만 시작하고 Manifest에 작성된 블렌딩을
  사용합니다. 착지 구간이 완료된 뒤에만 Idle, 이동 또는 장착 Idle을
  선택합니다. 필요한 이동 상태 항목을 제거하면 애니메이션 콘텐츠 검증이
  실패하며 Unity가 오브젝트 이름, 애니메이션 이름, 타이머 또는 근접
  fallback으로 대체하지 않습니다.

## 73. 런타임 월드 재구축 뒤에도 유지되는 ActorProfile 레퍼토리

- 애니메이션 Manifest는 계속 작성 원본이며 런타임 Database와 배정된
  ActorProfile을 동기화합니다. ActorProfile 동기화기는 현재 레퍼토리를
  `ActorProfile` 원본의 `has_animation` 기여분으로 투영합니다. 이는 런타임
  프로필 투영이며 영속 작성 월드 Fact가 아닙니다.
- `OntologyWorldBootstrap`은 씬 구성, 복원 또는 입장 과정에서 런타임 월드를
  교체할 수 있습니다. 프로필 동기화기는 `WorldRebuilt`를 구독하고 교체 뒤
  현재 프로필을 다시 투영하므로 새 canonical 애니메이션이 애니메이션 ID나
  캐릭터 이름 fallback 없이 기존 캐릭터에도 제공됩니다.
- 레퍼토리 제거도 그대로 권위적입니다. 동기화는 이전 ActorProfile 기여분을
  먼저 철회하므로 Manifest/프로필 배정을 제거하면 오래된 클립을 남기지 않고
  해당 런타임 애니메이션 경로를 제거합니다.
## 규칙 블록과 의미 패키지 수명주기

- 할당된 규칙 블록의 식별자는 규칙 이름이나 바인딩 변수가 아니라 Authority의 `bindingId`이다.
- 온라인 편집은 Authority 우선 방식이다. Unity는 명령 대기 중 기존 프로젝션을 유지하고, 승인된 리비전을 받은 뒤에만 화면을 갱신한다.
- 의미 패키지의 트리플·규칙 바인딩 소유권은 정규화되고 리비전 이력을 가진다. 한 바인딩을 제거하면 그 바인딩과 `RuleBound` 결과만 철회하고, 마지막 소유 바인딩을 제거하면 행동 패키지를 닫아 패키지 소유 정규·타입 트리플을 철회하되 독립 기여는 보존한다.
- 행동 패키지는 `requiresOwnedBinding`을 선언한다. Authority는 소유 규칙 블록 없이 행동 트리플만 추가하는 패키지를 거부하며, 데이터 전용 패키지만 명시적으로 예외를 선언할 수 있다.
- 편집기의 결과 화면은 프로젝션된 트리플 출처를 표시하여 패키지 소유·직접 작성·시스템·규칙 결과를 Unity의 추측 없이 구분한다.
- 기존 카탈로그 기여를 채택할 때는 정확히 일치하는 목표 트리플을 교체 대상 철회 전에 소유한다. 채택된 행은 displaced 기준 원장에 들어가거나 마지막 규칙 블록 삭제 후 독립 데이터로 다시 나타나면 안 된다.
## 74. Unity가 소유하는 로컬 충돌 표현

- 온톨로지 데이터와 Physical Meaning은 Unity 물리 설정을 제공하며 대체 충돌 좌표를 계산하지 않는다. LocalCharacterController 프로필은 작성된 최대 단차, 경사 제한, 스킨 폭, 최소 이동 거리 값을 Unity `CharacterController`에 매핑한다.
- 로컬 플레이어의 런타임 충돌·경사·단차 해결은 단일 `CharacterController.Move`가 소유한다. 기존 CapsuleCast·Raycast·Overlap 기반 자체 단차 계산기는 폐기했으며 위쪽 변위를 직접 주입하지 않는다.
- `OntologyCharacterSupportProbe`는 Unity Cast로 주변 `WalkableSupport`를 관측하고 의미를 분류할 뿐이다. 이 결과는 임시 관측 증거이며 Transform을 이동시키거나 Unity 접촉 없이 접지 상태를 만들 수 없다.
- CharacterController는 Rigidbody 중력을 자동으로 받지 않으므로 데이터에서 받은 중력값의 속도 적분은 유지한다. Rigidbody 엔티티는 Physical Profile 어댑터가 설정한 Unity 중력·충돌·감쇠·제약·Physic Material을 사용한다.
- 입력을 열기 전에 수행하는 제한된 1회 월드 입장 접지 정렬은 준비 초기화이며 두 번째 런타임 이동 소유자가 아니다.
휴머노이드 발 접지는 표현 전용이다. 활성 Physical Profile이 탐색·블렌딩
설정값을 제공하고 Unity Physics가 발 접촉점을 제공하며 Animator IK가 보이는
발을 정렬한다. 이 처리는 Actor 루트를 이동하거나 Authority 위치, 접지 상태,
충돌 해결 결과를 변경하지 않는다.

## 75. 재사용 가능한 UGC 근접 무기 의미

- `melee_weapon` 규칙 블록 빠른 설정은 Weapon/Carryable 개념,
  장착·해제·휘두르기·공격 바인딩, 전투 조정 트리플,
  `HandheldWeapon` 물리 의미와 부착 데이터를 하나의 Authority 의미
  패키지로 작성한다.
- `Weapon` 개념과 `attack_contact_mode=WeaponContactWindow`이 투영되면
  Unity는 의미 데이터에서 접촉 조회 프리젠터를 구성한다. 기존 무기
  프리팩은 보정된 접촉 영역을 유지하고, 임의 UGC 오브젝트는 렌더러
  경계로 보수적 접촉 영역을 만든다.
- 자동 생성 접촉 영역은 표현 관찰 증거일 뿐이다. 공격 권한이나 피해를
  직접 만들지 않으며 무기 의미가 제거되면 함께 비활성화된다.

## 76. Authority 투영 기반 플레이어 피격 반응

- PlayerProfile이 `hit_animation_intent=HitReaction`을 작성하고, 프로젝트 소유
  `Standing React Large From Front.fbx`를 Manifest -> Database -> PlayerProfile
  생산 라인을 통해 `Anim_Player_HitReaction_Front`로 등록한다.
- Damageable 프리젠터는 첫 Authority 체력 투영을 기준값으로 삼고, 더
  새로운 Authority 리비전에서 체력이 감소했을 때만 작성된 일시 피격
  의도를 표현한다. 같은 투영 재생, 회복, 사망 전환은 일반 피격 반응을
  추가로 만들지 않는다.
- CharacterController가 플레이어 이동의 단일 소유자이므로 Root Motion을
  비활성화한다. 로컬 접촉 완료 경로는 타격 VFX만 표현하여 Authority
  투영이 소유한 애니메이션을 중복 재생하지 않는다.

## 77. Authority 소유 자율 공격 발생

- 자율 공격 미리 평가는 몬스터에 배정된 Rule Block을 실행하며, 승인되면 스케줄러 틱마다 즉시 피해를 주는 대신 하나의 일시적 `AttackOccurrence`를 만듭니다.
- 작성된 `attack_windup_seconds`, `attack_recovery_seconds` 트리플에 따라 준비, 한 번의 접촉, 회복 단계를 진행합니다. 접촉 시 같은 액션과 Rule Block 경로를 다시 실행해 현재 생존, 적대 관계, 실시간 거리, 재사용 대기시간을 검증한 뒤 영속 피해를 한 번만 적용합니다.
- 승인된 접촉 revision은 즉시 전달됩니다. Unity는 투영된 공격 의도와 체력·사망 결과만 표현하며 접촉 권한이나 피해를 소유하지 않습니다. Rule Block을 제거하면 공격 동작도 제거됩니다.
- revision 알림은 확정 이벤트 ID, 대상 엔티티 ID, 규칙 평가가 만든 피해
  결과 여부를 함께 전달합니다. 일치하는 Damageable 표현기는 이 일시 발생
  건을 한 번만 소비해 작성된 피격 의도를 즉시 재생하며, 체력과 사망 상태의
  최종 기준은 이후 Authority 투영입니다.
- 휴머노이드 사망 클립은 Root Motion을 끈 채 수직/XZ 루트 이동을 포즈에
  굽힙니다. 따라서 CharacterController가 계속 유일한 위치 소유자로 남고
  사망 자세가 공중으로 이동하지 않습니다.

## 78. 생명주기로 제한되는 자율 근접 접촉

- 매 틱 조회하는 Authority 대상 투영이 생명주기의 기준입니다. 이전 설정이
  캐시에 남아 있어도 현재 `is_alive=true` 투영에서 빠진 행위자는 임시 자율
  이동과 진행 중 공격에서 즉시 제거됩니다.
- 자율 근접 접촉은 프리팹 모양이나 넓은 행동 `attack_range`로 추측하지
  않습니다. 몬스터가 `collision_radius`, `collision_height`,
  `attack_contact_reach`를 작성하고 Authority가 공격 시작과 실제 접촉 시점
  모두에서 수직 겹침과 캡슐 표면 도달 여부를 검사합니다.
- 접촉 시 배정된 공격 Rule Block을 다시 평가합니다. 대상이 죽었거나
  사라졌거나 실시간 위치·충돌 의미가 없거나 접촉에서 벗어나면 실패로
  닫힙니다. 사망 결과가 커밋되면 대상의 임시 이동 상태도 즉시 폐기됩니다.
- 가변 `current_health`, `is_alive` 값은 의미 기준선 소유가 아니라 배치 초기화와
  생명주기 상태입니다. 계약 마이그레이션은 이 값을 보존한 채 불변 의미만
  교체하고, Rule 결과가 이미 있으면 덮어쓰지 않으며, 중복 작성본은 제거하고
  행동 규칙이 만든 영속 생명주기 결과를 우선합니다.

## 79. Authority가 소유하는 플레이어 근접 접촉

- 왼쪽 클릭은 의도만 발행하고 일시적인 플레이어 `AttackOccurrence` 하나를 요청합니다. Unity가 직접 영속 피해를 실행하지 않습니다.
- 불변 공격 액션은 Authority 공격 발생을 명시적으로 요구합니다. 접촉 해결이 끝난 동일 발생 ID가 없는 일반 액션 요청은 실패하므로 Unity 접촉, 애니메이션 시각 또는 변조된 명령이 배정 Rule Block을 우회할 수 없습니다.
- 무기 트리플은 접촉 시작 시각, 접촉 창 길이, 도달 거리, 피해, 사거리, 재사용 시간을 작성합니다. 해당 창에서 Unity는 투영된 대상 후보만 보고하며 Authority가 현재 행위자·도구·대상 ID, 장착, 진영 관계, 생명주기, 실시간 위치와 작성된 캡슐 접촉을 다시 검증한 뒤 발생을 정확히 한 번 소비합니다.
- 현재 계약의 영속 피해는 정수 체력 포인트 Rule 결과입니다. 소수 또는 모호한 수치 조정은 Unity나 전송 코드에서 반올림하지 않고 검증에 실패합니다.
- 공격 Rule Block, 발생 요구, 접촉 트리플, 명시적 접촉 프록시, 살아 있는 대상 자격 또는 진영 관계 중 하나를 제거하면 렌더러·프리팹·이름 기반 fallback 없이 공격 결과도 제거됩니다.

## 80. Authority가 평가하는 공격 재생 속도

- 무기는 숫자 Triple `attack_playback_speed`를 작성하고, 배정된 휘두르기 Rule Block이 이 Triple을 표현 속도 출처로 선언합니다. Authority가 블록을 평가한 뒤 승인된 속도를 `AttackLight`와 함께 전달합니다.
- Animation Manifest는 중립적인 `1.0x` 기본 속도와 정규화된 접촉 구간만 유지합니다. Unity는 무기 Triple을 직접 읽지 않고 Authority가 승인한 값만 선택된 클립 Playable에 곱합니다.
- 휘두르기 Rule Block이나 필수 속도 Triple을 제거하면 이름 기반 대체 없이 가속 공격도 제거됩니다.
# 82. Authority 재시작 뒤 임시 아바타 복구

- 영속 월드 입장은 유효하지만 Authority 또는 Redis 재시작으로 플레이어의
  임시 런타임 아바타만 사라질 수 있습니다. 이때 장비 거리 판정, 몬스터 타깃
  선택, 근접 접촉 판정은 복구 전까지 fail-closed 상태를 유지합니다.
- 클라이언트는 완료된 입장 흐름이 활성화한 아바타와 Zone만 기억하며, 세션
  하트비트나 런타임 위치 조회 시 아바타가 없을 때만 영속 체크포인트에서
  재활성화합니다. 정상 아바타를 반복 초기화하지 않습니다.
- 이 복구는 작성 Triple을 만들지 않으며 Rule Block, 거리, 생명주기, 접촉
  검증을 우회하지 않습니다.

## 83. 결정적인 런타임 정의 선택과 전투 생명주기 투영

- 발행된 불변 정의의 과거 이력은 보존하지만, 월드 런타임은 하나의 활성
  패키지 안에서 액션별 가장 높은 발행 정의 버전 하나만 선택합니다. 과거
  버전이 스케줄러 후보를 증식시키면 안 되며, 한 액터에 완전한 활성 패키지가
  둘 이상이면 계속 모호성으로 보고 fail-closed 처리합니다.
- 자율 액터 자격은 현재 Triple, 배정 Rule Block, 활성 패키지, Physical
  Meaning, 활성 생명주기 투영으로 다시 구성합니다. 죽었거나 계약이 불완전한
  액터는 일시적인 이동·공격 occurrence를 잃습니다.
- Unity 포인터 대상 선택은 현재 투영에서 살아 있는 대상만 순회합니다. 죽은
  표현 객체는 자신이 소유한 충돌체를 모두 비활성화하여 이후 전투 입력을
  가로막지 않으며, 생명과 피해 상태는 계속 Authority가 소유합니다.
- 장착 표현은 투영된 `equipped_by` 관계를 따릅니다. 작성된 슬롯이 차 있으면
  Unity는 그 투영 아이템에 활성화된 장착 해제 액션을 표시하며 암묵적인 교체
  규칙을 만들지 않습니다.
- 충돌 해결 위치 관찰은 승인된 활성 이동 Intent가 존재할 때만 전송합니다.
  정지 또는 만료 Intent에는 이후 pose 표본을 보내지 않아 거절된 관찰과 오래된
  전투 접촉 근거가 남지 않게 합니다.
## 84. 자율 몬스터의 플레이어 접촉은 최신 이중 위치 증거를 요구한다

- 플레이어가 정지 중이어도 설정된 주기로 임시 이동 lease를 갱신하여
  Authority 이동 상태와 충돌 해결 위치 관찰이 만료되지 않게 한다.
- 플레이어 이동 설정도 자율 전투 설정과 같이 하나의 활성 패키지 안에서
  가장 높은 발행 locomotion Action 버전을 선택한다. 불변 이력 때문에
  활성 아바타가 시뮬레이션에서 빠져서는 안 된다.
- 자율 근접 공격이 플레이어에게 피해를 확정하려면 occurrence의 접촉
  시점에 Authority 이동 캡슐과 최신 Unity 충돌 해결 위치 관찰이 모두
  접촉 범위 안이어야 한다.
- Unity 위치 관찰은 권한 위치가 아니다. 오래됐거나 떨어진 접촉을
  거절할 수만 있으며 Authority 이동 상태나 영속 데이터를 덮어쓰지
  않는다.

## 85. 온톨로지 런타임 성능 증거 경계

- 런타임 최적화는 의미 우회가 아니라 측정 지표에서 시작한다. 규칙 평가는
  결과를 바꾸지 않고 평가·건너뜀 규칙 수, 반복 수, 소요 시간을 기록한다.
- Headless Zone 런타임은 입력 엔티티·Fact·바인딩·컴파일·반복 수를 기록한다.
  active와 reduced Zone은 각각 작성된 1초·5초 주기를 실제로 지키며 reduced
  모드가 암묵적으로 매초 평가되면 안 된다.
- Authority Projection 행은 수신 Projection마다 엔티티와 subject 기준으로
  한 번 인덱싱한다. 이 조회 인덱스는 capability를 추론하거나 빠진 Rule
  Block을 보완하지 않으며 재구축 시 이전 Projection 행을 철회한다.
- 현재 장비에서 엔티티 1,000개, 규칙 100개, 작성 Fact 100,100개의 대표
  측정은 인덱싱된 규칙 평가 내부 0.426 ms, 전체 테스트 286 ms였다. 따라서
  다음 조사는 안정화 단계 평가기가 아니라 월드·snapshot 구성, 규칙
  역직렬화·컴파일, Projection 동기화 범위로 제한한다.
- 지속 런타임 계약 캐시는 아직 이 증거만으로 승인하지 않는다. 다음 진입
  조건은 서버 snapshot 조회 시간, 정의 컴파일 시간, cache hit/miss,
  revision·package 무효화의 실측이다.

## 86. 요청 범위 Authority 평가 Snapshot

- Action 성능 지표는 제한된 `call.kind`와 고정된
  `prepare_action_evaluation` 범위만 사용한다. 원본 UGC Action ID는 무제한
  시계열과 telemetry DoS 위험이 있으므로 metric tag로 사용하지 않는다.
- 엔티티 1,000개, Fact 100,000개, 규칙 100개, 동시 Action 20개의 기존
  배치는 8,495 ms였고 Action 평가 p95는 6,383 ms였다. transport와 invoked
  Rule이 요청 범위 읽기 전용 평가 Snapshot 하나를 재사용한 뒤 배치는
  6,236 ms, 순수 평가 p95는 27.998 ms로 감소했다.
- Snapshot은 `PrepareActionEvaluation` 요청마다 한 번 만들고 월드 revision
  사이에 공유하지 않는다. 승인이나 mutation 결과를 캐시하지 않으며 호출별
  effect overlay와 임시 canonical intent는 평가 뒤 제거된다. Rule 제거 뒤
  새로 만든 Snapshot은 fail-closed 처리된다.
- 남은 실측 병목은 요청마다 Fact 100,000개의 전체 Snapshot을 컴파일하는
  단계이며 p50은 약 3,498 ms다. matcher가 비변경 intent overlay를 사용하고
  Authority 게시가 PostgreSQL revision 기반 다중 인스턴스 fence를 갖추기
  전에는 revision 범위 지속 캐시를 도입하지 않는다.
- Headless Zone 입력은 하나의 Repeatable Read transaction에서 월드 revision과
  불변 binding identity를 함께 복사한다. transaction 종료 후 평가하며 revision이
  바뀌면 추론 결과를 폐기하고 마지막 완료 Snapshot을 유지한다.
- 엔티티 1,000개, Fact 100,000개, binding 100개의 Projection 인덱스 구성은
  79.306 ms였다. 현재 Unity Editor에서 thread allocation 값이 0을 반환했으므로
  allocation은 최적화 성과가 아니라 명시적인 측정 공백으로 남긴다.

## 87. 불변 평가 오버레이와 발행 펜스

- 정규 입력 Intent는 요청 로컬 오버레이로 매칭하며 공유 월드 Snapshot에
  추가하거나 제거하지 않는다. 동시 Action 평가 간 Intent가 누출되지 않고
  전역 matcher 잠금도 필요하지 않다.
- 하나의 명령 범위 provenance 보존 오버레이가 성공한 주 효과와 후속 Rule
  변이를 순서대로 전달한다. Assert, Retract, Set, Adjust, 역방향 효과에서 원시
  기여 개수, 원본 Rule Binding, 결과 수명을 유지한다.
- 후속 Rule 평가는 더 이상 전체 Authority Snapshot을 다시 읽지 않는다. Fact
  100,000개에서 후속 Rule 0개, 1개, 4개 모두 준비 Snapshot 1회, 후속 재로딩
  0회였다. 워밍업 후 Snapshot 컴파일은 각각 610.753ms, 422.798ms,
  562.736ms였고 4개 Rule 체인은 0.210ms였다.
- Headless Zone 발행은 월드 revision, 평가 완료 시각, 관측 시각 순서의 원자적
  compare-and-set 펜스를 사용한다. 발행 직전에 PostgreSQL revision을 다시
  확인하므로 오래된 평가기가 더 최신의 완료 Snapshot을 덮을 수 없다.
- 필수 후속 Rule 실패는 쿨다운 획득 전에 처리되고 영속 변이를 롤백한다.
  다만 쿨다운 획득 후 최종 commit 전에 발생하는 극단적 실패는 registry에
  예약 취소 API가 없어 외부 lease가 TTL까지 남을 수 있다.
- 명령마다 수행하는 전체 Snapshot 컴파일이 여전히 지배 비용이다. 다음 후보는
  revision 범위 불변 계약 캐시이지만 월드 revision과 패키지 ID로 무효화하고
  Rule 제거 시에도 fail-closed해야 한다.

## 88. 정확한 revision 컴파일 계약과 명령 delta

- Authority는 불변 컴파일 평가 Base만 캐시한다. 정확한 키에는 월드 ID, 월드
  revision, 평가기 schema version, 활성 패키지 전체와 발행 정의 checksum을
  canonical하게 구성한 SHA-256 ID가 포함된다. 이전 revision이나 호환 패키지로
  fallback하지 않는다.
- cache miss 빌드는 독립 connection과 Repeatable Read transaction에서 수행한다.
  키와 Fact 행은 같은 DB Snapshot에서 읽는다. 호출자가 관측한 키와 완료된
  빌드는 다시 일치해야 하며, waiter 하나의 취소는 공유 single-flight 빌드를
  취소하거나 제거하지 않는다.
- 바인딩된 Rule 조회는 바인딩에 기록된 정확한 활성 package ID/version에 속한
  Rule 정의만 허용한다. 비활성 또는 무관한 패키지의 발행 Rule은 게임 계약을
  충족할 수 없다.
- 명령은 캐시 Base를 변경하거나 복제하지 않는다. 변경된 subject-predicate 키의
  raw row와 semantic addition/tombstone만 보관한다. 주 효과와 순서화된 후속
  Rule은 같은 명령 로컬 delta를 읽으며 provenance, raw cardinality, 결과 수명,
  Rule Binding projection을 유지한다. rollback 시 delta 전체를 폐기한다.
- 프로세스 로컬 캐시는 single-flight이며 항목 수와 보수적 추정 보존 byte로
  제한된다. overflow key도 별도의 제한된 single-flight 표를 사용하고 전체
  빌드 파이프라인은 프로세스 단위 동시성 상한을 갖는다. pending key 상한을
  넘으면 무제한 DB 대기열을 만들지 않고 `action_evaluation_backpressure`로
  fail-closed한다. metric은 고정 이름만 사용하며 월드·패키지·Action ID를
  tag로 쓰지 않는다.
- Fact 100,000개에서 cold compile 464.556ms, 정확한 키 read hit 15.742ms,
  delta를 통한 첫 committed mutation 4.902ms로 측정됐다. 이전 약 762ms의 전체
  copy-on-write 재구축은 제거됐다.

## 89. 컴파일 계약 운영 수명과 메모리 경계

- 공유 계약 빌드는 개별 요청이 아니라 서비스가 소유한다. 호출자 취소는 해당
  waiter만 중단한다. Application stopping은 별도의 종료 의미로 공유 owner를
  취소하고, 설정 가능한 빌드 timeout은 기본 30초이며 Action을
  `action_evaluation_timeout`으로 거절한다.
- 취소는 DB 읽기, source 복사, 월드 compile, retained-memory 추정까지 전달된다.
  큰 반복문은 owner token을 주기적으로 확인하므로 100,000 Fact 전체 compile이
  끝날 때까지 기다리지 않고 timeout과 종료 정리를 시작할 수 있다.
- retained-memory 추정에는 source record/string, raw provenance row의
  dictionary/list/array, 컴파일 월드의 entity, Fact, origin, predicate,
  changed-predicate, concept 인덱스가 포함된다. 악의적 입력에서도 overflow하지
  않도록 포화 연산하며 compile 중 한 번만 계산한다.
- 단일 계약이 캐시 byte 한도를 넘으면 현재 waiter에는 결과를 반환하지만
  resident로 보존하지 않는다. resident count/bytes는 0으로 돌아가고 oversized
  bypass로 기록된다. overflow pending-key metric은 실제 의미가 이름에 명시되며
  MeterListener 테스트가 resident, byte, pending, oversized 계측 균형을 검증한다.
- 종료, timeout, 실패, overflow, oversized admission, 빌드 정리 중 Dispose
  경로 모두 single-flight identity를 유지하고 pending key와 동시성 permit을
  반환한다.

## 90. 활성화 세션 단위 플레이어 이동 보정

- 플레이어 런타임을 활성화할 때마다 서버가 불투명한 `RuntimeSessionId`를 새로
  생성한다. 이동 상태, 이동 Intent, 런타임 Action Intent, 충돌 해결 위치 관찰은
  모두 같은 세션 식별자를 가진다.
- 입력 sequence는 한 런타임 세션 안에서만 단조 증가한다. Unity는 Snapshot 세션이
  현재 세션과 같고 `LastProcessedIntentSequence`가 마지막 승인 입력까지 처리된
  경우에만 위치를 보정한다. server Tick만 새롭다는 이유로 보정하지 않는다.
- 새 입력이 승인되면 이전 입력을 기준으로 남아 있던 평면 위치 보정을 즉시
  폐기한다. 따라서 정지한 뒤 늦게 도착한 이동 상태가 플레이어를 뒤로 끌지 못한다.
- Authority 이동 발행은 런타임 세션과 server Tick을 함께 비교하는 CAS를 사용한다.
  이전 활성화의 실행 중 Tick은 새 활성화 상태를 덮어쓸 수 없다.
- 일반 영속 체크포인트 저장은 실행 중인 이동을 재시작하지 않는다. 리스폰·복구처럼
  런타임 위치를 다시 심을 때만 새 활성화를 수행하고 Unity 보정 경계를 초기화한다.

## 91. 콘텐츠 릴리스·월드 준비·입장 단계 분리

- 불변 Rule과 Action 정의는 하나의 원자적 콘텐츠 릴리스로 함께 발행한다. 충돌하면
  릴리스 전체를 롤백한다. 실제 월드 입장은 작성 콘텐츠를 발행하거나 활성화하지 않는다.
- 입장은 활성 패키지와 로컬 Rule/Action의 canonical payload, 아바타 의미 계약
  manifest를 읽기 전용으로 검사하는 단계에서 시작한다. canonical payload가 다르면
  같은 패키지·정의 ID만으로 준비 완료로 인정하지 않는다.
- 월드 생성 또는 소유자의 명시적 준비 작업이 Zone 기반을 작성하고,
  `prepare_player_avatar` 명령 하나로 아바타 엔티티 생성·소유권 등록·의미 계약 적용을
  하나의 revisioned·멱등 Authority 트랜잭션에서 처리한다.
- 프로필 최종 확인의 실행 오케스트레이터는 편집 가능한 기존 월드에 대해 이 명시적
  멱등 준비를 먼저 수행한 뒤 입장을 호출한다. 이 준비는 `EnterRoutineCore` 밖에
  유지하며, 읽기 전용 방문자에게 실행 과정에서 월드 작성 권한을 부여하지 않는다.
- 기존 월드 아바타 ID는 Authority 계정 대시보드의 사용자·월드 등록 관계에서 가져온다.
  Unity는 계정 캐릭터 ID, 씬 GUID, 프리팹 또는 다른 월드에서 캐시한 ID로 이를 추론하거나
  교체하지 않는다. 선택한 월드에 등록된 아바타가 아직 없으면 불변 씬 seed와 월드 ID로
  결정론적인 월드 범위 ID를 생성한다.
- 의미 계약 준비 완료는 정확한 활성 Application·Slot·Contract와 모든 소유 Fact 및
  Rule Binding의 해제되지 않은 ownership 행을 요구한다. 독립적으로 같은 기여가
  존재하는 것만으로 준비 완료를 가장할 수 없다.
- 일반 입장에서는 콘텐츠 발행, Zone·엔티티 생성, 레거시 마이그레이션, 의미 계약
  복구를 수행하지 않는다. 보류 명령 복구는 별도 복구 경계이며, 리스폰 Rule 평가와
  충돌 보정 체크포인트 확인은 명시적인 입장 소유 게임 동작으로 유지한다.
- 런타임 활성화는 일시적이고 세션 단위이다. 이후 입장에 실패하면 그 입장이 만든
  정확한 세션만 해제한다. 영속 `/entry` 바인딩은 모든 준비가 성공한 뒤에만 확정한다.
- 입장 전 생명·리스폰 검사, 무이동 이동 계약 handshake, 충돌 보정 체크포인트 확인은
  해당 아바타의 정확한 임시 런타임 세션 활성화를 요구한다. 영속 입장 바인딩까지
  확정됐다는 뜻의 `IsWorldRuntimeReady`를 더 앞선 입장 검사 조건으로 사용하지 않는다.
- 개발 검증은 서비스 기반 실행 전에 불변 릴리스 manifest, 입장 경로의 작성 명령
  부재, DB 마이그레이션 전체 적용 상태를 확인한다.
- 서비스 기반 검증은 현재 World Authority 이미지를 실제로 배포하고 입장 사전검증
  경로까지 확인한다. 상태 확인만 성공하는 오래된 컨테이너는 콘텐츠 불일치가 아니라
  배포 계약 실패이며, 이전 API로 우회하거나 입장을 허용하지 않는다.

## 92. 분리된 원격 멀티플레이 테스트 배포

- 최초 원격 멀티플레이 검증은 전용 `tormia_test` PostgreSQL 데이터베이스와
  최소 권한의 `tormia_test_app` 계정을 사용한다. 기존 서비스의 데이터베이스,
  프로세스, Nginx 가상 호스트는 이 배포 경계 밖에 둔다.
- World Authority 컨테이너는 `127.0.0.1:5272`에만 바인딩한다. 외부 요청은
  독립된 `tov-api.punkarena.app` Nginx 가상 호스트를 통해서만 들어온다.
- RDS 관리자 자격 증명은 초기 생성 단계에서만 사용한다. 데이터베이스 생성과
  마이그레이션 후 원격 임시 파일을 삭제하고, 실행 서비스에는 앱 계정 정보만 남긴다.
- Unity는 로컬과 원격 Authority 주소를 모두 유지한다. 설정 자산의 에디터 전환값으로
  플레이 모드와 콘텐츠 작성 도구가 HTTPS 테스트 Authority를 사용하게 할 수 있으며,
  Android는 항상 원격 테스트 주소를 선택한다. DB나 Redis 자격 증명은 포함하지 않는다.
- Android 외부 테스트 전에는 테스트 호스트의 DNS 연결과 신뢰 가능한 TLS 인증서
  설치가 완료되어야 한다.
- 초대 월드 입장은 선택한 월드의 명시적인 활성 콘텐츠 패키지를 사용한다. 최초
  입장 시 아바타 시드, 월드, 인증 사용자를 함께 반영한 ID로 Authority에 멤버
  아바타 생성을 요청하며 기존 아바타 ID는 보존한다.
- 원격 멀티플레이는 Nginx의 일반 REST와 SignalR 프록시 경로를 분리하고, 연속된
  Zone 알림을 합친 뒤 아바타 스냅샷을 읽는다. 하나의 아바타는 하나의 활성 조작
  세션만 가지므로 여러 장치 테스트에는 서로 다른 계정을 사용한다.
# 94. 하이브리드 실시간 전송 기준선

- HTTPS와 SignalR은 신뢰성 있는 제어·복구 경로로 유지한다. UDP는 고빈도 이동
  intent와 Authority motion snapshot만을 위한 교체 가능한 후속 경로다.
- 전송은 게임 권한을 소유하지 않는다. 모든 이동 패킷은 활성 런타임 세션과
  평가된 이동 계약 범위 안에서만 처리된다.
- UDP를 활성화하기 전에 현재 기준선을 계측한다. Authority는 플레이어 이동
  Tick 시간·초과·활성 아바타·프레임 항목과 SignalR 발행 횟수·항목·시간·실패를
  기록한다. Unity는 재접속, 프레임 수신, stale·역순 snapshot, snapshot age,
  보간 underrun과 제한 외삽 발생을 기록한다.
- 특정 기술 가정이 아니라 측정 증거가 단계 전환을 결정한다. SignalR과 HTTP는
  fallback 및 complete recovery 경로로 유지한다.

## 95. 하이브리드 UDP 전송 기술 선정

- Unity와 .NET 8 Authority의 첫 UDP 이동 수직 슬라이스는 LiteNetLib
  2.1.4를 정확한 버전으로 고정한다.
- LiteNetLib는 신원, 규칙, 게임 결과, 영속 상태, 복구 경로를 소유하지
  않는다. HTTPS가 전송 입장을 발급하고 SignalR은 완전한 fallback으로 남는다.
- Unity Editor, Android IL2CPP, Linux .NET 8, 인증, 재전송 방지, 손실, 역순,
  재연결, fallback, 분리 배포 증거가 통과해야 UDP를 활성화한다.

## 96. Authority 소유 UDP 전송 입장

- 인증된 HTTPS는 계정 소유 아바타의 정확한 활성 런타임 세션에 짧은 수명의
  UDP ticket 하나를 발급한다. generation은 Authority가 배정한다.
- 사용 시 nonce 결합 HMAC 증명이 필요하다. Redis는 런타임 세션과 Zone을 다시
  확인하고 ticket을 한 번만 소모하며 짧은 인증 전송 handshake를 원자적으로
  승격한다. 키 데이터는 AES-GCM으로 보호한다.
- UDP는 기본 비활성이며 Redis, 키 보호, 신뢰 프록시 HTTPS, 멀티인스턴스 지원이
  없으면 실패 폐쇄된다. 런타임 비활성화는 일시 전송 범위를 모두 철회한다.
- ticket 입장은 게임 권한이나 영속 온톨로지 상태를 만들지 않는다. 수신기,
  재전송 방지 window, 단일 writer fence는 아직 활성화 조건으로 남는다.

## 97. Authority UDP 리스너 보안 경계

- LiteNetLib Authority 리스너는 기본 비활성이며 정확한 고정 부트스트랩과
  인증된 `Unreliable` 채널 0 이동 데이터그램만 받는다. 이 단계에서는 Docker나
  운영 서버의 UDP 포트를 노출하지 않는다.
- 패킷은 제한된 구조 검증, 활성 세션과 정확한 세대 확인, 상수 시간 HMAC,
  원자적 재전송 창 소비, 페이로드 해석과 결합 확인, 전달 직전 두 번째 세대
  확인 순서로 처리한다.
- 인증된 이동 의도는 격리된 제한 큐에만 들어간다. 아직
  `PlayerIntentRegistry`, 규칙 평가, 게임 상태, 영속 저장에는 연결하지 않는다.
- 주소, 대기 핸드셰이크, 교환, 조회, 큐 용량은 초과 시 닫힌 상태로 실패한다.
  종료, 런타임 비활성화, 티켓 재발급, 오래된 세대는 전송 권한을 철회하고
  보관 중인 비밀값을 지운다.
- HTTPS와 SignalR은 제어, 대체 경로, 완전 복구 경로로 유지한다.

## 98. Unity UDP 이동 송신 준비

- Unity는 인증 HTTPS로 Authority UDP 티켓을 요청하고 정확한 고정 부트스트랩과
  인증 이동 데이터그램 계약을 만들 수 있다.
- 어댑터는 기본 비활성이다. `IPlayerMotionIntentTransport` 진입점은 아직 HTTP로
  위임하므로 Authority 소비와 승인 응답을 통합하기 전까지 활성 게임 Writer는
  정확히 하나다.
- 입장은 컴포넌트 수명과 정확한 런타임 세션, 월드, 아바타, Zone 결합으로
  차단한다. 비활성화, 재입장, 시간 초과, 연결 해제, 결합 변경은 작업을 무효화하고
  보관한 바이트 배열 비밀값을 지운다.
- Unity 어셈블리는 LiteNetLib 참조를 명시적으로 고정한다. Android IL2CPP,
  외부망, 할당량 증거는 이후 활성화 조건으로 남는다.

## 99. 공용 Authority 이동 입장

- HTTP와 인증 UDP 이동 후보는 하나의 Authority 입장 서비스와 하나의 고정 Tick
  intent 레지스트리로 들어간다. 전송 계층은 이동 규칙을 선택하거나 소유하지 않는다.
- 입장은 소유권, 정확한 런타임 세션과 Zone, 완전한 작성 이동 의미, 유일한 활성
  action과 Rule binding, 영속 변경이 없는 Rule 미리보기, 현재 월드 revision,
  단조 증가 sequence를 검증한다.
- 런타임 세션, UDP 세대, revision pending/exact 상태, 활성 Writer는 intent 저장과
  원자적으로 확인한다. UDP 승계 후에는 이후 명시적 fallback 전환 전까지 HTTP와
  이전 세대를 차단한다.
- Rule 변경은 영속 커밋 전에 pending을 기록하고 정확한 커밋 revision 확인 뒤에만
  해제하는 2단계 fence를 사용한다. 장애 구간 복구는 실패 폐쇄, 월드별 단일 조회,
  제한된 대기자와 backoff를 사용한다.
- 컴파일된 입장 계약은 용량 제한과 revision 키를 사용한다. Rule Block 제거 뒤
  이전 캐시 승인은 사용할 수 없다. UDP snapshot과 Unity Writer 활성화는 이후
  단계로 남는다.

## 100. Authority UDP Zone 이동 스냅샷

- UDP 이동 스냅샷은 이미 승인된 Authority 고정 Tick Zone 프레임에서만 파생되는
  교체 가능한 표현 분기다. Rule을 평가하거나 게임 상태를 변경하지 않으며 기존
  SignalR 발행을 대체하지 않는다.
- SignalR과 UDP는 복합 발행 경계에서 한 번 생성한 동일한
  `FrameOccurrenceId`를 받는다. Redis는 UDP fan-out backplane일 뿐이며 원본
  프레임 식별자나 Tick을 다시 쓰지 않는다. Redis 또는 backplane 장애는 UDP
  작업만 버리거나 재시도하며 Authority 시뮬레이션, HTTP, SignalR은 독립적으로
  계속 동작한다.
- 프레임은 엔티티 수, 보관 바이트, 실제 1000바이트 데이터그램 한도로 제한한다.
  프로토콜 v2는 occurrence ID, 페이지 번호와 수, 전체 항목 수, actor별 서버
  Tick을 인증한다. 고정 Tick 프레임은 변경된 actor의 delta만 포함할 수 있으므로
  제한된 입력 큐는 승인한 occurrence를 도착 순서대로 보존하고, 포화 시 가장 새로
  들어온 occurrence를 버린다. 같은 Zone의 앞선 대기 delta를 덮어쓰지 않는다.
- 수신자는 제한된 일괄 조회로 정확한 현재 전송 세대를 다시 검증하고, 로컬 peer와
  세션을 한 번 더 확인한 뒤 peer별 HMAC과 서버 소유 packet sequence를 Unreliable
  채널 0으로 보낸다. 취소할 수 없는 세대 조회가 시간 초과되면 실제 작업이 끝날
  때까지 용량 lease를 유지한다.
- 이 단계에서는 Unity 스냅샷 소비자를 활성화하지 않는다. 클라이언트 검증이 끝날
  때까지 HTTPS와 SignalR이 완전한 대체·복구 경로다.

## 101. Unity UDP 이동 스냅샷 수신

- UDP 스냅샷 수신은 UDP 입력 송신과 별도 플래그로 제어한다. 둘 다 기본
  비활성이며 수신 준비를 켜도 두 번째 이동 intent Writer가 생기지 않는다.
- 입장 부트스트랩은 outer frame 버전 1을 유지하고 ticket과 realtime wire는
  프로토콜 v2를 협상한다. Unity는 채널, 전송 방식, 구조, 정확한 전송 세션과
  세대, HMAC, 64-packet replay window, 월드, Zone, 현재 Authority 런타임 결합
  순서로 검증한다.
- 페이지는 occurrence 수, 페이지·항목 상한, 보관 바이트, 수명으로 제한한다.
  역순 페이지는 완성될 수 있지만 누락·중복·불일치·오래됨·잘못된 페이지 집합은
  표현 계층에 전달하지 않는다.
- 완전히 조립되고 인증된 occurrence만 전송 중립 이동 feed로 들어간다. feed는
  `FrameOccurrenceId`로 SignalR과 UDP 중복을 제거하고 actor별 런타임 세션과
  서버 Tick으로 순서를 정한다. Transform을 직접 변경하거나 게임 권한을 추론하지
  않는다.
- 신뢰 가능한 SignalR 또는 정확한 HTTP 복구만 actor 런타임 세션 장벽을 만들거나
  교체할 수 있다. Zone 전체 복구는 누락 actor를 제거하며, 캡처한 scope, reliable
  epoch, 서버 Tick, 갱신 시간이 늦은 HTTP 응답의 최신 세션 되감기를 막는다. UDP는
  신뢰 경로가 이미 확인한 장벽만 전진시킬 수 있다.
- Unity 컴파일에는 새로운 C# 오류가 없다. 공식 MCP 테스트 실행기가 이전의
  진행률 0인 `tests_running` 작업을 계속 보관하고 있어 자동 PlayMode 실행은
  보류 상태이며, 추가한 테스트를 실행 완료 증거로 주장하지 않는다.

## 102. 명시적 Authority 이동 writer 전환

- 런타임 활성화는 Authority 소유 HTTP writer를 만들고 mode, epoch, 정확한
  월드 revision을 반환한다. UDP가 꺼져 있거나 티켓을 요청하지 않아도 HTTP
  이동은 사용할 수 있다.
- 티켓 발급·교환·peer 연결은 전송 신원만 준비하며 게임 입력 writer를
  승격하지 않는다. 인증된 HTTPS `udp/promote` 전환만 HTTP writer를 정확히
  교환된 UDP session과 generation으로 변경할 수 있다.
- HTTP intent는 Authority가 발급한 writer epoch를 포함한다. UDP intent의
  epoch는 정확한 활성 transport session과 generation에서 조회한다. 최종
  registry commit은 runtime session, Zone, 사용자·아바타 범위, revision,
  writer mode·epoch, UDP 결합을 원자적으로 다시 검증한다.
- UDP가 활성 writer인 동안 티켓 발급은 `udp_rekey_requires_fallback`으로
  거절한다. 따라서 재키는 UDP에서 HTTP로 명시적 fallback한 뒤 새 티켓을
  발급해야 하며, 11단계 계약은 UDP-to-UDP writer 교체를 허용하지 않는다.
- 교환된 handshake 기록과 정확한 연결 peer presence는 서로 다른 일시적
  기록이다. datagram과 snapshot 승인은 연결 기록을 요구하며, 연결 종료는
  presence만 제거해 정확한 현재 UDP writer의 신뢰성 있는 fallback은 유지한다.
- 인증된 HTTPS `http/fallback` 전환은 UDP intent lease, 승격 결합, 미사용
  후보를 원자적으로 철회하고 generation fence를 전진시킨 뒤 더 새 HTTP
  writer epoch를 만든다. ACK 재시도는 멱등이며 오래된 session, generation,
  epoch, revision은 실패 폐쇄된다. 승인된 intent commit은 epoch를 바꾸지 않고
  writer가 관측한 월드 revision을 갱신하며 Authority pending/current revision
  fence는 계속 적용된다.
- fallback은 티켓 발급 당시 revision이 아니라 현재 Authority revision에 맞춰
  조정한다. 따라서 정확한 현재 UDP 결합은 이후 월드 편집이 있어도 HTTP로
  복귀할 수 있으며 오래된 session, binding, writer epoch는 계속 실패 폐쇄된다.
  승격이 실패해 HTTP가 여전히 정확한 현재 writer이면 fallback은 epoch를
  유지하고 후보 전송 상태를 정리하며 Authority writer 증거를 반환하는 멱등
  복구로 동작한다.
- 멱등 전환 성공과 거절 증거는 world, user, avatar, Zone, runtime 전체 범위가
  일치해야 한다. HTTP endpoint는 필터링된 전환 결과를 범위 확인 없는 raw
  writer 조회로 덮어쓰지 않는다.
- writer 전환은 일시적 전송 권한일 뿐이다. Triple, Rule 결과, 영속 이벤트,
  이동 허용 또는 Unity Transform을 만들지 않는다.

## 103. 결정론적 Authority UDP 장애 경계

- 인증된 UDP 이동 장애 테스트는 데이터그램 인증과 replay 승인부터 제한된
  consumer, canonical 이동 승인, 공용 intent registry까지 서버 전체 경로를
  실행한다. 패킷 손실은 없는 입력을 만들지 않고 제한 범위 역순 도착은 sequence를
  되감지 않으며 replay·너무 오래된 패킷과 HTTP fallback 전에 대기하던 패킷은
  이후 commit되지 않는다.
- consumer는 호스팅 루프와 테스트가 함께 사용하는 제한된 결정론적 drain 경계를
  제공한다. 이 경계는 두 번째 writer나 게임 동작을 만들지 않으며 기존 production
  승인 경로를 wall-clock 대기 없이 제어할 수 있게만 한다.
- Redis 티켓 만료는 backend 공통 계약 하나를 사용한다. 만료 뒤 첫 교환은 티켓을
  원자적으로 소비하고 `Expired`를 반환하며 이후 replay는 모두
  `AlreadyRedeemed`를 반환한다. 만료된 자격 증명은 데이터그램 인증 키를 절대
  반환하지 않는다.
- Redis 연결 세대 확인은 peer별 순차 hash 조회나 KEYS/ARGV가 무제한 커지는
  단일 호출 대신 제한된 Lua chunk를 사용한다. chunk 상한은
  `Realtime:UdpMaximumGenerationBatchSize`로 설정하며 기본값은 generation 조회
  동시성 상한과 같다. 각 결과는 world, user, avatar, Zone, runtime session,
  transport session, generation, protocol 전체 결합을 계속 비교하고 실패하거나
  잘못된 chunk는 독립적으로 완료된 다른 chunk를 버리지 않은 채 실패 폐쇄한다.
- Redis 통합 테스트는 `TORMIA_TEST_REDIS_CONNECTION`을 지정한 경우에만
  실행한다. 연결 문자열은 격리된 비기본 데이터베이스를
  `defaultDatabase=1` 이상으로 명시해야 한다. 서로 다른 multiplexer 두 개와
  GUID 범위 데이터, 정확한 키 정리만 사용하며 `FLUSHDB`는 사용하지 않는다.
  동시 중복 교환, 재발급 대 승격, 제출 대 HTTP fallback 경쟁 테스트로 오래된
  generation과 오래된 UDP writer가 전환 뒤 공유 이동을 기록하지 못함을 검증한다.
- UDP 진단은 `writer_mismatch`와 `connected_presence`를 제한된 reason label로
  보존해 신원이나 월드 범위를 로그로 남기지 않고도 전송 배포 장애를 구분한다.
  generation fence batch 횟수·크기와 제한된 outcome label은 월드별 카디널리티
  없이 capacity, timeout, 잘못된 결과, 실패 상태를 보여준다.

## 104. Linux x64 UDP 컨테이너 준비

- World Authority 이미지는 `linux-x64` 대상으로 명시적으로 복원·게시하며
  ASP.NET 기반 이미지의 비루트 애플리케이션 사용자로 실행한다. TCP 8080과
  UDP 5273은 이미지 메타데이터이고, 13단계 검증에서는 TCP만 호스트에
  매핑한다.
- 이미지 health check는 추가 네이티브 패키지 없이 로컬 TCP `/health`를
  사용한다. `/health/realtime`은 자격 증명을 노출하지 않고 신뢰성 backplane,
  UDP ticket·listener gate, listener port, ticket-store backend를 보고한다.
- 두 UDP gate의 기본값은 비활성이다. 명시적인 단일 인스턴스 Development가
  아니면 Redis, 유효한 자격 증명 보호기, 비특권 포트가 모두 있어야 하며
  불완전한 설정은 서비스 시작 전에 실패 폐쇄된다.
- Linux Production DI 검증으로 UDP 진단과 snapshot 발행기의 Windows 전용
  생성자 가시성 가정을 제거했다.
- 13단계는 Compose, 클라우드, 방화벽, DNS, AWS 상태를 바꾸지 않는다.
  14단계에서 UDP를 의도적으로 매핑하고 공개 HTTPS 프록시의 정확한 주소를
  `Realtime:TrustedProxyAddresses`에 설정해야 하며 광범위 신뢰는 금지한다.

## 105. 분리된 원격 UDP 롤아웃 준비

- 현재 테스트 Authority는 같은 호스트의 Nginx 뒤에 Docker 컨테이너 하나로
  실행되며 `127.0.0.1:5272 -> 8080/tcp`만 공개한다. Docker bridge gateway는
  `172.17.0.1`이고 UDP 5273은 없으며 전환 전 공개 health endpoint는 정상이다.
- opt-in 롤아웃은 forwarded HTTPS 신뢰를 위해 정확한 gateway를 계산하고,
  mode 0600의 안정적인 자격 증명 보호 secret을 만들며, host UDP 매핑이 없는
  후보를 loopback TCP 5274에서 검증하고, 이전 컨테이너를 자동·수동 rollback용으로
  보존한다.
- 최종 승격 범위는 분리된 Authority 하나이며 loopback TCP 5272와 UDP 5273만
  매핑한다. 공개 HTTPS 메타데이터, 외부 인증 UDP 클라이언트, 신뢰 경로 fallback이
  모두 통과할 때까지 Unity UDP는 기본 비활성으로 유지한다.
- AWS 자격 증명이 없어 보안 그룹을 권한 있게 감사하거나 좁힐 수 없었다. 저장소
  메모에는 모든 트래픽 허용이라고 적혀 있지만 현재 도달성은 외부 UDP probe로만
  확인할 수 있으며, AWS 증거 없이 규칙이 좁혀졌다고 주장하지 않는다.
- 불변 후보 archive는 로컬에 준비했지만 외부 전송에 대한 명시적 승인 전까지
  원격 artifact 업로드와 전환은 보류한다.
